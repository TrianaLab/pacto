    CLI Reference¶

    Every command accepts -v / --verbose for debug-level logging and --help for detailed usage. --output-format is a global flag taking text (the default), json or markdown.

    What --output-format guarantees

    Read this before you parse Pacto's output in a script.

    • json describes a successful result. When a command fails to produce its result, for example because a reference is unreachable or pacto.lock is missing, the error goes to stderr as plain text and stdout stays empty, whatever --output-format says. A negative verdict is still a result: pacto validate on an invalid contract and pacto diff on a breaking change both print their whole JSON document to stdout and exit 1. An empty stdout tells you there is nothing to parse. Read stdout when it is non-empty, and read the exit code for the verdict.
    • Only pacto diff implements markdown, for posting a diff as a CI comment. Every other command renders text.
    • Keys are camelCase in every command ("path", "valid", "errors", "upToDate"). Before v4, init, validate, pack, pull and push emitted capitalised keys ("Path", "Valid").
    • An unrecognised value is rejected. --output-format yaml exits 1 with unsupported output format "yaml" before the command runs.

    The interactive and side-effecting commands (login, logout, update, mcp, dashboard) inherit the flag from the root command and always emit text.

    Global flags¶

          --config string          config file path
  -h, --help                   help for pacto
      --no-anim                disable animations
      --no-cache               disable OCI bundle cache
      --output-format string   output format (text, json, markdown) (default "text")
  -v, --verbose                enable verbose output

    Exit codes¶

    Pacto exits 0 or 1. 0 means the command produced its result and the result was acceptable. 1 means anything else, so the exit status alone cannot distinguish "the check failed" from "the command could not run".

    Exits 1 Exits 0
    pacto diff where the overall classification is BREAKING a POTENTIAL_BREAKING or NON_BREAKING diff
    pacto validate reporting at least one error validation that reported only warnings
    pacto lock --check on a stale lockfile, or with none at all (LOCK_MISSING) a lockfile that is up to date
    any command that could not run, for example on an unresolvable reference, an unreadable bundle or an unknown flag pacto impact run on declared-only sources, whatever it classifies (see below)

    Two cases affect CI gates:

    • A pacto diff against a missing reference exits 1, the same as a breaking change.
    • pacto impact exits 1 only when the change is breaking and a live source shows an incompatible consumer. Declared-only sources have no consumers, so it prints Classification: BREAKING and exits 0.

    Use stdout to tell a verdict from a failure. A command that produced a verdict writes it to stdout and puts a one-line summary on stderr. A command that could not run leaves stdout empty:

    Invocation Exit stdout stderr
    pacto diff --output-format json OLD NEW (breaking) 1 the full JSON result breaking changes detected
    pacto diff --output-format json oci://…/absent:1.0.0 NEW 1 empty old contract: artifact not found: …

    In a script, branch on stdout when it is non-empty, and treat an empty stdout with exit 1 as a tool failure.

    OCI version resolution¶

    All commands that accept oci:// references support automatic version resolution. When a reference omits the tag (for example oci://ghcr.io/acme/svc-pacto with no :1.0.0), pacto queries the registry for available tags and selects the highest semver version.

    For dependency references declared with a compatibility constraint, only tags satisfying the constraint are considered. For example, a dependency with compatibility: "^2.0.0" and available tags 1.0.0, 2.0.0, 2.3.0, 3.0.0 resolves to 2.3.0.

    Resolution ignores non-semver tags such as latest and main. Digest-pinned references (@sha256:...) and explicitly tagged references are used as-is.

    Constraints apply to the CLI's dependency graph

    The CLI applies compatibility constraints when it resolves a contract's declared dependencies, for example in pacto graph. The dashboard's version discovery selects the highest semver tag and ignores per-dependency compatibility constraints. Root-contract pulls (a tagless top-level oci:// ref) also select the highest semver tag with no constraint.

    pacto agent¶

    Runs until interrupted. Watches TCP listeners and outbound connection outcomes with an eBPF program, attributes each socket to the workload that created it (a Kubernetes pod, a container, a systemd unit or a pacto run session, from its cgroup, or from its network namespace when the cgroup names none) and publishes a snapshot every --publish-interval. --sink kubernetes writes the node's NodeRuntimeObservation status (pods only; what the Pacto operator's node agent DaemonSet runs); --sink stdout prints one JSON snapshot per line.

    --sink local and --sink evidence check workloads against their contracts on this host. The workloads come from --bindings (a YAML list of {match: {unit|container|cgroup|session|pid}, contract, host, interfaces: {name: port}, dependencies: {name: host:port}}) and with --docker from running containers labelled dev.pacto.contract=, dev.pacto.bind.<interface>=<port> and dev.pacto.dep.<dependency>=. Interfaces and dependencies are judged from the kernel's view, health and metrics capabilities by probing the bound port; a negative is reported once it persists for --stabilization-window. --sink local prints every target's compliance and findings each interval in --output-format; --sink evidence signs each target's evidence and sends it to an Evidence Server, which needs contracts pinned as oci://...@sha256:<digest>. Envelope sequences start at the wall clock in nanoseconds and count up, so they keep increasing across restarts as long as the clock does.

    Needs Linux 5.8 or later with BTF, root (or BPF, PERFMON and SYS_PTRACE) and the host's /proc and cgroupfs.

    pacto agent [flags]

    Examples:

      pacto agent --sink stdout --publish-interval 5s
  pacto agent --sink kubernetes --cgroup-root /host/sys/fs/cgroup
  pacto agent --sink local --docker --cgroup-root /host/sys/fs/cgroup
  pacto agent --sink evidence --bindings bindings.yaml --evidence-url https://evidence.example.com \
    --evidence-key agent.key --evidence-key-id k1 --evidence-producer host-1

    Flags:

          --bindings string                   with --sink local or evidence: YAML file binding workloads to contracts
      --cgroup-root string                where the host cgroup v2 hierarchy is mounted; empty attributes by network namespace only (default "/sys/fs/cgroup")
      --docker                            with --sink local or evidence: check running containers labelled dev.pacto.contract (Docker Engine API on /var/run/docker.sock)
      --docker-label-filter stringArray   with --docker: only check containers that also carry this label (key=value or key; repeatable, all must match), e.g. com.docker.compose.project=demo
      --enable-probing                    also probe the wire protocol of every interface found listening
      --evidence-key string               with --sink evidence: private key file envelopes are signed with
      --evidence-key-id string            with --sink evidence: key id (must match the server's trust entry)
      --evidence-producer string          with --sink evidence: producer id
      --evidence-url string               with --sink evidence: Evidence Server base URL
  -h, --help                              help for agent
      --namespace string                  namespace the NodeRuntimeObservation is written to with --sink kubernetes (default $POD_NAMESPACE)
      --node-name string                  name of this host; with --sink kubernetes also the NodeRuntimeObservation name (default $NODE_NAME)
      --proc-root string                  where the host /proc is mounted (a pod needs hostPID, a container --pid=host) (default "/proc")
      --publish-interval duration         how often a snapshot is published (whole seconds) (default 30s)
      --resync-interval duration          how often workloads, network namespaces and listeners are re-read from /proc (default 1m0s)
      --ringbuf-size uint32               kernel ring buffer size in bytes; a power of two and a multiple of the page size (default 262144)
      --sink string                       where snapshots go: one of [kubernetes stdout local evidence] (default "stdout")
      --stabilization-window duration     how long a negative must persist before it is reported (default 2m0s)

    pacto dashboard¶

    Launches an operational dashboard over the fleet snapshot: the same operational graph the CLI's pacto fleet commands query, served as a web UI.

    The dashboard is the exploration and observability layer of the Pacto system. It visualizes the same contracts the CLI manages and the operator verifies, organised around four workflows: an operational Overview, the Services inventory, the Operational Graph and Change analysis.

    Each positional argument is a pacto source reference: - oci://registry/repo → OCI registry source (can be repeated) - ./path/to/dir → local filesystem source (at most one)

    When no arguments are given, sources are auto-detected: - local: enabled if pacto.yaml is found in the working directory - cache: enabled if the OCI bundle cache (~/.cache/pacto/oci) holds bundles - k8s: enabled if a kubeconfig or in-cluster config resolves - oci: from the positional arguments, the PACTO_DASHBOARD_REPO env var, or the status.contract.resolvedRef of the cluster's Pacto resources

    When running alongside the Kubernetes operator, OCI repositories are automatically discovered from the status.contract.resolvedRef fields of Pacto CRD resources on every refresh. The result combines runtime state from the operator with contract content from OCI.

    Every source contributes to one snapshot, rebuilt in the background, and each answer carries the as-of time and the completeness of the sources behind it.

    pacto dashboard [sources...] [flags]

    Examples:

      # Start dashboard with auto-detected sources
  pacto dashboard

  # Start from a specific directory
  pacto dashboard ./services

  # Include OCI repositories
  pacto dashboard oci://ghcr.io/org/order-service oci://ghcr.io/org/payment-service

  # Mix local and OCI sources
  pacto dashboard ./services oci://ghcr.io/org/payment-service

  # Custom port
  pacto dashboard --port 9090

  # Specify Kubernetes namespace (default: all namespaces)
  pacto dashboard --namespace production

    Flags:

          --cors-origin string                explicit cross-origin allowed to call the API (default: same-origin only)
      --delivery-namespace string         namespace Pacto delivery runs in, whose published identity policy (agent, break-glass and human groups, team prefix) says who is an agent and who may answer (default "pacto-delivery")
      --delivery-trust string             the trust config delivery records are verified with, so History reads signed records (the recorder's PEM public key or a YAML trust config; default $PACTO_DELIVERY_TRUST)
  -h, --help                              help for dashboard
      --host string                       bind address for the dashboard server (default "127.0.0.1")
      --mira-url string                   Mira's address, to link the health-check citations of delivery verdicts
      --namespace string                  Kubernetes namespace (empty = all namespaces)
      --oidc-ca-file string               PEM bundle of the CAs that sign the issuer's certificate, trusted on top of the system roots (also PACTO_DASHBOARD_OIDC_CA_FILE)
      --oidc-client-id string             OpenID Connect client id of the dashboard
      --oidc-display-name string          the identity provider's name on the sign-in button, as in Sign in with Keycloak (default OIDC; also PACTO_DASHBOARD_OIDC_DISPLAY_NAME)
      --oidc-extra-scopes strings         scopes to ask for beyond openid, profile and groups
      --oidc-groups-claim string          ID token claim the API server takes the groups from; must match its claim mapping (default groups)
      --oidc-groups-prefix string         prefix the API server puts before every group; must match its claim mapping
      --oidc-internal-issuer-url string   address the dashboard reaches the issuer at when it differs from the public issuer URL browsers use, such as an in-cluster Service; ID tokens must still name the public issuer (also PACTO_DASHBOARD_OIDC_INTERNAL_ISSUER_URL)
      --oidc-issuer-url string            OpenID Connect issuer people sign in with before the dashboard shows anything; every view then shows what the signed-in person's Kubernetes RBAC lets them read, and every action runs as them (also PACTO_DASHBOARD_OIDC_ISSUER_URL; the client secret comes from PACTO_DASHBOARD_OIDC_CLIENT_SECRET)
      --oidc-redirect-url string          the dashboard's /auth/callback as browsers reach it (https)
      --oidc-username-claim string        ID token claim the API server takes the username from; must match its claim mapping (default sub)
      --oidc-username-prefix string       prefix the API server puts before the username; must match its claim mapping (default the issuer URL and #, none for the email claim; - for none)
      --port int                          port for the dashboard server (default 3000)
      --session-idle-timeout duration     a session without a request for this long ends (default 1h)
      --session-max-age duration          a session ends this long after sign-in, renewed or not (default 12h)
      --token-login                       let people sign in by pasting a Kubernetes bearer token, for a cluster whose API server trusts no identity provider; a token session never decides on a held change (also PACTO_DASHBOARD_TOKEN_LOGIN)

    It auto-detects sources: pass OCI repositories as arguments, or run it next to the operator (with a kubeconfig) and it discovers OCI repositories from each Pacto resource's status.contract.resolvedRef. Use --no-cache for a cold start (it skips scanning pre-existing cached bundles; bundles fetched during the session are still cached).

    pacto delivery¶

    Pacto delivery decides which version each environment (a Stage) runs. Every change is an Operation: plan it to see what the promoter will do and who must agree, propose it, and a person approves only when the contracts say a consumer would break, Pacto cannot see enough or the Stage asks for approval on every promote.

    There is no approve tool for agents. approve is for people.

    pacto delivery [flags]

    Flags:

          --delivery-namespace string   namespace Pacto delivery runs in, whose published identity policy (agent, break-glass and human groups, team prefix) says who is an agent and who may answer (default "pacto-delivery")
  -h, --help                        help for delivery
  -n, --namespace string            namespace of the Stage and its Operations (default "default")
      --trust string                the trust config delivery records are verified with: the recorder's PEM public key, or a YAML file of keys and the streams each may sign (default $PACTO_DELIVERY_TRUST)

    pacto delivery approve¶

    Record your decision on a held operation, as the person your kubeconfig signs you in as. When the promoter asks for a fresh login (delivery.promoter.authFreshness), the command instead makes you log in again in your browser (prompt=login, max_age=0) with its own OpenID Connect client and sends the Approval with that login's token, never your kubeconfig's: an agent running in your shell cannot approve as you without you typing your password at that moment. The token is not stored.

    pacto delivery approve <operation> [flags]

    Flags:

          --decision string             approve, reject or accept-unknown (default "approve")
  -h, --help                        help for approve
      --note string                 why, for the record
      --oidc-ca-file string         PEM bundle of the CAs that sign the issuer's certificate, trusted on top of the system roots (also PACTO_DELIVERY_OIDC_CA_FILE)
      --oidc-client-id string       OpenID Connect client used only for approvals, never by a kubeconfig (a confidential client's secret comes from PACTO_DELIVERY_OIDC_CLIENT_SECRET) (default "pacto-approve")
      --oidc-extra-scopes strings   scopes to ask for beyond openid, profile and groups

    pacto diff¶

    Compares two contracts (local paths or oci:// references) and produces a classified change set (BREAKING, POTENTIAL_BREAKING, NON_BREAKING).

    pacto diff <old> <new> [flags]

    Examples:

      # Compare a remote contract with a local one
  pacto diff oci://ghcr.io/acme/svc-pacto:1.0.0 my-service

  # Markdown output for CI comments
  pacto diff --output-format markdown oci://ghcr.io/acme/svc-pacto:1.0.0 my-service

    Flags:

      -h, --help                     help for diff
      --new-set stringArray      set a value on the new contract (e.g. --new-set service.version=2.0.0)
      --new-values stringArray   values file to merge into the new contract (can be repeated)
      --old-set stringArray      set a value on the old contract (e.g. --old-set service.version=1.0.0)
      --old-values stringArray   values file to merge into the old contract (can be repeated)

    Exit code: 1 when the overall classification is BREAKING, and also when the diff could not be produced. A non-zero exit alone is therefore no contract verdict. See Exit codes for how to tell the two apart. A POTENTIAL_BREAKING result exits 0, so a CI gate that stops on it must read the classification.

    The diff engine performs deep comparison of referenced OpenAPI specs, detecting changes at the path, method, parameter, request body and response level. The optional docs/ directory is ignored: documentation changes produce no diff entries and leave the compatibility classification unchanged.

    When both bundles include an sbom/ directory with recognized SBOM files (.spdx.json or .cdx.json), pacto diff reports package-level changes: added, removed or modified packages (version and license). SBOM changes are informational and leave the overall classification and exit code unchanged.

    When dependencies change between the old and new contracts (version upgrades, additions or removals), a dependency graph diff section is displayed showing the tree of affected nodes.

    See Change Classification for the full rules.

    pacto evidence serve¶

    pacto init¶

    Writes the contract for the service in dir (default: the current folder).

    An empty or new folder gets a blank contract with the bundle structure (interfaces/, configuration/). A folder that already holds a service gets a contract read from its Dockerfile and Kubernetes manifests, publish section included, and a list of what Pacto found and what it could not tell (Unknown). --delivery also writes the cluster pieces: the Pacto resource that checks the running service, and per environment a Stage with the Flux OCIRepository and Kustomization it applies through. Each Stage starts at observe: it plans every new version and moves nothing, and the OCIRepository stays pinned to the tag you deploy, so GitOps keeps applying what it did. The last environment's Stage also asks a person to approve every promote.

    Several folders are each pactified, with a summary at the end. --cluster drafts a contract for every workload in the namespaces that no Pacto describes yet, in <out>/<namespace>/<name>: its manifests are read from the cluster, and the services its pods were seen calling become dependencies pinned to the version seen running, for you to widen. Drafts are only written, never published, and a draft that is not valid fails the command.

    It only adds files and missing .pactoignore lines; any other file already there is yours and is left as it is, so running it twice is safe. --plan shows exactly what would be added and changes nothing.

    pacto init [dir...] [flags]

    Examples:

      pacto init my-service
  pacto init --plan
  pacto init --delivery --owner payments --fleet ../contracts
  pacto init --delivery --no-transparency-log --insecure-registry
  pacto init --delivery --registry-secret registry-creds
  pacto init services/checkout services/payments --plan
  pacto init --cluster --namespace shop --out drafts

    Flags:

          --cluster                  draft a contract for every workload in the cluster that no Pacto describes, reading the current kubeconfig context
      --delivery                 also write the cluster pieces: the Pacto resource, a Stage per environment and its Flux OCIRepository and Kustomization
      --env strings              environments for --delivery, in promotion order (default [test,prod])
      --fleet strings            folders of other services' contracts to find the services that use this one
  -h, --help                     help for init
      --insecure-registry        with --delivery: the Flux OCIRepositories read the registry over plain HTTP (a local registry only)
      --name string              service name (default: the workload's name, then the folder's)
      --namespace strings        with --cluster: a namespace to read; repeat it for more (default: every namespace)
      --no-transparency-log      write transparencyLog: false under publish.sign, so signatures stay out of the public transparency log (offline signing, a throwaway key)
      --out string               with --cluster: the folder the drafts go in, one <namespace>/<name> folder each
      --owner string             the team that owns the service (default: the workload's team label)
      --plan                     show what would be added and change nothing
      --registry string          where to publish, as host/path (default: read from the workload's image)
      --registry-secret string   with --delivery: the docker-registry Secret, in each environment's namespace, that Flux and the Pacto resource log in to a private registry with

    Scaffolds three files: a valid pacto.yaml, a placeholder OpenAPI spec at interfaces/openapi.yaml and a configuration JSON Schema at configuration/schema.json.

    <name> is the service name: it becomes the directory and service.name, which must match ^[a-z0-9]([a-z0-9-]*[a-z0-9])?$. pacto init fleet/checkout-web therefore scaffolds a bundle that fails validation: service.name gets the whole path and fails SCHEMA_VIOLATION. To scaffold inside a directory, cd there first and pass the bare name.

    All three are required by the scaffolded contract, because its interfaces: and configurations: sections point at the other two files. If you delete a directory, also delete the section that references it, or validation fails with FILE_NOT_FOUND. A contract that declares neither section needs only pacto.yaml, so drop the section and the directory together.

    The scaffold fails validate --readiness on purpose

    Its two placeholder readiness claims are not-done, which scores 0 against the scaffolded minScore: 80 and fails with READINESS_GATE_UNMET. Plain pacto validate passes, because the gate is opt-in. Fill the claims in as the work lands. The placeholder is the starting position of a real assessment, so keep it and update it.

    pacto mcp¶

    Starts a Model Context Protocol (MCP) server exposing Pacto tools for AI agents. Supports stdio (default) and HTTP transports.

    When a bundle reference (local directory or oci:// ref) is given, the server also exposes one executable tool per OpenAPI operation in the bundle's openapi interfaces, plus a pacto_skill tool for any skills/*.md domain knowledge. Read-only (GET/HEAD) operations are exposed by default; pass --allow-writes to expose mutating operations.

    With --root, the server exposes a read-only contract catalog: the given roots plus their dependency closure, resolved once at startup and then frozen, so the session keeps its startup view even when a registry tag moves. Roots that fail to resolve stay visible as partial knowledge. The catalog grants no authorization and executes nothing.

    With --fleet, the server exposes the read-only operational-graph query tools over one snapshot. The shared fleet source flags (--local, --target-state, --evidence-url, --traces, --oci, --cache, --k8s, --namespace and --freshness) compose that snapshot and are read in --fleet mode only.

    With --delivery, the server exposes the Pacto delivery tools (pacto_delivery_*) over the ambient cluster: operation types, plan, get, explain, history, blame, undo plans and record checks, plus propose and cancel only when the apiserver says the caller is an agent (a service account, or an agent by the identity policy Pacto delivery publishes). It has no approve tool.

    Over HTTP, --auth-issuer and --resource make every request carry a bearer token the server verifies (issuer, audience, expiry) and publish protected-resource metadata (RFC 9728); a bind beyond loopback needs them and refuses --auth and --allow-writes, which would lend this process's service credential to every caller. With --delivery the server then exchanges each caller's token for one the apiserver accepts (RFC 8693, --exchange-client-id) and builds the tools for that caller on every request, so an agent proposes as itself and a person gets the read-only tools. With --fleet the server names each caller with the claim mapping (--oidc-username-claim, --oidc-username-prefix, --oidc-groups-claim and --oidc-groups-prefix) and asks Kubernetes RBAC about that user; the API server does not confirm it, so the mapping must match its claimMappings.

    With --publish, the authoring server also exposes pacto_publish_plan and pacto_publish, which publish a contract's version exactly as pacto publish does, with this process's registry credentials.

    A bundle reference, --root, --fleet, --delivery and --publish select different servers and cannot be combined.

    pacto mcp [bundle-ref] [flags]

    Examples:

      # Start MCP server over stdio (default)
  pacto mcp

  # Start MCP server over HTTP
  pacto mcp -t http

  # Expose a bundle's OpenAPI operations as agent tools

  # Include mutating operations and an auth credential
  pacto mcp oci://ghcr.io/acme/svc:1.0.0 --base-url https://api.example.com \
    --auth bearerAuth=$TOKEN --allow-writes

  # Expose a contract catalog discovered from explicit roots
  pacto mcp --root oci://ghcr.io/acme/platform:1.4.0 --root ./experimental-platform

      --auth-issuer string            OpenID issuer whose bearer tokens every HTTP request must carry
      --base-url string               base URL for live invocation (overrides the OpenAPI servers[] URL)
      --cache                         include every bundle in the local OCI cache as an offline baseline revision
      --delivery                      expose the Pacto delivery tools over the ambient cluster
      --delivery-namespace string     in --delivery mode: namespace Pacto delivery runs in, whose published identity policy (agent, break-glass and human groups, team prefix) says who is an agent and who may answer (default "pacto-delivery")
      --delivery-trust string         in --delivery mode: the trust config delivery records are verified with (the recorder's PEM public key or a YAML trust config; default $PACTO_DELIVERY_TRUST)

      --oidc-username-claim string    ID token claim the API server takes the username from; must match its claim mapping (default sub)
      --oidc-username-prefix string   prefix the API server puts before the username; must match its claim mapping (default the issuer URL and #, none for the email claim; - for none)

    The default server exposes the four authoring tools below. A bundle reference and four flags select a different server, each with its own tools. See Server modes after this table:

    Tool Description
    pacto_create Create a new contract from intent-level inputs (name, description, interfaces, runtime semantics). Supports dry run.
    pacto_edit Edit an existing contract: add or remove interfaces and dependencies, change runtime, update metadata. Supports dry run.
    pacto_check Validate a contract and return errors, warnings and actionable improvement suggestions.
    pacto_schema Return the Pacto format explanation and full JSON Schema reference.

    These four authoring tools operate on local contract directories (they read and write pacto.yaml on disk) and accept no oci:// refs.

    Server modes¶

    The default server exposes the authoring tools above. A bundle reference, --root, --fleet, --publish and --delivery each select a different server. Passing more than one is an error:

    Invocation Server
    pacto mcp Authoring tools.
    pacto mcp <bundle-ref> Authoring tools plus the bundle's OpenAPI operations as executable agent tools, alongside a pacto_skill tool for any bundled skills.
    pacto mcp --fleet Authoring tools plus read-only operational-graph query tools.
    pacto mcp --publish Authoring tools plus pacto_publish_plan and pacto_publish, which publish a version to your registry. Stdio only.
    pacto mcp --delivery Authoring tools plus the delivery tools over the cluster your kubeconfig points at: read delivery state and, for an agent, ask for or cancel a change. There is no approve tool.
    pacto mcp --root <ref> [--root <ref>] A read-only contract catalog discovered from the named roots. Catalog mode registers only catalog tools, and none of them writes to disk.

    --root is repeatable and takes a local bundle directory or an oci:// reference. The roots and their dependency closure are resolved once, at startup, through the same reference parsing, credentials and cache the rest of the CLI uses; after that the session is frozen, so every answer reflects startup state even if a registry tag moves. A root that fails to resolve stays visible with a classified reason, and the catalog reports itself as partial. The catalog reads only the named roots and their closure, never refreshes and persists nothing.

    pacto publish¶

    Publishes every artifact the contract's publish section declares (pactoVersion 2.1), the contract bundle and the deploy artifact Flux applies, all tagged with service.version. Docker or the declared command builds. Pacto pushes each artifact to a new tag, signs every digest with Sigstore (built in) and attaches the SBOM files the build wrote. A breaking change since the last published version is refused below a major bump (a minor before 1.0).

    --plan shows what is missing and changes nothing. Running publish again from the same commit finishes what is missing and changes nothing else. --propose hands the deploy artifact to Pacto delivery as a promote on a Stage, once the Stage records it as published, meaning Flux polled the candidate OCIRepository and verified the signature. It waits up to --propose-timeout for that.

    pacto publish [dir] [flags]

    Examples:

      # What would be published, and what refuses it
  pacto publish --plan

  # The same, for the contract in ./payments
  pacto publish --plan ./payments

  # Publish, then propose the version on the test Stage
  pacto publish --propose test/payments

    Flags:

      -h, --help                       help for publish
  -p, --path string                path to contract directory, the same as [dir] (default: current directory)
      --plan                       show what is missing and what refuses it; change nothing
      --propose string             after publishing, propose the deploy artifact on <namespace>/<stage> (needs delivery.enabled on the pacto-operator chart)
      --propose-timeout duration   how long --propose waits for the Stage to record the version as published (default 10m0s)
      --revision string            source revision stamped on every artifact (default: the git commit of the contract directory, which must have no uncommitted changes)
      --set stringArray            set a contract value (e.g. --set service.version=2.0.0)
      --values stringArray         values file to merge into the contract (can be repeated; last wins)

    Validates the contract (including remote policy and config refs), builds an OCI artifact and pushes it to the specified registry reference. Pushing the same content again succeeds without writing anything; different content under an existing reference is refused unless --force.

    pacto push <ref> [flags]

      # Push with auto-tag (uses contract version)
  pacto push oci://ghcr.io/acme/my-service-pacto -p my-service

  # Push with explicit tag
  pacto push oci://ghcr.io/acme/my-service-pacto:latest -p my-service

  pacto push oci://ghcr.io/acme/my-service-pacto -p my-service --force

  -h, --help                 help for push
  -p, --path string          path to contract directory (default: current directory)
      --set stringArray      set a contract value (e.g. --set service.version=2.0.0)
      --values stringArray   values file to merge into the contract (can be repeated; last wins)

    If the tag already holds the same content, pacto push succeeds and writes nothing. If it holds different content, pacto push refuses with a non-zero exit and writes nothing. Use --force to overwrite.

    --values has no -f shorthand on push

    On every other override-taking command -f is the shorthand for --values. On pacto push, -f is --force, so --values must be spelled out in full here.

    pacto run¶

    Starts the command and watches the TCP sockets of its whole process tree: the interfaces bound with --bind must be listened on, the dependencies bound with --dep reached. Every --interval it prints the contract's compliance and findings in --output-format; once the command exits it prints a final round from the last view taken while the command ran, and exits with the command's exit code. With --fail-on it exits 1 instead of 0 when the final verdict is that bad or worse.

    The command runs in a process group of its own, so a Ctrl-C reaches it once. When pacto run owns the terminal, the command's group takes it over: it reads the terminal and gets Ctrl-C and Ctrl-Z straight from it, and pacto run takes the terminal back once it exits. Otherwise SIGINT and SIGTERM sent to pacto run are passed on to the command's whole group.

    Pacto leaves the command's stdin, stdout and stderr untouched. Rounds go to stderr, each in a single write, or with --report to a file: the file is truncated when the run starts and every round is appended to it in a single write, so a reader following it sees whole rounds (with json, one object per line).

    With root (or BPF, PERFMON, SYS_PTRACE and write access to its own cgroup) on Linux 5.8 or later with BTF and cgroup v2, the command starts inside a new cgroup pacto-run-<pid> and an eBPF program sees every listener and every connection outcome of the tree, failures included (collector pacto-run+ebpf). Otherwise it falls back to polling /proc every second and says so (collector pacto-run): listeners are seen in full, so a missing one is still confirmed, but a connection is seen only while it is open at a poll and a failed connection never, so a dependency is reported reachable or unknown, never unreachable. If the program attached but the command cannot start inside the new cgroup, the run falls back to polling too and says so. Elsewhere than Linux the command runs unobserved and every runtime assertion is unsupported.

    A negative is reported once it persists for --stabilization-window. Health and metrics capabilities are probed on --host at their bound interface's port. With --evidence-url every round is also signed and sent to an Evidence Server, which needs the contract pinned as oci://...@sha256:<digest>.

    pacto run --contract <dir|oci ref> [flags] -- command [args...]

    Examples:

      pacto run --contract ./payments --bind api=8080 --dep postgres=127.0.0.1:5432 -- ./payments-server
  pacto run --contract oci://ghcr.io/acme/payments:1.4.0 --bind api=8080 --fail-on noncompliant \
    --stabilization-window 30s --output-format json --report rounds.jsonl -- java -jar payments.jar

    Flags:

          --bind stringArray                interface=port the command serves the interface on (repeatable)
      --cgroup-root string              cgroup v2 directory the session cgroup is created in (default: the caller's own cgroup under /sys/fs/cgroup)
      --contract string                 contract bundle directory or oci:// reference (required)
      --dep stringArray                 dependency=host:port the command reaches the dependency at (repeatable)
      --enable-probing                  also probe the wire protocol of every interface found listening
      --evidence-key string             private key file envelopes are signed with
      --evidence-key-id string          key id (must match the server's trust entry)
      --evidence-producer string        producer id
      --evidence-url string             Evidence Server base URL
      --fail-on string                  exit 1 when the command exits 0 but the final verdict is this bad or worse: one of [none noncompliant unknown] (default "none")
  -h, --help                            help for run
      --host string                     address capability and protocol probes dial (default "127.0.0.1")
      --interval duration               how often a round is evaluated and printed (whole seconds) (default 10s)
      --proc-root string                where /proc is mounted (default "/proc")
      --report string                   file every round is appended to instead of stderr (truncated when the run starts)
      --ringbuf-size uint32             kernel ring buffer size in bytes; a power of two and a multiple of the page size (default 262144)
      --stabilization-window duration   how long a negative must persist before it is reported (default 2m0s)

    A new version of pacto is available: v1.0.0 -> v1.2.0

    pacto validate¶

    Validates a pacto.yaml in the given directory (or oci:// reference) against the specification, running the three validation layers: structural, cross-field and policy.

    pacto validate [dir | oci://ref] [flags]

    Examples:

      # Validate a local contract
  pacto validate my-service

  # Validate from current directory
  pacto validate

  # Validate from an OCI registry
  pacto validate oci://ghcr.io/acme/my-service-pacto:1.0.0

  # JSON output
  pacto validate --output-format json my-service

  # Also check the readiness gate (fail if score < minScore)
  pacto validate --readiness my-service

    Flags:

      -h, --help                 help for validate
      --readiness            also check the readiness gate: fail if the derived readiness score is below the declared (or default 100) minScore. Opt-in because gate evaluation is time-dependent (check expiry is compared against the run time), which would otherwise make plain validation non-deterministic
      --set stringArray      set a contract value (e.g. --set service.version=2.0.0)
  -f, --values stringArray   values file to merge into the contract (can be repeated; last wins)

    The --readiness gate is opt-in because it is time-dependent: it compares the assessment's single readiness.expires date against the run time, which would make plain validate non-deterministic. Expiry is declared once for the whole assessment. Individual claims carry no expires field, and adding one fails to load with PARSE_ERROR. Without the flag, validation checks the contract's structure and rules. It still checks the shape of readiness claims and skips the freshness gate.     Environment variables¶

    Boolean variables are parsed the way Go parses a boolean: 1, t, T, true, TRUE and True enable them and 0, f, F, false, FALSE and False disable them. Any other value, including yes and on, reads as off with no warning. The two opt-outs PACTO_NO_ANIM and PACTO_NO_UPDATE_CHECK are the exception: for them any other non-empty value reads as on.

    Variable Description
    PACTO_CACHE_DIR Cache directory for the pacto dashboard bundle scan. The core CLI cache location is controlled by XDG_CACHE_HOME (see below).
    PACTO_NO_CACHE Boolean. Disable OCI bundle caching (equivalent to --no-cache)
    PACTO_NO_ANIM Boolean. Disables spinners and animations (equivalent to --no-anim).
    PACTO_NO_UPDATE_CHECK Boolean. Disables automatic update checks.
    PACTO_REGISTRY_USERNAME Registry username for authentication
    PACTO_REGISTRY_PASSWORD Registry password for authentication
    PACTO_REGISTRY_TOKEN Registry token for authentication
    PACTO_INSECURE_REGISTRIES Comma-separated registry hosts that Pacto reaches over plain HTTP. It applies to every registry access: pacto push, pacto pull, dependency and policy resolution and the Evidence Server. Scoped per host, so HTTPS registries are unaffected. Loopback hosts use plain HTTP without being listed. Use it only for a controlled in-cluster registry: it disables transport encryption, so credentials and payloads travel in the clear.
    PACTO_EVIDENCE_SOURCE_URL Base URL of an Evidence Server whose read-only operational-graph contribution pacto dashboard should consume. The operator sets it when it wires a managed Evidence Server. Unset means no evidence source configured, which the dashboard reports separately from an unavailable source.
    XDG_CONFIG_HOME Override config directory (default: ~/.config). Affects pacto login credentials and update check cache
    XDG_CACHE_HOME Override cache directory (default: ~/.cache). Affects OCI bundle cache location

    Dashboard environment variables¶

    The following variables configure the dashboard when set (see also Dashboard Container). Each mirrors the flag named beside it: an explicitly passed flag wins, and otherwise the variable overrides that flag's default.

    Variable Flag Description
    PACTO_DASHBOARD_REPO (positional args) Comma-separated OCI repositories, used only when no positional oci:// argument is given
    PACTO_DASHBOARD_HOST --host Bind address (default: 127.0.0.1)
    PACTO_DASHBOARD_PORT --port HTTP port (default: 3000)
    PACTO_DASHBOARD_NAMESPACE --namespace Kubernetes namespace filter (empty = all)
    PACTO_DASHBOARD_CORS_ORIGIN --cors-origin One explicit origin allowed to call the API. Unset means same-origin only.
    PACTO_DASHBOARD_TRACES --traces OTLP/JSON trace files to fold observed dependencies from
    PACTO_DASHBOARD_TRACE_SOURCES --trace-source Named offline trace sources as NAME=PATH, where NAME is the source's identity (what the fleet, the API and the dashboard's Data Source list call it) and PATH is the trace file location. Identity and location are separate, so reordering the configuration or moving the file keeps the source's name. Two sources whose files share a basename stay two sources. A name must be unique across every Data Source the dashboard assembles.

    The two list variables split on whitespace

    PACTO_DASHBOARD_TRACES and PACTO_DASHBOARD_TRACE_SOURCES go through the same generic flag binding as every other dashboard variable, which splits a multi-valued string on spaces. PACTO_DASHBOARD_TRACES="a.json b.json" supplies two files; PACTO_DASHBOARD_TRACES=a.json,b.json supplies one, named a.json,b.json. PACTO_DASHBOARD_REPO is read directly and splits on commas.

    The dashboard starts either way: it skips a trace file it cannot read, so the symptom is missing observed dependencies with no error. Check the snapshot's reported limitations if the operational graph looks emptier than you expect.

    Authentication¶

    Pacto follows this credential resolution chain:

    1. Environment variables (PACTO_REGISTRY_TOKEN, or PACTO_REGISTRY_USERNAME + PACTO_REGISTRY_PASSWORD)
    2. Pacto config (~/.config/pacto/config.json, written by pacto login, which persists --username and --password)
    3. GitHub CLI (gh auth token, for ghcr.io and docker.pkg.github.com only)
    4. Docker config (~/.docker/config.json) and credential helpers (including cloud-registry helpers for ECR, GCR and ACR)
    5. Anonymous fallback

    For GitHub registries, step 3 means you can skip pacto login entirely if you have gh authenticated with the write:packages scope (see pacto login above).

    Pacto stores no credentials in contract files.
