    Drive Pacto from an agent¶

    This page is for an engineer who wants an AI agent, such as Claude, Cursor or Copilot, to use Pacto. It covers how to connect the agent, what it can do and the limits that keep it safe. Every tool and input is listed in the MCP reference.

    Words in links are defined in the glossary: MCP, contract, bundle, fleet, delivery and change.

    Connect your agent¶

    Install the pacto command first (Installation) and check that pacto version works. Every agent then starts pacto mcp and talks to it over its standard input and output. Pick yours:

    Add to your project's .mcp.json:

    {
  "mcpServers": {
    "pacto": { "command": "pacto", "args": ["mcp"] }
  }
}

    Add to claude_desktop_config.json (~/Library/Application Support/Claude/ on macOS, %APPDATA%\Claude\ on Windows):

    {
  "mcpServers": {
    "pacto": { "command": "pacto", "args": ["mcp"] }
  }
}

    Add to .cursor/mcp.json:

    {
  "mcpServers": {
    "pacto": { "command": "pacto", "args": ["mcp"] }
  }
}

    Add to .vscode/mcp.json (requires VS Code 1.99+ and the Copilot Chat extension):

    {
  "servers": {
    "pacto": { "command": "pacto", "args": ["mcp"] }
  }
}

    That starts the default server. To pick another, add its flag to args, for example ["mcp", "--delivery"].

    Pick what the agent may do¶

    How you start the server decides what the agent can reach. Pick one mode: --root, --fleet, a bundle, --publish and --delivery cannot be combined with each other.

    Start it with The agent can It can change
    pacto mcp Write and check contracts in local folders Contract files on disk
    pacto mcp --root oci://... Read published contracts and what they depend on Nothing
    pacto mcp --fleet Everything the default does, plus answer questions about your fleet Contract files on disk
    pacto mcp ./my-service --base-url https://... Everything the default does, plus call the service's own API, one tool per operation. The bundle is a folder or an oci:// reference; --base-url is where the running service answers Contract files; the live service only with --allow-writes
    pacto mcp --publish Everything the default does, plus publish a version to your registry Contract files and your registry
    pacto mcp --delivery Everything the default does, plus read delivery state and, if the cluster counts it as an agent, ask for or cancel a change Contract files and its own requests; it can never approve

    If the agent must change nothing at all, use --root.

    Files. The contract tools write to the folder the agent names in each call, relative to the folder the server was started in. Pacto does not limit which folder, so start the server in the project the agent should work on, as a user that can write only there. Claude Code and Cursor start it in your project; for Claude Desktop, have the agent pass full paths.

    Fleet. --fleet reads the sources you name with more flags, such as --local ./contracts for folders, --oci <ref> for published contracts and --k8s for your kubeconfig's cluster. See pacto mcp.

    Credentials. --publish, --root and --fleet use the registry logins of pacto login. A bundle's API calls use --auth name=value for the service's own sign-in, as its OpenAPI document declares it.

    Delivery: who counts as an agent¶

    --delivery acts on the cluster your kubeconfig points at, as the identity in it. Every service account counts as an agent, and so does anyone the platform team's groups name as one; see Who counts as a person, an agent or a team. Only an agent gets the tools to ask for and cancel a change; a person gets only the read tools. So give the agent a kubeconfig for its own service account, never yours: an agent holding your credentials is you to the cluster. Have the agent fill on_behalf_of on pacto_delivery_operation_propose with the person it works for: then that person cannot also approve the change, which keeps two people on every change.

    What keeps it safe¶

    • An agent never approves. In delivery mode it can ask for a change, and Pacto's checks and the owning team decide (Who may approve). There is no approve tool.
    • Calls to your service are read-only by default. Only GET and HEAD operations become tools unless you pass --allow-writes. Each call stops after 30 seconds and follows no redirect.
    • Tools carry no safety labels. Pacto does not mark its tools as read-only or destructive in MCP, so build allow-lists by name from the table below.
    • Partial answers say so. Fleet answers carry asOf, the time they describe, and completeness, complete or partial. When a source was unreachable the answer says partial, and "not found" then means "not known".
    • Answers are frozen at start. --root, --fleet and a bundle (the ./my-service argument) are read once when the server starts. Restart it to see newer services or versions.
    • Over the network, callers must sign in. By default the server talks over standard input and output. With -t http it serves HTTP on this machine only. Serving other machines needs --auth-issuer and --resource, so every request carries a token from your company sign-in, and the server then refuses --auth and --allow-writes, which would lend one credential to every caller. See agents over the network.

    Which tools exist¶

    Tools Mode Read or write
    pacto_create, pacto_edit every mode but --root Write contract files. pacto_create with pactify: true does what pacto init does for a folder or a cluster (see Pactify a service)
    pacto_check, pacto_schema every mode but --root Read
    pacto_fleet_search, pacto_fleet_get, pacto_fleet_graph, pacto_fleet_status, pacto_fleet_explain, pacto_impact --fleet Read
    pacto_catalog_revision, plus two MCP resources (documents the agent reads): pacto://catalog and pacto://catalog/closure, the contracts you named plus everything they depend on --root Read
    One tool per API operation, named by its operationId (or <method>_<path>) a bundle Calls your service: read-only, or its write operations too with --allow-writes
    pacto_skill a bundle Read: returns the notes a bundle ships for agents in skills/*.md
    pacto_publish_plan --publish Read
    pacto_publish --publish Writes to your registry
    pacto_delivery_operation_types, pacto_delivery_operation_plan, pacto_delivery_get, pacto_delivery_explain, pacto_delivery_history, pacto_delivery_blame, pacto_delivery_undo_plan, pacto_delivery_record_verify --delivery Read
    pacto_delivery_operation_propose, pacto_delivery_cancel --delivery, agents only Ask for or cancel a change

    Pacto skips any API operation named pacto_*, so the prefix always means a Pacto tool. Inputs and outputs are in the MCP reference.

    Try it¶

    You:    Create a pacto contract for a stateful Go HTTP API called user-service
        that stores data in PostgreSQL
Claude: [writes pacto.yaml with an HTTP interface and marks the service as
         keeping data that survives a restart]

You:    Add a dependency on payments-api
Claude: [calls pacto_edit with add_dependencies]

You:    Check the contract in ./user-service
Claude: user-service is valid.

    Pacto adds a dependency only from calls it observed, which pactify does when the node agent runs in the cluster. The node agent is a Pacto program on each Kubernetes node, separate from the AI agent that calls these tools. Add any other dependency yourself, as in the second prompt.

    If the tools do not show up¶

    1. Run pacto version to check Pacto is installed and on your PATH.
    2. Check your MCP configuration file for JSON syntax errors.
    3. Ask your agent to list its tools (in Claude Code, /mcp).
    4. Add -v to args to see what the server does while it starts, such as reading a bundle from a registry. It logs nothing per tool call.
