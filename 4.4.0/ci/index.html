    Put it in your repository¶

    Add Pacto to your build pipeline (CI) so a pull request that would break the services using yours fails its checks, and every merge publishes a version. This page assumes you have a contract, pacto.yaml, from Pactify a service. The examples use the names from that page: the contract is published to oci://ghcr.io/acme/contracts/my-service, the publish.bundle field of pacto.yaml.

    What to commit¶

    Commit what pacto init wrote (pacto.yaml, .pactoignore, .gitignore, delivery/ and any files the contract points to, such as an OpenAPI document).

    If your contract lists dependencies, also run pacto lock . and commit the pacto.lock it writes. It records the exact published build of every contract yours depends on, so every build checks against the same ones. It is optional: without it, Pacto looks dependencies up fresh each time. See Lockfile.

    Declare your API first¶

    pacto diff sees API changes only in the interfaces the contract declares. If pacto init did not find your OpenAPI document, add it to pacto.yaml yourself, with the path from the repository root:

    interfaces:
  - name: rest-api
    type: openapi
    ref: api/openapi.yaml
    visibility: public          # other teams may call it

    Other interface types and fields are in Contract sections.

    On every pull request¶

    The snippets below are steps of a GitHub Actions job, after actions/checkout. Install Pacto first; the token avoids GitHub's limit on anonymous API calls, which shared CI runners hit:

    - name: Install Pacto
  run: curl -fsSL https://raw.githubusercontent.com/TrianaLab/pacto/main/scripts/get-pacto.sh | bash
  env:
    GH_TOKEN: ${{ github.token }}

    Add two checks. The second reads your registry, so give the job a login. These variables work for any registry; on GitHub's, the built-in token will do:

    env:
  PACTO_REGISTRY_USERNAME: ${{ github.actor }}
  PACTO_REGISTRY_PASSWORD: ${{ secrets.GITHUB_TOKEN }}

    - name: Validate the contract
  run: pacto validate .

- name: Check for breaking changes
  run: pacto diff oci://ghcr.io/acme/contracts/my-service .

    pacto validate catches missing or malformed fields, fields that contradict each other and failed policies, the rules your platform team may set for every contract.

    pacto diff compares the contract in the pull request (the second argument) with the last one you published (the first). With no version after the name, it picks the highest published version. It exits 1 only when the change is BREAKING (POTENTIAL_BREAKING and NON_BREAKING pass), a breaking change, so the check fails. Your branch protection rules decide whether a failed check blocks the merge.

    Until the first version is published there is nothing to compare with and pacto diff fails, so add this step after your first pacto publish. To compare two folders with no registry, run pacto diff ./main ./feature-branch.

    On every pull request: who breaks¶

    pacto diff says whether a change is breaking. pacto impact says which consumers it breaks, from the consumer contracts it can see. Your repository holds only your contract, so name each consumer's published contract with --root, one per consumer, and keep that list current. The step needs jq, which GitHub-hosted runners include, and the same login variables:

    - name: Check who the change breaks
  run: |
    pacto impact oci://ghcr.io/acme/contracts/my-service . \
      --root oci://ghcr.io/acme/contracts/checkout \
      --root oci://ghcr.io/acme/contracts/reporting \
      --output-format json > impact.json || [ $? -eq 2 ]
    jq -r '.consumers[] | select(.compatibilityVerdict == "incompatible") | "\(.service) (owner \(.owner // "unknown")) accepts \(.compatibility)"' impact.json
    jq -e '.classification != "BREAKING" or all(.consumers[]; .compatibilityVerdict != "incompatible")' impact.json

    The first jq lists each consumer whose compatibility range rejects the new version, with its owner. The second fails the step when the change is BREAKING and at least one consumer is incompatible. A consumer whose range Pacto cannot evaluate, such as one with an invalid contract, reads unknown and does not fail the step.

    pacto impact ends in a release gate and exits on it: 0 clear, 1 blocked and 2 unverified. Contracts from --root carry no targets, so a BREAKING change with consumers exits 2, and GitHub Actions fails a step on any non-zero exit. || [ $? -eq 2 ] lets the step go on to the jq checks after a 2. A 1, for a blocked change or a command that could not run, still fails the step.

    To gate on what is deployed, keep the --root flags and add a source of targets: --k8s reads the Pacto resources in the current cluster and --evidence-url reads an Evidence Server. Exit 1 then fails the step when an incompatible consumer runs somewhere. --target-state reads targets from a fixture file, for demos and tests.

    After a merge: publish¶

    With the same login variables:

    - name: Set up a Docker builder
  run: docker buildx create --use --driver docker-container

- name: Publish a version
  run: |
    echo "$COSIGN_KEY" > cosign.key      # publish.sign reads it from the repository root
    pacto publish
  env:
    COSIGN_KEY: ${{ secrets.COSIGN_KEY }}
    COSIGN_PASSWORD: ${{ secrets.COSIGN_PASSWORD }}

    pacto publish builds the image, pushes it to your registry with your Kubernetes files and the contract, and signs them; delivery only rolls out versions published this way. Store the contents of cosign.key and its password as CI secrets. On GitHub, the job also needs permissions: packages: write to push.

    It never overwrites a published version, and a merge that does not raise service.version in pacto.yaml, such as a docs change, fails here. Raise the version with each change you want to ship, or run this step only when pacto.yaml changed. See Publish a version.

    If you use contracts without delivery, pacto push oci://ghcr.io/acme/contracts/my-service -p . uploads only the contract.

    A breaking change you need to ship¶

    Sometimes a breaking change is the right call. Give it a new major version (1.4.2 becomes 2.0.0): pacto publish refuses a breaking change with a smaller version. With delivery, the change then waits for the teams whose services it would break. Do not remove fields or change pactoVersion to get past the check.

    pacto diff still fails with the new major version, because the change is still breaking, so that pull request's check stays red. Merge it the way your repository lets a reviewer override a failed check, such as an admin bypass. Or make the diff step informational (continue-on-error: true on GitHub) and let pacto publish be the gate, since it refuses a breaking change without a new major version.

    GitHub Actions and other CI systems¶

    The GitHub Actions integration wraps these steps in a ready-made action that also installs Pacto and comments on the pull request. For GitLab CI, Jenkins or CircleCI, install Pacto with the installer script and run the same commands.
