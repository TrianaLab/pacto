    Contract sections¶

    The fields that name a service, say who owns it and list what it exposes: pactoVersion, service, interfaces, capabilities, metadata and extensions. Configuration and policy are in Configuration and policy; dependencies and state are in Dependencies and state; readiness is in Readiness.

    pactoVersion¶

    The contract specification version: "2.0" or "2.1". 2.1 adds publish, checks, external dependencies and the mcp interface type. Every 2.0 contract is also valid under 2.1. A 2.1 contract needs Pacto core 4.1.0 or later and operator 6.1.0 or later; see Versions.

    pactoVersion: "2.0"

    The version picks the JSON Schema the contract is validated against: pacto-v2.0.schema.json or pacto-v2.1.schema.json. Any other value is a hard error: the contract fails to load before validation runs and reports PARSE_ERROR (unsupported pactoVersion "3.0"; supported: 2.0, 2.1). See Validation layers.

    service¶

    Identifies the service.

    Field Type Required Constraints
    name string Yes Pattern: ^[a-z0-9]([a-z0-9-]*[a-z0-9])?$
    version string Yes Parses as semver (for example 2.1.0). See the note below
    owner OwnerInfo No Object only (string form removed)

    service carries identity only. The contract has no image or chart field: how you build and deploy a service is a delivery concern that lives outside the contract.

    version is parsed leniently, so write it strictly

    Pacto accepts any version that Masterminds/semver can parse. That parser fills in the parts you leave out and accepts a leading v, so 1, 0.1 and v0.1 all validate and all mean 0.1.0-style coerced versions. 1.2.3.4, abc, a capital V1.0.0 and anything with surrounding whitespace are rejected with INVALID_SEMVER.

    Later steps keep the coerced string as written, so that string is what gets published. pacto push tags the artifact with the literal string, and two contracts written 1 and 1.0.0 become two different tags of the same version. Write the full MAJOR.MINOR.PATCH and skip the v.

    OwnerInfo¶

    Structured ownership metadata. All fields are optional but at least one must be present. The field you set decides the canonical owner key that the graph groups by. See Ownership and the canonical owner key.

    Field Type Required Constraints
    team string No The team's bare name, such as billing: usually the team label on its workloads. pacto init and pacto_check flag a team/ prefix
    dri string No Directly Responsible Individual
    contacts OwnerContact[] No Contact points

    OwnerContact¶

    Field Type Required Constraints
    type string Yes One of: email, url, group, oncall, chat, other
    value string Yes Non-empty
    purpose string No One of: ownership, support, escalation, oncall, notifications

    Examples:

    # Structured form (the owner is always an object)
service:
  owner:
    team: foundations
    dri: eduardo.diaz
    contacts:
      - type: email
        value: foundations@acme.com
        purpose: ownership
      - type: chat
        value: "#foundations"

# Minimal object form (at least one field required)
service:
  owner:
    team: payments

    interfaces¶

    Declares the service's communication boundaries. Optional: a service with no network interfaces, such as a batch job or shared library, can omit this section. The ref field points at the spec you already publish: an OpenAPI document, an AsyncAPI document, a gRPC service descriptor or the MCP tools a service exposes. Pacto reads that spec in place.

    Field Type Required Constraints
    name string Yes Non-empty. Must be unique across interfaces
    type string Yes Enum: openapi, asyncapi, grpc, mcp (2.1)
    ref string Yes Non-empty. Path to the spec file within the bundle
    visibility string No Enum: public, internal. Default: internal

    Interface types¶

    Value Spec kind
    openapi OpenAPI document for HTTP/REST traffic
    asyncapi AsyncAPI document for event-driven communication
    grpc gRPC service descriptor
    mcp The tools a service such as an AI agent exposes, as an MCP tools/list result. See an agent is a service

    Note

    Interface names must be unique within a contract. Every interface requires a non-empty ref (SCHEMA_VIOLATION otherwise), and the referenced file must exist in the bundle (FILE_NOT_FOUND otherwise). A .json, .yaml or .yml ref must also parse (INVALID_INTERFACE_SPEC otherwise). For any other extension, such as a gRPC .proto, Pacto checks only that the file exists. Ports are a deployment concern, so interfaces have no port field. Declare health and metrics endpoints as capabilities.

    Interfaces at runtime¶

    The Kubernetes operator checks two fields of a running interface: type and visibility.

    • type. The operator sends a probe to the port and looks at the protocol that answers. openapi accepts HTTP/1 or HTTP/2 and grpc accepts HTTP/2. Anything else is INTERFACE_PROTOCOL_MISMATCH. A TLS port, no answer and asyncapi stay unverified.
    • visibility (internal when omitted). It is contradicted only when the operator sees an address outside private networks: a public externalIPs entry, or a LoadBalancer Service (without an internal load balancer annotation) or an Ingress whose status carries a public IP or hostname. That is INTERFACE_VISIBILITY_MISMATCH. A NodePort Service, an internal or address-less load balancer and an HTTPRoute leave exposure unknown, so the field stays unverified. A public interface seen only in-cluster also stays unverified, because a gateway the operator cannot see may expose it.

    A field the operator cannot check leaves the contract status unchanged. See Runtime conformance.

    capabilities¶

    Optional. Declares standard observability capabilities (health, metrics) or custom extension capabilities. Use this section to tell the platform that a service exposes health and metrics endpoints.

    Field Type Required Constraints
    type string Yes Enum: health, metrics, extension
    ref string Conditional Required for extension only. A namespaced identifier (e.g. example.com/custom). Not allowed for health/metrics
    binding Binding No Standard types only (health/metrics). Binds the endpoint to a declared interface. Not allowed for extension

    Capability binding¶

    Binds a standard capability endpoint (health/metrics) to a declared interface so a collector can probe it. binding.type is a closed set and http is the only supported transport in this release. Any other transport fails structural validation.

    A binding resolves as follows:

    • binding.type: http means the capability is probed over HTTP.
    • binding.interface names the declared interface that provides the address and port for the probe. It is the platform-neutral counterpart of the Kubernetes CR's spec.target.interfaceBindings[].interface, which resolves to a concrete Kubernetes Service port. The capability path is independent of that interface's OpenAPI, AsyncAPI or gRPC specification.
    • binding.path is relative to the resolved endpoint.
    Field Type Required Constraints
    type string Yes Enum: http (only supported transport; any other value fails validation)
    interface string Yes Must match a declared interfaces[].name: the interface whose platform binding provides the address and port (CAPABILITY_INTERFACE_UNKNOWN otherwise)
    path string No Application path relative to the resolved endpoint. Must start with a single / and carry no scheme/host/fragment (CAPABILITY_PATH_INVALID otherwise) 
    capabilities:
  - type: health
    binding:
      type: http
      interface: rest-api
      path: /health
  - type: metrics
    binding:
      type: http
      interface: rest-api
      path: /metrics
  - type: extension
    ref: example.com/tracing

    You can declare a health or metrics capability with no binding. Another collector can verify that declaration. The Kubernetes integration reports an unbound capability as Unsupported/Unknown because it has no endpoint to probe. An extension capability requires a namespaced ref and cannot declare a binding. Pacto has no evaluator for extensions, so it lists each one in coverage.unverified as capabilities[ref=<ref>] and excludes it from required assertions. A contract that declares one can still reach Compliant, and that verdict covers none of its extensions.

    metadata¶

    Optional. Free-form key-value pairs for organizational use. Pacto validates only the type.

    metadata:
  team: payments
  tier: critical
  on-call: "#payments-oncall"

    The schema sets additionalProperties: false at every level except inside metadata, so an unknown field fails validation.

    Tip

    metadata is a deliberate extension point for tooling. Platform teams use it to attach signals that their CI or deployment systems read from a contract. For example, infrastructure contracts can carry metadata.labels like platform/provisioner: crossplane to drive provisioning generically. See Infrastructure contracts.

    extensions¶

    Optional. A free-form object for forward-compatible, namespaced extension data outside the core contract model. Use metadata for organizational key-value pairs and extensions for structured data that future Pacto features or third-party tools interpret. Namespace each key, for example with a domain, to avoid collisions. In this release Pacto validates only the type.

    extensions:
  example.com/custom-tool:
    enabled: true
