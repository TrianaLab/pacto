    Guided tour¶

    This tour answers six questions people ask about services they did not build. Each answer uses one or two pacto commands on a fixed set of example contracts and explains the output. The tour covers contracts and the checks on them. Delivery has its own demos.

    Before you start¶

    Everything here runs offline except pacto dashboard. The fixture is committed to the repository, so you need no cluster, registry, running service or network.

    You need the Pacto CLI on your PATH and a clone:

    git clone https://github.com/TrianaLab/pacto.git && cd pacto

    Every command below is written to be pasted from the repository root.

    To drive a real stack, see the Docker Compose demo. It needs neither a clone nor the CLI.

    The tour shows runtime conformance (checking what a service really does on the network) as a recorded finding only: story 2 shows one the kernel saw. To watch it live, use the Compose demo or the node agent on a Kubernetes cluster.

    The fleet¶

    Sixteen services are in the snapshot. Five carry the stories:

    Service Owner Its part
    payments-service payments-team six revisions; the change stories 3 and 4 analyse
    orders-service commerce-team declares a dependency on payments, and is observed calling it
    api-gateway platform-foundations declares the same dependency, and has an expired readiness assessment
    auth-service identity-team deployed and never observed: the Unknown target
    audit-log platform-foundations-security calls payments and declares nothing: the shadow consumer

    A target is one running deployment of a service. A readiness assessment is a dated list of claims in a contract, and a shadow consumer is a service seen calling another that no contract declares; the glossary has these and the other words the tour uses.

    A contract says what a service exposes, what it needs and how it behaves. How the service is deployed stays in its own files. The contract reference has every section.

    Target: production-eu/kubernetes-workload/commerce%2Forders-service

  finding [error] STATELESS_PERSISTENT_CONFLICT: declared stateless but the observed workload mounts a persistent volume
  finding [error] INTERFACE_ABSENT: nothing listens on the declared http interface (seen by k8s-observer+ebpf)

    Coverage: 5/5 evaluated marks the difference from the Unknown above: every check ran, so the verdict is a conclusion. Each finding names one exact contradiction. The contract declares the workload stateless and the observation found a persistent volume mounted. The contract declares an http interface and nothing listens on its port: seen by k8s-observer+ebpf says the node agent saw that in the kernel, and Kubernetes agreed. Each finding is one fact that disagrees with one declaration.

    Story 4: Find who a breaking change affects¶

    Turn a classification into a list of consumers, each graded by how it is known.

    pacto impact examples/demo/bundles/payments-service/v1.2.1 examples/demo/bundles/payments-service/v2.0.1 --local examples/demo/bundles

    Impact: payments-service 1.2.1 -> 2.0.1
Classification: BREAKING
Breaking changes: 10
Potentially breaking changes: 15
Affected consumers (4):
  api-gateway                  direct     confidence=contractual  compat=incompatible owner=platform-foundations
  frontend                     transitive confidence=inferred     compat=unknown      owner=frontend-team
  orders-service               direct     confidence=contractual  compat=incompatible owner=commerce-team
  pacto-demo                   transitive confidence=inferred     compat=unknown      owner=platform-foundations
Release gate: unverified
unverified: the change is BREAKING and 4 consumers depend on payments-service, but none is shown to be both incompatible and running. Review each consumer, and add a source that knows where services run (for example --target-state) to tell deployed impact apart

    Four consumers. confidence=contractual means the consumer declared this dependency in its own contract; confidence=inferred means it was reached transitively. compat=incompatible is a second judgement: 2.0.1 falls outside the consumer's declared version range. The release gate is unverified and the command exits 2. The bundles say nothing about where anything runs, so Pacto cannot show a consumer is hit and does not call the change safe either.

    Contracts find only the consumers that declare the dependency. Add observed traffic:

    pacto impact examples/demo/bundles/payments-service/v1.2.1 examples/demo/bundles/payments-service/v2.0.1 --local examples/demo/bundles --traces examples/demo/traces.json

    Impact: payments-service 1.2.1 -> 2.0.1

Potentially breaking changes: 15

  api-gateway                  direct     confidence=contractual  compat=incompatible owner=platform-foundations
  audit-log                    direct     confidence=observed     compat=unknown      owner=platform-foundations-security
  frontend                     transitive confidence=inferred     compat=unknown      owner=frontend-team
  orders-service               direct     confidence=corroborated compat=incompatible owner=commerce-team
  pacto-demo                   transitive confidence=inferred     compat=unknown      owner=platform-foundations
Release gate: unverified
unverified: the change is BREAKING and 5 consumers depend on payments-service, but none is shown to be both incompatible and running. Review each consumer, and add a source that knows where services run (for example --target-state) to tell deployed impact apart

    Five now. audit-log calls payments-service in production and declares nothing, so only observed traffic finds it. It arrives as confidence=observed. orders-service, which both declared the dependency and was seen using it, is upgraded to confidence=corroborated.

    Then ask where the change actually lands:

    pacto impact examples/demo/bundles/payments-service/v1.2.1 examples/demo/bundles/payments-service/v2.0.1 --local examples/demo/bundles --traces examples/demo/traces.json --target-state examples/demo/fleet-targets.yaml

    Story 6: Give an agent read-only tools¶

    Serve a contract as MCP tools, and check what the default withholds.

    pacto mcp turns a bundle's OpenAPI interface into MCP tools. By default it turns only the read-only operations into tools. Point a human and an agent at one process:

    pacto dashboard examples/demo/bundles --port 8899
pacto mcp examples/demo/pacto-dashboard --base-url http://127.0.0.1:8899

    Then open http://127.0.0.1:8899/#/fleet, and connect your MCP client to the second command. The dashboard is itself a Pacto bundle with a real OpenAPI contract, so the agent's tools are generated from the contract of the very server the human is looking at. The tools come from the dashboard's OpenAPI interface, one per read-only operation. Beside the interface operations, the server always registers Pacto's own authoring tools: pacto_create and pacto_edit write contract files to disk.

    Every bundle withholds mutating operations by default. Serve the demo's payments service, and Pacto drops its five mutating operations, every POST, PUT, PATCH and DELETE that bundle's interface declares, with a warning on stderr:

    pacto mcp examples/demo/bundles/payments-service/v2.1.0 --base-url http://127.0.0.1:1

    The base URL is a dead address on purpose: Pacto registers and lists the tools and calls none of them.

    Add --allow-writes and both the warning and the restriction disappear. --allow-writes governs the interface tools only. To withhold the authoring tools, register this server only where you want contracts written. See MCP integration for the full wiring.
