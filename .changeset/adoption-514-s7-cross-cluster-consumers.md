Consumers and delivery state across every cluster of a hub. An impact answer over more than one cluster carries `clusters` (each with its status and the new `asOf`), each consumer's `clusters` (ids into that list) and `unreadClusters`: once a person approved or removed a member, the clusters that publish to the hub's targets repository and are not members are counted, never named, with a `CLUSTERS_UNREAD` limitation, and a `BREAKING` change stays `unverified` with the new gate code `CLUSTERS_UNREAD`. A consumer with a target in a stale or unreachable cluster turns a `compatible` verdict into `unknown`, with a note naming the cluster and its age; an `incompatible` verdict stays. `pacto impact` prints a `Clusters read:` line and a `clusters:` line under each consumer, and Change analysis names each target in the Runs on cell with its cluster. Single-cluster answers are unchanged.

A promote planned on a hub reads every approved member's signed snapshot beside the hub's own Pactos, through one join reader the CLI, dashboard and promoter share, so a consumer in another cluster that does not accept the change asks its owners, and a member that went stale, a join list Pacto could not read or a cluster that is not a member yet asks a person to accept the unknown for a change that is not plainly non-breaking. `pacto delivery` gains `--detected` to read the hub's members. The promoter derives the targets repository from `--registry`. A member's promoter runs with the new `--member` flag, which the chart passes whenever `hub.url` is set: it reads no joins and asks a person here for any change that is not plainly non-breaking, since consumers in other clusters are read on the hub.

The dashboard's inbox, Environments and History, and the MCP tools that answer them, read delivery from every kubeconfig context the dashboard reads, each read reviewed for the person per cluster, namespace and object. Rows carry `cluster`, `listing.clusters` gives per-cluster completeness and `listing.hiddenClusters` counts the clusters the reader may not see. Rows of another cluster are read-only: acting on one is refused with `RemoteClusterReadOnly` and the command that acts there. The history, blame, undo, record, operation and progress routes and the MCP tools `pacto_delivery_history`, `pacto_delivery_blame` and `pacto_delivery_undo_plan` take `cluster`. No contract field, `pactoVersion` or CRD changes.
