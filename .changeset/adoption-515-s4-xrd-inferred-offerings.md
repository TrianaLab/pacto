A platform with Crossplane never hand-writes an offering contract an XRD already describes. The operator reads each XRD and the Compositions that select it, read-only, and pushes it once a minute as an inferred offering, signed with the installation key, to its own `<registry>/pacto-inferred/crossplane-<clusterID>/services`: the XRD's spec schema as the `provisioning` configuration with its bounds and enums kept and every object closed, and the Composition names as the `class` enum. It is on by default with a registry on a cluster-wide operator; turn it off with `crossplane.offerings.enabled=false` (`--crossplane-offerings=false`). The format is public: a contribution whose `pacto.yaml` also declares `service.offering`, `service.summary` and `configurations`, so any tool may push one. `pacto fleet offerings` lists the declared offerings with a drift line when an accepted offering's source changed, and `--inferred` (`pacto_fleet_entities` and the dashboard with `declaration: inferred` and kind `offering`) lists the inferred ones, muted, with their source object, producer and classes. An inferred offering never counts as declared, never satisfies a range, never clears a gate and is never consumable. A person accepts one with `pacto declare offering:<name> --from <ref> --detected <detection> --version <version> --owner <team>`, plan first, signed by their Sigstore login, with a declaration naming `inferredFrom: offering:<producer>/<service>@<digest>`, which `pacto validate` refuses with `DECLARATION_OFFERING_MISMATCH` when it names an offering `service.offering` does not; `pacto_declare` writes a draft and the dashboard's offering page offers **Accept this offering**. An open parameter schema is refused with `OfferingSchemaOpen` naming each open path. When both revisions declare `service.offering`, `pacto diff` grades the configuration schema as consumer input. No `pactoVersion` or contract field changes. See [Inferred offerings](https://pacto.run/latest/inferred-offerings/).
