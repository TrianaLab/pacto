    CLI Reference¶

    Every command accepts -v / --verbose for debug-level logging and --help for detailed usage. --output-format is a global flag taking text (the default), json or markdown.

    What --output-format guarantees

    Read this before you parse Pacto's output in a script.

    • json describes a successful result. When a command fails to produce its result, for example because a reference is unreachable or pacto.lock is missing, the error goes to stderr as plain text and stdout stays empty, whatever --output-format says. A negative verdict is still a result: pacto validate on an invalid contract and pacto diff on a breaking change both print their whole JSON document to stdout and exit 1. An empty stdout tells you there is nothing to parse. Read stdout when it is non-empty, and read the exit code for the verdict.
    • Only pacto diff implements markdown, for posting a diff as a CI comment. Every other command renders text.
    • Keys are camelCase in every command ("path", "valid", "errors", "upToDate"). Before v4, init, validate, pack, pull and push emitted capitalised keys ("Path", "Valid").
    • An unrecognised value is rejected. --output-format yaml exits 1 with unsupported output format "yaml" before the command runs.

    The interactive and side-effecting commands (login, logout, update, mcp, dashboard) inherit the flag from the root command and always emit text.

  -h, --help[=true|false]       help for pacto
      --no-anim[=true|false]    disable animations

  -v, --verbose[=true|false]    enable verbose output

    Exit codes¶

    Pacto exits 0, 1 or 2, apart from pacto run (below). 0 means the command produced its result and the result was acceptable. 1 means the check failed or the command could not run, so the exit status alone cannot distinguish "the check failed" from "the command could not run". 2 means pacto impact could not show that a change or an event is safe, and no other command exits 2 for its own result. pacto run exits with the exit code of the command it wraps, whatever it is, or 1 when that command exits 0 and the final verdict fails --fail-on. Recording a run record (--stats-registry, --stats-file) never changes an exit code. pacto stats publish exits 1 when a file could not be published.

    Exits 1 Exits 0
    pacto diff where the overall classification is BREAKING a POTENTIAL_BREAKING or NON_BREAKING diff
    pacto validate reporting at least one error validation that reported only warnings
    pacto lock --check on a stale lockfile, or with none at all (LOCK_MISSING) a lockfile that is up to date
    pacto impact where the gate is blocked: a BREAKING change reaches a consumer that does not accept the new version and runs on a known target, or a policy referrer that fails the new policy does pacto impact where the gate is clear: the change is not BREAKING and every policy referrer was checked and passes the new policy, or the snapshot is complete and no service depends on the changed one; an event (--unavailable, --removed or --regressed) when the complete snapshot shows nothing depends on the service
    pacto stats publish when a file could not be read, parsed or published pacto stats publish that published every file
    any command that could not run, for example on an unresolvable reference, an unreadable bundle or an unknown flag
    Exits 2
    pacto impact where the gate is unverified: a BREAKING change that nothing is shown to block, on a partial answer or with consumers none of which is shown to be safe; or a change of any classification with a policy referrer that fails the new policy and runs nowhere known, could not be checked or could not be resolved
    pacto impact --unavailable, --removed or --regressed when anything depends on the service or the answer is partial. An event never exits 1 for its result

    Two cases affect CI gates:

    • A pacto diff against a missing reference exits 1, the same as a breaking change.
    • pacto impact exits 1 only when the change is breaking and a source that knows where services run shows an incompatible consumer on a target. Sources that know no targets, such as --local alone, cannot show that, so a breaking change with consumers exits 2. A job that gates on deployed impact alone can treat 2 as a pass; any other job fails on it.

    Use stdout to tell a verdict from a failure. A command that produced a verdict writes it to stdout and puts a one-line summary on stderr. A command that could not run leaves stdout empty:

    Invocation Exit stdout stderr
    pacto diff --output-format json OLD NEW (breaking) 1 the full JSON result breaking changes detected
    pacto diff --output-format json oci://…/absent:1.0.0 NEW 1 empty old contract: artifact not found: …

    In a script, branch on stdout when it is non-empty, and treat an empty stdout with exit 1 as a tool failure.

    OCI version resolution¶

    All commands that accept oci:// references support automatic version resolution. When a reference omits the tag (for example oci://ghcr.io/acme/svc-pacto with no :1.0.0), pacto queries the registry for available tags and selects the highest semver version.

    For dependency references declared with a compatibility constraint, only tags satisfying the constraint are considered. For example, a dependency with compatibility: "^2.0.0" and available tags 1.0.0, 2.0.0, 2.3.0, 3.0.0 resolves to 2.3.0.

    Resolution ignores non-semver tags such as latest and main. Digest-pinned references (@sha256:...) and explicitly tagged references are used as-is.

    Constraints apply to the CLI's dependency graph

    The CLI applies compatibility constraints when it resolves a contract's declared dependencies, for example in pacto graph. The dashboard's version discovery selects the highest semver tag and ignores per-dependency compatibility constraints. Root-contract pulls (a tagless top-level oci:// ref) also select the highest semver tag with no constraint.

    pacto agent¶

    Runs until interrupted. Watches TCP listeners and outbound connection outcomes with an eBPF program, attributes each socket to the workload that created it (a Kubernetes pod, a container, a systemd unit or a pacto run session, from its cgroup, or from its network namespace when the cgroup names none) and publishes a snapshot every --publish-interval. --sink kubernetes writes the node's NodeRuntimeObservation status (pods only; what the Pacto operator's node agent DaemonSet runs); --sink stdout prints one JSON snapshot per line.

    --sink local and --sink evidence check workloads against their contracts on this host. The workloads come from --bindings (a YAML list of {match: {unit|container|cgroup|session|pid}, contract, host, interfaces: {name: port}, dependencies: {name: host:port}}) and with --docker from running containers labelled dev.pacto.contract=, dev.pacto.bind.<interface>=<port> and dev.pacto.dep.<dependency>=. Interfaces and dependencies are judged from the kernel's view, health and metrics capabilities by probing the bound port; a negative is reported once it persists for --stabilization-window. --sink local prints every target's compliance and findings each interval in --output-format; --sink evidence signs each target's evidence and sends it to an Evidence Server, which needs contracts pinned as oci://...@sha256:<digest>. Envelope sequences start at the wall clock in nanoseconds and count up, so they keep increasing across restarts as long as the clock does.

    Needs Linux 5.11 or later with BTF, or 5.8 or later with BTF and root or CAP_SYS_RESOURCE; root (or BPF, PERFMON and SYS_PTRACE); and the host's /proc and cgroupfs.

    pacto agent [flags]

    Examples:

      pacto agent --sink stdout --publish-interval 5s
  pacto agent --sink kubernetes --cgroup-root /host/sys/fs/cgroup
  pacto agent --sink local --docker --cgroup-root /host/sys/fs/cgroup
  pacto agent --sink evidence --bindings bindings.yaml --evidence-url https://evidence.example.com \
    --evidence-key agent.key --evidence-key-id k1 --evidence-producer host-1

    Flags:

          --bindings string                   with --sink local or evidence: YAML file binding workloads to contracts
      --cgroup-root string                where the host cgroup v2 hierarchy is mounted; empty attributes by network namespace only (default "/sys/fs/cgroup")
      --docker[=true|false]               with --sink local or evidence: check running containers labelled dev.pacto.contract (Docker Engine API on /var/run/docker.sock)
      --docker-label-filter stringArray   with --docker: only check containers that also carry this label (key=value or key; repeatable, all must match), e.g. com.docker.compose.project=demo
      --enable-probing[=true|false]       also probe the wire protocol of every interface found listening
      --evidence-key string               with --sink evidence: private key file envelopes are signed with
      --evidence-key-id string            with --sink evidence: key id (must match the server's trust entry)
      --evidence-producer string          with --sink evidence: producer id
      --evidence-url string               with --sink evidence: Evidence Server base URL
  -h, --help[=true|false]                 help for agent
      --namespace string                  namespace the NodeRuntimeObservation is written to with --sink kubernetes (default $POD_NAMESPACE)
      --node-name string                  name of this host; with --sink kubernetes also the NodeRuntimeObservation name (default $NODE_NAME)
      --proc-root string                  where the host /proc is mounted (a pod needs hostPID, a container --pid=host) (default "/proc")
      --publish-interval duration         how often a snapshot is published (whole seconds) (default 30s)
      --resync-interval duration          how often workloads, network namespaces and listeners are re-read from /proc (default 1m0s)
      --ringbuf-size uint32               kernel ring buffer size in bytes; a power of two and a multiple of the page size (default 262144)
      --sink string                       where snapshots go: one of [kubernetes stdout local evidence] (default "stdout")
      --stabilization-window duration     how long a negative must persist before it is reported (default 2m0s)

    pacto dashboard¶

    Launches an operational dashboard over the fleet snapshot: the same operational graph the CLI's pacto fleet commands query, served as a web UI.

    The dashboard is the exploration and observability layer of the Pacto system. It visualizes the same contracts the CLI manages and the operator verifies, organised around four workflows: an operational Overview, the Services inventory, the Operational Graph and Change analysis.

    Each positional argument is a contract source reference: - oci://registry/repo → OCI registry source (can be repeated) - ./path/to/dir → local filesystem source (at most one)

    When no arguments are given, sources are auto-detected: - local: enabled if pacto.yaml is found in the working directory - cache: enabled if the OCI bundle cache (~/.cache/pacto/oci) holds bundles - k8s: enabled if a kubeconfig or in-cluster config resolves - oci: from the positional arguments, the PACTO_DASHBOARD_REPO env var, or the status.contract.resolvedRef of the cluster's Pacto resources

    When running alongside the Kubernetes operator, OCI repositories are automatically discovered from the status.contract.resolvedRef fields of Pacto CRD resources on every refresh. The result combines runtime state from the operator with contract content from OCI.

    Every source contributes to one snapshot, rebuilt in the background, and each answer carries the as-of time and the completeness of the sources behind it.

    pacto dashboard [sources...] [flags]

    Examples:

      # Start dashboard with auto-detected sources
  pacto dashboard

  # Start from a specific directory
  pacto dashboard ./services

  # Include OCI repositories
  pacto dashboard oci://ghcr.io/org/order-service oci://ghcr.io/org/payment-service

  # Mix local and OCI sources
  pacto dashboard ./services oci://ghcr.io/org/payment-service

  # Custom port
  pacto dashboard --port 9090

  # Specify Kubernetes namespace (default: all namespaces)
  pacto dashboard --namespace production

    Flags:

          --allow-anonymous[=true|false]      serve beyond loopback without sign-in: everyone who reaches the address reads the whole fleet (also PACTO_DASHBOARD_ALLOW_ANONYMOUS)
      --cors-origin string                explicit cross-origin allowed to call the API (default: same-origin only)
      --delivery-namespace string         namespace Pacto delivery runs in, whose published identity policy (agent, break-glass and human groups, team prefix) says who is an agent and who may answer (default "pacto-delivery")
      --delivery-trust string             the trust config delivery records are verified with, so History reads signed records (the recorder's PEM public key or a YAML trust config; default $PACTO_DELIVERY_TRUST)
  -h, --help[=true|false]                 help for dashboard
      --host string                       bind address for the dashboard server (default "127.0.0.1")
      --mira-source stringArray           base URL of a Mira node whose service map supplies observed calls between services (repeatable; also PACTO_DASHBOARD_MIRA_SOURCES)
      --mira-url string                   Mira's address, to link health-check citations and open a service in Mira
      --namespace string                  Kubernetes namespace (empty = all namespaces)
      --oidc-ca-file string               PEM bundle of the CAs that sign the issuer's certificate, trusted on top of the system roots (also PACTO_DASHBOARD_OIDC_CA_FILE)
      --oidc-client-id string             OpenID Connect client id of the dashboard
      --oidc-display-name string          the identity provider's name on the sign-in button, as in Sign in with Keycloak (default OIDC; also PACTO_DASHBOARD_OIDC_DISPLAY_NAME)
      --oidc-extra-scopes strings         scopes to ask for beyond openid, profile and groups
      --oidc-groups-claim string          ID token claim the API server takes the groups from; must match its claim mapping (default groups)
      --oidc-groups-prefix string         prefix the API server puts before every group; must match its claim mapping
      --oidc-internal-issuer-url string   address the dashboard reaches the issuer at when it differs from the public issuer URL browsers use, such as an in-cluster Service; ID tokens must still name the public issuer (also PACTO_DASHBOARD_OIDC_INTERNAL_ISSUER_URL)
      --oidc-issuer-url string            OpenID Connect issuer people sign in with before the dashboard shows anything; every view then shows what the signed-in person's Kubernetes RBAC lets them read, and every action runs as them (also PACTO_DASHBOARD_OIDC_ISSUER_URL; the client secret comes from PACTO_DASHBOARD_OIDC_CLIENT_SECRET)

      --oidc-username-claim string        ID token claim the API server takes the username from; must match its claim mapping (default sub)
      --oidc-username-prefix string       prefix the API server puts before the username; must match its claim mapping (default the issuer URL and #, none for the email claim; - for none)
      --port int                          port for the dashboard server (default 3000)
      --session-idle-timeout duration     a session without a request for this long ends (default 1h)

      --trace-source stringArray          named offline OTLP/JSON trace source as NAME=PATH, where NAME is its stable data-source identity (repeatable; also PACTO_DASHBOARD_TRACE_SOURCES)
      --traces stringArray                OTLP/JSON trace file to fold observed dependencies from (repeatable; also PACTO_DASHBOARD_TRACES)

    It auto-detects sources: pass OCI repositories as arguments, or run it next to the operator (with a kubeconfig) and it discovers OCI repositories from each Pacto resource's status.contract.resolvedRef. Use --no-cache for a cold start (it skips scanning pre-existing cached bundles; bundles fetched during the session are still cached).

    For a tour of what the dashboard surfaces, see For platform engineers; to run it as a container, see Dashboard container.

    pacto delivery¶

    Pacto delivery decides which version each environment (a Stage) runs. Every change is an Operation: plan it to see what the promoter will do and who must agree, propose it, and a person approves only when the contracts say a consumer would break, Pacto cannot see enough or the Stage asks for approval on every promote.

    There is no approve tool for agents. approve is for people.

    pacto delivery [flags]

    Flags:

          --delivery-namespace string   namespace Pacto delivery runs in, whose published identity policy (agent, break-glass and human groups, team prefix) says who is an agent and who may answer (default "pacto-delivery")
  -h, --help[=true|false]           help for delivery
  -n, --namespace string            namespace of the Stage and its Operations (default "default")
      --trust string                the trust config delivery records are verified with: the recorder's PEM public key, or a YAML file of keys and the streams each may sign (default $PACTO_DELIVERY_TRUST)

    pacto delivery approve¶

    Record your decision on a held operation, as the person your kubeconfig signs you in as. When the promoter asks for a fresh login (delivery.promoter.authFreshness), the command instead makes you log in again in your browser (prompt=login, max_age=0) with its own OpenID Connect client and sends the Approval with that login's token, never your kubeconfig's: an agent running in your shell cannot approve as you without you typing your password at that moment. The token is not stored.

    pacto delivery approve <operation> [flags]

    Flags:

          --decision string             approve, reject or accept-unknown (default "approve")
  -h, --help[=true|false]           help for approve
      --note string                 why, for the record
      --oidc-ca-file string         PEM bundle of the CAs that sign the issuer's certificate, trusted on top of the system roots (also PACTO_DELIVERY_OIDC_CA_FILE)
      --oidc-client-id string       OpenID Connect client used only for approvals, never by a kubeconfig (a confidential client's secret comes from PACTO_DELIVERY_OIDC_CLIENT_SECRET) (default "pacto-approve")
      --oidc-extra-scopes strings   scopes to ask for beyond openid, profile and groups
      --oidc-issuer-url string      OpenID Connect issuer the cluster trusts, to log in again with (also PACTO_DELIVERY_OIDC_ISSUER_URL)
      --oidc-redirect-port int      loopback port the identity provider sends the browser back to (default: a free port)

    pacto delivery autonomy¶

    How many of the services Pacto has seen have a contract, how many promotions in each Stage's window no person asked for or approved, each Stage's level with the next level Pacto proposes and its newest would-have decision, and the blockers with a fix to copy. It only reads: a level moves through a proposed and approved operation.

    It runs the dashboard's own autonomy view with your kubeconfig identity, so the apiserver decides what you see. Without -n it reads the namespaces you may list Stages in and leaves out, without naming them, those outside your permissions; a namespace that refuses the list makes the answer partial and is named in unreadable. The answer is the dashboard's JSON in every output format.

    pacto delivery autonomy [flags]

    Flags:

          --blockers int        Where the page of blockers starts; limit and q apply to it too
      --domain string       With service: the service's registry domain, empty for the default. A Stage that names another domain is left out; one that names none matches any
  -h, --help[=true|false]   help for autonomy
      --level string        Keep only the Stages at this level; none keeps those that report no level the ladder knows. It narrows the Stages, never byLevel or the blockers (observe, advise, auto-nonbreaking, autonomous, none)
      --limit int           How many per page; 0 means the list's default
      --offset int          Where the page starts. Past the end answers the last page
      --q string            Keep only what contains this text, ignoring case
      --service string      Keep only the Stages of the service with exactly this name; it narrows byLevel too, never the blockers or promotionsWithoutPerson

    pacto impact¶

    Composes a semantic contract diff (old→new) with the operational graph to answer which consumers a change really affects, how strong the evidence is and whether their declared compatibility still holds.

    When no fleet source holds the changed service, the new revision is added to the snapshot so the services that depend on it are found.

    With --unavailable, --removed or --regressed, impact answers what happens if that service becomes unavailable, is removed or a revision of it regressed. --unavailable and --removed also take offering:<name>, which asks the same of every service that provides the platform offering. Consumers are graded breaks (every edge on their path is required), may degrade (an optional edge) or unknown. The gate is unverified (exit 2) when anything depends on the service and clear (exit 0) only when the complete snapshot shows nothing does. --regressed with an artifact digest reads delivery's recorded failures with your own cluster credentials when a cluster is reachable.

    The answer ends in a release gate, and the exit status follows it: 0 clear: the change is not BREAKING and every service that references its policy passes the new policy, or the snapshot is complete and no service depends on the changed one. 1 blocked: a consumer that runs on a known target does not accept the new version of a BREAKING change, or its contract fails the changed service's new policy, whatever the classification. 2 unverified: nothing is shown to block the change, but the answer cannot clear it: a BREAKING change whose answer is partial or whose consumers none is shown to be safe, or a service that references the changed policy and fails it running nowhere known, could not be checked or could not be resolved. A run over --local bundles alone knows no targets, so a BREAKING change with consumers exits 2. A command that could not run also exits 1, with nothing on stdout. Add --target-state (or a live source) so the gate can tell deployed impact apart.

    Pacto finds consumers only in the sources you pass, such as --local, --root, --oci, --cache, --k8s, --evidence-url and --traces. With --local alone Pacto sees only the contracts in those folders, so "No affected consumers" is not evidence of safety.

    Examples:

      # Impact of upgrading a local service against the local fleet
  pacto impact ./svc-v1 ./svc-v2 --local .

  # Include observed (runtime) evidence and emit JSON

  # What breaks if redis becomes unavailable, or postgresql is removed

    pacto init¶

    Writes the contract for the service in dir (default: the current folder).

    An empty or new folder gets a blank contract with the bundle structure (interfaces/, configuration/) and the owner and domain you pass; with no --owner the owner is a commented placeholder that Unknown names. A folder that already holds a service gets a contract read from its Dockerfile and Kubernetes manifests, and a list of what Pacto found and what it could not tell (Unknown). The workload's environment, including the ConfigMaps it reads, becomes a configuration schema with each value as its default. A URL in it that names another service in the cluster becomes a dependency: with that service's contract in --fleet, its bundle and a range from its version; without it, a placeholder range that the comment above it and Unknown name. A readiness, liveness or startup probe becomes a health check.

    Either contract also gets a publish section, for pacto publish, with its bundle under --registry (default: the workload's image registry, else the registry.example placeholder). To describe the service and leave delivery out, pass --describe-only: the contract then has no publish section and needs no signing key. --delivery also writes the cluster pieces: the Pacto resource that checks the running service, and per environment a Stage with the Flux OCIRepository and Kustomization it applies through. Each Stage starts at observe: it plans every new version and moves nothing, and the OCIRepository stays pinned to the tag you deploy, so GitOps keeps applying what it did. The last environment's Stage also asks a person to approve every promote.

    --owner is the team's bare name, such as billing: usually the team label on the workload. --domain is the business domain, such as payments. An AI agent is a service too: its tools are an mcp interface, the model it calls is a dependency and its eval suite is a checks entry; see https://pacto.run/latest/contract-reference/checks/#an-agent-is-a-service.

    Several folders are each pactified, with a summary at the end. --cluster drafts a contract for every workload in the namespaces that no Pacto describes yet, in <out>/<namespace>/<name>: its manifests are read from the cluster, and the services its pods were seen calling become dependencies pinned to the version seen running, for you to widen. Drafts are only written, never published, and a draft that is not valid fails the command.

    With --from the service is created from a golden path: an oci:// reference or a directory whose contract declares service.template. The path's contract is copied with its identity reset: the name, version 0.1.0, --owner (required) and --domain, with --values and --set applied over any field and service.origin recording the path it came from. A path read from a registry is pulled by digest; when the trust config (--trust, else $PACTO_DELIVERY_TRUST) names a template key, the path must be signed by one or nothing is created, and otherwise the signature is reported Unknown. The created contract is validated with its references resolved before anything is written, and the Status block says what was checked and what Pacto cannot tell yet. Each plugin the path names is listed with the binary it resolves to; only the ones you name with --run-plugins run, never with --plan, and the files they return are added like the path's own. --delivery plans the cluster pieces from the created contract when the path publishes manifests under publish.deploy; otherwise the delivery step says why none were planned.

    It only adds files and missing .pactoignore lines; any other file already there is yours and is left as it is, so running it twice is safe. --plan shows exactly what would be added and changes nothing.

    pacto init [dir...] [flags]

    Examples:

      pacto init my-service
  pacto init my-service --owner billing --domain payments --registry ghcr.io/acme
  pacto init --plan
  pacto init --describe-only --owner billing
  pacto init --delivery --owner payments --fleet ../contracts
  pacto init --delivery --no-transparency-log --insecure-registry
  pacto init --delivery --registry-secret registry-creds
  pacto init services/checkout services/payments --plan
  pacto init --cluster --namespace shop --out drafts
  pacto init gift-cards --from oci://ghcr.io/acme/paths/http-service:1.0.0 --owner checkout --domain commerce

    Flags:

          --cluster[=true|false]               draft a contract for every workload in the cluster that no Pacto describes, reading the current kubeconfig context
      --delivery[=true|false]              also declares each --env in pacto.yaml with an empty values file, and writes the cluster pieces: the Pacto resource, a Stage per environment and its Flux OCIRepository and Kustomization
      --describe-only[=true|false]         write a contract that only describes the service: no publish section, so no signing key
      --domain string                      business domain, such as payments
      --env strings                        environments for --delivery: declared in the contract and given a Stage each, in promotion order (default [test,prod])
      --fleet strings                      folders of other services' contracts to find the services that use this one
      --from string                        a golden path to create the service from: an oci:// reference or a directory
  -h, --help[=true|false]                  help for init
      --insecure-registry[=true|false]     with --delivery: the Flux OCIRepositories read the registry over plain HTTP (a local registry only)
      --name string                        service name (default: the workload's name, then the folder's)
      --namespace strings                  with --cluster: a namespace to read; repeat it for more (default: every namespace)
      --no-transparency-log[=true|false]   write transparencyLog: false under publish.sign, so signatures stay out of the public transparency log (offline signing, a throwaway key)
      --out string                         with --cluster: the folder the drafts go in, one <namespace>/<name> folder each
      --owner string                       the team that owns the service, as a bare name such as billing (default: the workload's team label)

      --registry string                    where to publish, as host/path (default: read from the workload's image)
      --registry-secret string             with --delivery: the docker-registry Secret, in each environment's namespace, that Flux and the Pacto resource log in to a private registry with
      --run-plugins strings                run these plugins the golden path names, by name (see the plan's plugin steps); each step prints the binary it runs
      --set stringArray                    set a contract value (e.g. --set service.version=2.0.0)
      --trust string                       the trust config the golden path's signature is verified with: a PEM public key or a trust config file (default $PACTO_DELIVERY_TRUST)
  -f, --values stringArray                 values file to merge into the contract (can be repeated; last wins)

    In an empty folder it scaffolds three files: a valid pacto.yaml, a placeholder OpenAPI spec at interfaces/openapi.yaml and a configuration JSON Schema at configuration/schema.json. It also plans a .pactoignore that keeps the signing key out of the bundle.

    The folder's last part becomes service.name, which must match ^[a-z0-9]([a-z0-9-]*[a-z0-9])?$, so pacto init fleet/checkout-web writes a contract for checkout-web in fleet/checkout-web. Pass --name to choose another name.

    --owner becomes service.owner.team; without it the owner is a commented placeholder and Unknown names it. --domain becomes service.domain and raises pactoVersion to 2.4. The contract gets a publish section with bundle: oci://<registry>/<name> and sign.key: cosign.key: the registry is --registry, else the registry.example placeholder that Unknown names. --describe-only leaves the publish section out.

    All three files are required by the scaffolded contract, because its interfaces: and configurations: sections point at the other two files. If you delete a directory, also delete the section that references it, or validation fails with FILE_NOT_FOUND. A contract that declares neither section needs only pacto.yaml, so drop the section and the directory together.

    --from creates one service from a golden path, in a folder that holds no pacto.yaml yet, so it refuses --cluster and several folders. --values, --set, --trust and --run-plugins go with --from. --values files apply first, then --set; a null removes a field. --trust takes a trust config file or a bare PEM public key, which then verifies golden paths in every repository; a bare key in $PACTO_DELIVERY_TRUST verifies records only. Only role: template keys verify a golden path; see Trust. The path's pacto.lock is not copied: run pacto lock in the new folder to pin its references. --delivery, with --env, --registry-secret and --insecure-registry, plans the cluster pieces from the new contract when the path publishes manifests under publish.deploy; otherwise the delivery step says why none were planned.

    pacto mcp¶

    Starts a Model Context Protocol (MCP) server exposing Pacto tools for AI agents. Supports stdio (default) and HTTP transports.

    When a bundle reference (local directory or oci:// ref) is given, the server also exposes one executable tool per OpenAPI operation in the bundle's openapi interfaces, plus a pacto_skill tool for any skills/*.md domain knowledge. Read-only (GET/HEAD) operations are exposed by default; pass --allow-writes to expose mutating operations.

    With --root, the server exposes a read-only contract catalog: the given roots plus their dependency closure, resolved once at startup and then frozen, so the session keeps its startup view even when a registry tag moves. Roots that fail to resolve stay visible as partial knowledge. The catalog grants no authorization and executes nothing.

    With --fleet, the server exposes the read-only operational-graph query tools over a fleet snapshot, rebuilt when a call arrives 30 seconds or more after the last rebuild attempt. With --dashboard-url their answers link each entity to its page on that dashboard. The shared fleet source flags (--local, --target-state, --evidence-url, --traces, --mira-source, --oci, --cache, --k8s, --namespace and --freshness) compose that snapshot and are read in --fleet mode only.

    With --delivery, the server exposes the Pacto delivery tools (pacto_delivery_*) over the ambient cluster: operation types, plan, get, explain, history, blame, undo plans and record checks, the dashboard's delivery views (caller, inbox, environments, autonomy, published and refusals, scoped by --namespace like the dashboard's), plus propose and cancel only when the apiserver says the caller is an agent (a service account, or an agent by the identity policy Pacto delivery publishes). It has no approve tool.

    Over HTTP on loopback without --auth-issuer, the server prints a bearer at launch (pmcp_..., this launch only) and every request must carry it, so other local processes cannot call the server.

    Over HTTP, --auth-issuer and --resource make every request carry a bearer token the server verifies (issuer, audience, expiry) and publish protected-resource metadata (RFC 9728); a bind beyond loopback needs them and refuses --auth and --allow-writes, which would lend this process's service credential to every caller. With --delivery the server then exchanges each caller's token for one the apiserver accepts (RFC 8693, --exchange-client-id) and builds the tools for that caller on every request, so an agent proposes as itself and a person gets the read-only tools. With --fleet the server exchanges each caller's token the same way, asks the apiserver who the caller is (a SelfSubjectReview) and asks Kubernetes RBAC what that user may read.

    With --publish, the authoring server also exposes pacto_publish_plan and pacto_publish, which publish a contract's version exactly as pacto publish does, with this process's registry credentials.

    Over HTTP the only contract tool is pacto_schema: pacto_create, pacto_edit and pacto_check read and write the server's folders and follow refs with its credentials, so they run beside the agent over stdio.

    A bundle reference, --fleet and --delivery combine in one server; --root and --publish select servers of their own. Call pacto_capabilities to learn what a server serves.

    pacto run¶

    Starts the command and watches the TCP sockets of its whole process tree: the interfaces bound with --bind must be listened on, the dependencies bound with --dep reached. Every --interval it prints the contract's compliance and findings in --output-format; once the command exits it prints a final round from the last view taken while the command ran, and exits with the command's exit code. With --fail-on it exits 1 instead of 0 when the final verdict is that bad or worse.

    The command runs in a process group of its own, so a Ctrl-C reaches it once. When pacto run owns the terminal, the command's group takes it over: it reads the terminal and gets Ctrl-C and Ctrl-Z straight from it, and pacto run takes the terminal back once it exits. Otherwise SIGINT and SIGTERM sent to pacto run are passed on to the command's whole group.

    Pacto leaves the command's stdin, stdout and stderr untouched. Rounds go to stderr, each in a single write, or with --report to a file: the file is truncated when the run starts and every round is appended to it in a single write, so a reader following it sees whole rounds (with json, one object per line).

    With root (or BPF, PERFMON, SYS_PTRACE and write access to its own cgroup) on Linux 5.11 or later with BTF and cgroup v2 (or 5.8 or later with BTF and root or CAP_SYS_RESOURCE), the command starts inside a new cgroup pacto-run-<pid> and an eBPF program sees every listener and every connection outcome of the tree, failures included (collector pacto-run+ebpf). Otherwise it falls back to polling /proc every second and says so (collector pacto-run): listeners are seen in full, so a missing one is still confirmed, but a connection is seen only while it is open at a poll and a failed connection never, so a dependency is reported reachable or unknown, never unreachable. If the program attached but the command cannot start inside the new cgroup, the run falls back to polling too and says so. Elsewhere than Linux the command runs unobserved and every runtime assertion is unsupported.

    A negative is reported once it persists for --stabilization-window. Health and metrics capabilities are probed on --host at their bound interface's port. With --evidence-url every round is also signed and sent to an Evidence Server, which needs the contract pinned as oci://...@sha256:<digest>.

    pacto run --contract <dir|oci ref> [flags] -- command [args...]

    Examples:

      pacto run --contract ./payments --bind api=8080 --dep postgres=127.0.0.1:5432 -- ./payments-server
  pacto run --contract oci://ghcr.io/acme/payments:1.4.0 --bind api=8080 --fail-on noncompliant \
    --stabilization-window 30s --output-format json --report rounds.jsonl -- java -jar payments.jar

    Flags:

          --bind stringArray                interface=port the command serves the interface on (repeatable)
      --cgroup-root string              cgroup v2 directory the session cgroup is created in (default: the caller's own cgroup under /sys/fs/cgroup)
      --contract string                 contract bundle directory or oci:// reference (required)
      --dep stringArray                 dependency=host:port the command reaches the dependency at (repeatable)
      --enable-probing[=true|false]     also probe the wire protocol of every interface found listening
      --evidence-key string             private key file envelopes are signed with
      --evidence-key-id string          key id (must match the server's trust entry)
      --evidence-producer string        producer id

      --fail-on string                  exit 1 when the command exits 0 but the final verdict is this bad or worse: one of [none noncompliant unknown] (default "none")

    Update notifications¶

    When a newer version is available, pacto displays a notification after any command:

    A new version of pacto is available: v1.0.0 -> v1.2.0
Run 'pacto update' to update.

    The check runs asynchronously and adds no latency. Results are cached for 24 hours in ~/.config/pacto/update-check.json.

    • Using --output-format json or --output-format markdown (the notice shows only for text output)
    • The PACTO_NO_UPDATE_CHECK=1 environment variable is set

    pacto validate¶

    Validates a pacto.yaml in the given directory (or oci:// reference) against the specification, running the three validation layers: structural, cross-field and policy.

    The output has one PASS, FAIL or SKIP line per stage, in order: load, lock, structural, cross-field, policy, configuration-refs, environments, guarantees, readiness and closure. The configuration-refs stage fetches the contract each configuration ref names and checks the values against its configuration schema; a ref that cannot be fetched fails it when values depend on it. The environments stage checks each environment's file against the schema of every configuration it names. Each error sits under its stage with its file:line:column when Pacto can locate it. A failed load or lock stage skips every stage after it, and a failed structural, cross-field or policy stage skips the stages after it up to environments. A failed configuration-refs stage skips nothing. The guarantees, readiness and closure stages run even when an earlier stage fails. The last line, Next:, names the one command to run now. With --output-format json the same comes as stages and next.

    pacto validate [dir | oci://ref] [flags]

    Examples:

      # Validate a local contract
  pacto validate my-service

  # Validate from current directory
  pacto validate

  # Validate from an OCI registry
  pacto validate oci://ghcr.io/acme/my-service-pacto:1.0.0

  # JSON output
  pacto validate --output-format json my-service

  # Also check the readiness gate (fail if score < minScore)
  pacto validate --readiness my-service

  # Also check every dependency against this contract's policies
  pacto validate --closure my-service

    Flags:

          --closure[=true|false]     also check every contract in the dependency closure against the policies this contract resolves. Fails when a dependency cannot be resolved and warns about deprecated interfaces of direct dependencies. Fetches each dependency once
  -h, --help[=true|false]        help for validate
      --readiness[=true|false]   also check the readiness gate: fail if the derived readiness score is below the declared (or default 100) minScore. Opt-in because gate evaluation is time-dependent (check expiry is compared against the run time), which would otherwise make plain validation non-deterministic
      --set stringArray          set a contract value (e.g. --set service.version=2.0.0)
  -f, --values stringArray       values file to merge into the contract (can be repeated; last wins)

    The --readiness gate is opt-in because it is time-dependent: it compares the assessment's single readiness.expires date against the run time, which would make plain validate non-deterministic. Expiry is declared once for the whole assessment. Individual claims carry no expires field, and adding one fails to load with PARSE_ERROR. Without the flag, validation checks the contract's structure and rules. It still checks the shape of readiness claims and skips the freshness gate. See the readiness reference for the score and gate semantics.

    A contract with a mistyped value fails like this:

    svc is invalid
PASS load
SKIP lock               no pacto.lock
FAIL structural
  svc/pacto.yaml:6:1: ERROR [SCHEMA_VIOLATION] workload: at '/workload': value must be one of 'service', 'job', 'scheduled' (did you mean "service"?)
SKIP cross-field        structural failed
SKIP policy             structural failed
SKIP configuration-refs structural failed
SKIP environments       structural failed
SKIP guarantees         no dependency declares requires
SKIP readiness          not requested (--readiness)
SKIP closure            not requested (--closure)
Next: fix workload at svc/pacto.yaml:6:1 [SCHEMA_VIOLATION], then run pacto validate svc

    Errors within a stage are listed in file order. An unknown field or an enum value close to a known one carries a did you mean hint. A failed lock stage names the pacto lock command that repairs it. When every stage passes, Next is pacto impact PUBLISHED_REF <dir>, which shows the services the change breaks; replace PUBLISHED_REF with the oci:// reference of the version you run today. In JSON, stages lists each stage with its status, reason and errors, each error carries line and column when known, file is the file they point into, and next holds the command. errors and warnings still list every stage's findings. With --set or -f an error in pacto.yaml carries no line or column, because those flags validate a merged document whose lines differ from the file. An error in an environment's file keeps them.

    Exit code: Non-zero if validation fails.

    Environment variables¶

    Boolean variables are parsed the way Go parses a boolean: 1, t, T, true, TRUE and True enable them and 0, f, F, false, FALSE and False disable them. Any other value, including yes and on, reads as off with no warning. The two opt-outs PACTO_NO_ANIM and PACTO_NO_UPDATE_CHECK are the exception: for them any other non-empty value reads as on.

    Variable Description
    PACTO_CACHE_DIR Cache directory for the pacto dashboard bundle scan. The core CLI cache location is controlled by XDG_CACHE_HOME (see below).
    PACTO_NO_CACHE Boolean. Disable OCI bundle caching (equivalent to --no-cache)
    PACTO_NO_ANIM Boolean. Disables spinners and animations (equivalent to --no-anim).
    PACTO_NO_UPDATE_CHECK Boolean. Disables automatic update checks.
    PACTO_REGISTRY_USERNAME Registry username for authentication
    PACTO_REGISTRY_PASSWORD Registry password for authentication
    PACTO_REGISTRY_TOKEN Registry token for authentication
    PACTO_INSECURE_REGISTRIES Comma-separated registry hosts that Pacto reaches over plain HTTP. It applies to every registry access: pacto push, pacto pull, dependency and policy resolution and the Evidence Server. Scoped per host, so HTTPS registries are unaffected. Loopback hosts use plain HTTP without being listed. Use it only for a controlled in-cluster registry: it disables transport encryption, so credentials and payloads travel in the clear.
    PACTO_EVIDENCE_SOURCE_URL Base URL of an Evidence Server whose read-only operational-graph contribution pacto dashboard should consume. The operator sets it when it wires a managed Evidence Server. Unset means no evidence source configured, which the dashboard reports separately from an unavailable source.
    XDG_CONFIG_HOME Override config directory (default: ~/.config). Affects pacto login credentials and update check cache
    XDG_CACHE_HOME Override cache directory (default: ~/.cache). Affects OCI bundle cache location

    Dashboard environment variables¶

    The following variables configure the dashboard when set (see also Dashboard Container). Each mirrors the flag named beside it: an explicitly passed flag wins, and otherwise the variable overrides that flag's default.

    Variable Flag Description
    PACTO_DASHBOARD_REPO (positional args) Comma-separated OCI repositories, used only when no positional oci:// argument is given
    PACTO_DASHBOARD_HOST --host Bind address (default: 127.0.0.1)
    PACTO_DASHBOARD_PORT --port HTTP port (default: 3000)
    PACTO_DASHBOARD_NAMESPACE --namespace Kubernetes namespace filter (empty = all)
    PACTO_DASHBOARD_CORS_ORIGIN --cors-origin One explicit origin allowed to call the API. Unset means same-origin only.
    PACTO_DASHBOARD_TRACES --traces OTLP/JSON trace files to fold observed dependencies from
    PACTO_DASHBOARD_MIRA_SOURCES --mira-source Space-separated Mira base URLs whose service map supplies observed calls
    PACTO_DASHBOARD_TRACE_SOURCES --trace-source Named offline trace sources as NAME=PATH, where NAME is the source's identity (what the fleet, the API and the dashboard's Data Source list call it) and PATH is the trace file location. Identity and location are separate, so reordering the configuration or moving the file keeps the source's name. Two sources whose files share a basename stay two sources. A name must be unique across every Data Source the dashboard assembles.

    The three list variables split on whitespace

    PACTO_DASHBOARD_TRACES, PACTO_DASHBOARD_TRACE_SOURCES and PACTO_DASHBOARD_MIRA_SOURCES go through the same generic flag binding as every other dashboard variable, which splits a multi-valued string on spaces. PACTO_DASHBOARD_TRACES="a.json b.json" supplies two files; PACTO_DASHBOARD_TRACES=a.json,b.json supplies one, named a.json,b.json. PACTO_DASHBOARD_REPO is read directly and splits on commas.

    The dashboard starts either way: it skips a trace file it cannot read, so the symptom is missing observed dependencies with no error. Check the snapshot's reported limitations if the operational graph looks emptier than you expect.

    Authentication¶

    Pacto follows this credential resolution chain:

    1. Environment variables (PACTO_REGISTRY_TOKEN, or PACTO_REGISTRY_USERNAME + PACTO_REGISTRY_PASSWORD)
    2. Pacto config (~/.config/pacto/config.json, written by pacto login, which persists --username and --password)
    3. GitHub CLI (gh auth token, for ghcr.io and docker.pkg.github.com only)
    4. Docker config (~/.docker/config.json) and credential helpers (including cloud-registry helpers for ECR, GCR and ACR)
    5. Anonymous fallback

    For GitHub registries, step 3 means you can skip pacto login entirely if you have gh authenticated with the write:packages scope (see pacto login above).

    Pacto stores no credentials in contract files.
