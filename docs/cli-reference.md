# CLI Reference

Every command accepts `-v` / `--verbose` for debug-level logging and `--help` for detailed usage. `--output-format` is a global flag taking `text` (the default), `json` or `markdown`.

!!! warning "What `--output-format` guarantees"
    Read this before you parse Pacto's output in a script.

    - **`json` describes a *successful* result.** When a command fails to
      produce its result, for example because a reference is unreachable or
      `pacto.lock` is missing, the error goes to **stderr as plain text and
      stdout stays empty**, whatever `--output-format` says. A negative
      *verdict* is still a result: `pacto validate` on an invalid contract and
      `pacto diff` on a breaking change both print their whole JSON document to
      stdout **and** exit 1. An empty stdout tells you there is nothing to
      parse. Read stdout when it is non-empty, and read the exit code for the
      verdict.
    - **Only `pacto diff` implements `markdown`**, for posting a diff as a CI
      comment. Every other command renders text.
    - **Keys are camelCase** in every command (`"path"`, `"valid"`, `"errors"`,
      `"upToDate"`). Before v4, `init`, `validate`, `pack`, `pull` and `push`
      emitted capitalised keys (`"Path"`, `"Valid"`).
    - **An unrecognised value is rejected.** `--output-format yaml` exits 1 with
      `unsupported output format "yaml"` before the command runs.

    The interactive and side-effecting commands (`login`, `logout`, `update`,
    `mcp`, `dashboard`) inherit the flag from the root command and always emit text.

## Exit codes

Pacto exits `0`, `1` or `2`, apart from `pacto run` (below). `0` means the
command produced its result and the result was acceptable. `1` means the check
failed or the command could not run, so **the exit status alone cannot
distinguish "the check failed" from "the command could not run"**. `2` means
`pacto impact` could not show that a change or an event is safe, and no other
command exits `2` for its own result. `pacto run` exits with the exit code of
the command it wraps, whatever it is, or `1` when that command exits `0` and
the final verdict fails `--fail-on`.

| Exits `1` | Exits `0` |
| --- | --- |
| `pacto diff` where the overall classification is `BREAKING` | a `POTENTIAL_BREAKING` or `NON_BREAKING` diff |
| `pacto validate` reporting at least one error | validation that reported only warnings |
| `pacto lock --check` on a stale lockfile, or with none at all (`LOCK_MISSING`) | a lockfile that is up to date |
| `pacto impact` where the gate is `blocked`: a `BREAKING` change reaches a consumer that does not accept the new version and runs on a known target, or a policy referrer that fails the new policy does | `pacto impact` where the gate is `clear`: the change is not `BREAKING` and every policy referrer was checked and passes the new policy, or the snapshot is complete and no service depends on the changed one; an event (`--unavailable`, `--removed` or `--regressed`) when the complete snapshot shows nothing depends on the service |
| **any command that could not run**, for example on an unresolvable reference, an unreadable bundle or an unknown flag | |

| Exits `2` |
| --- |
| `pacto impact` where the gate is `unverified`: a `BREAKING` change that nothing is shown to block, on a partial answer or with consumers none of which is shown to be safe; or a change of any classification with a policy referrer that fails the new policy and runs nowhere known, could not be checked or could not be resolved |
| `pacto impact --unavailable`, `--removed` or `--regressed` when anything depends on the service or the answer is partial. An event never exits `1` for its result |

Two cases affect CI gates:

- A `pacto diff` against a missing reference exits `1`, the same as a breaking
  change.
- `pacto impact` exits `1` only when the change is breaking **and** a source
  that knows where services run shows an incompatible consumer on a target.
  Sources that know no targets, such as `--local` alone, cannot show that, so
  a breaking change with consumers exits `2`. A job that gates on deployed
  impact alone can treat `2` as a pass; any other job fails on it.

**Use stdout to tell a verdict from a failure.** A command that produced a
verdict writes it to stdout and puts a one-line summary on stderr. A command
that could not run leaves stdout empty:

| Invocation | Exit | stdout | stderr |
| --- | --- | --- | --- |
| `pacto diff --output-format json OLD NEW` (breaking) | `1` | the full JSON result | `breaking changes detected` |
| `pacto diff --output-format json oci://…/absent:1.0.0 NEW` | `1` | *empty* | `old contract: artifact not found: …` |

In a script, branch on stdout when it is non-empty, and treat an empty stdout
with exit `1` as a tool failure.

## OCI version resolution

All commands that accept `oci://` references support automatic version resolution. When a reference omits the tag (for example `oci://ghcr.io/acme/svc-pacto` with no `:1.0.0`), pacto queries the registry for available tags and selects the **highest semver version**.

For dependency references declared with a `compatibility` constraint, only tags satisfying the constraint are considered. For example, a dependency with `compatibility: "^2.0.0"` and available tags `1.0.0`, `2.0.0`, `2.3.0`, `3.0.0` resolves to `2.3.0`.

Resolution ignores non-semver tags such as `latest` and `main`. Digest-pinned references (`@sha256:...`) and explicitly tagged references are used as-is.

!!! note "Constraints apply to the CLI's dependency graph"
    The CLI applies `compatibility` constraints when it resolves a contract's
    **declared dependencies**, for example in `pacto graph`. The **dashboard's**
    version discovery selects the highest semver tag and ignores per-dependency
    `compatibility` constraints. Root-contract pulls (a tagless top-level `oci://`
    ref) also select the highest semver tag with no constraint.

## `pacto agent`

Runs until interrupted. Watches TCP listeners and outbound connection outcomes with an eBPF program, attributes each socket to the workload that created it (a Kubernetes pod, a container, a systemd unit or a pacto run session, from its cgroup, or from its network namespace when the cgroup names none) and publishes a snapshot every --publish-interval. --sink kubernetes writes the node's NodeRuntimeObservation status (pods only; what the Pacto operator's node agent DaemonSet runs); --sink stdout prints one JSON snapshot per line.

--sink local and --sink evidence check workloads against their contracts on this host. The workloads come from --bindings (a YAML list of {match: {unit|container|cgroup|session|pid}, contract, host, interfaces: {name: port}, dependencies: {name: host:port}}) and with --docker from running containers labelled dev.pacto.contract=<dir|oci ref>, dev.pacto.bind.&lt;interface&gt;=&lt;port&gt; and dev.pacto.dep.&lt;dependency&gt;=<host:port>. Interfaces and dependencies are judged from the kernel's view, health and metrics capabilities by probing the bound port; a negative is reported once it persists for --stabilization-window. --sink local prints every target's compliance and findings each interval in --output-format; --sink evidence signs each target's evidence and sends it to an Evidence Server, which needs contracts pinned as oci://...@sha256:&lt;digest&gt;. Envelope sequences start at the wall clock in nanoseconds and count up, so they keep increasing across restarts as long as the clock does.

Needs Linux 5.11 or later with BTF, or 5.8 or later with BTF and root or CAP_SYS_RESOURCE; root (or BPF, PERFMON and SYS_PTRACE); and the host's /proc and cgroupfs.

```
pacto agent [flags]
```

**Examples:**

```
  pacto agent --sink stdout --publish-interval 5s
  pacto agent --sink kubernetes --cgroup-root /host/sys/fs/cgroup
  pacto agent --sink local --docker --cgroup-root /host/sys/fs/cgroup
  pacto agent --sink evidence --bindings bindings.yaml --evidence-url https://evidence.example.com \
    --evidence-key agent.key --evidence-key-id k1 --evidence-producer host-1
```

**Flags:**

```
      --bindings string                   with --sink local or evidence: YAML file binding workloads to contracts
      --cgroup-root string                where the host cgroup v2 hierarchy is mounted; empty attributes by network namespace only (default "/sys/fs/cgroup")
      --docker[=true|false]               with --sink local or evidence: check running containers labelled dev.pacto.contract (Docker Engine API on /var/run/docker.sock)
      --docker-label-filter stringArray   with --docker: only check containers that also carry this label (key=value or key; repeatable, all must match), e.g. com.docker.compose.project=demo
      --enable-probing[=true|false]       also probe the wire protocol of every interface found listening
      --evidence-key string               with --sink evidence: private key file envelopes are signed with
      --evidence-key-id string            with --sink evidence: key id (must match the server's trust entry)
      --evidence-producer string          with --sink evidence: producer id
      --evidence-url string               with --sink evidence: Evidence Server base URL
  -h, --help[=true|false]                 help for agent
      --namespace string                  namespace the NodeRuntimeObservation is written to with --sink kubernetes (default $POD_NAMESPACE)
      --node-name string                  name of this host; with --sink kubernetes also the NodeRuntimeObservation name (default $NODE_NAME)
      --proc-root string                  where the host /proc is mounted (a pod needs hostPID, a container --pid=host) (default "/proc")
      --publish-interval duration         how often a snapshot is published (whole seconds) (default 30s)
      --resync-interval duration          how often workloads, network namespaces and listeners are re-read from /proc (default 1m0s)
      --ringbuf-size uint32               kernel ring buffer size in bytes; a power of two and a multiple of the page size (default 262144)
      --sink string                       where snapshots go: one of [kubernetes stdout local evidence] (default "stdout")
      --stabilization-window duration     how long a negative must persist before it is reported (default 2m0s)
```

## `pacto dashboard`

Launches an operational dashboard over the fleet snapshot: the same
operational graph the CLI's `pacto fleet` commands query, served as a web UI.

The dashboard is the exploration and observability layer of the Pacto system.
It visualizes the same contracts the CLI manages and the operator verifies,
organised around four workflows: an operational Overview, the Services
inventory, the Operational Graph and Change analysis.

Each positional argument is a contract source reference:
  - oci://registry/repo  → OCI registry source (can be repeated)
  - ./path/to/dir        → local filesystem source (at most one)

When no arguments are given, sources are auto-detected:
  - local: enabled if pacto.yaml is found in the working directory
  - cache: enabled if the OCI bundle cache (~/.cache/pacto/oci) holds bundles
  - k8s:   enabled if a kubeconfig or in-cluster config resolves
  - oci:   from the positional arguments, the PACTO_DASHBOARD_REPO env var, or
           the status.contract.resolvedRef of the cluster's Pacto resources

When running alongside the Kubernetes operator, OCI repositories are
automatically discovered from the status.contract.resolvedRef fields of Pacto
CRD resources on every refresh. The result combines runtime state from the
operator with contract content from OCI.

Every source contributes to one snapshot, rebuilt in the background, and each
answer carries the as-of time and the completeness of the sources behind it.

```
pacto dashboard [sources...] [flags]
```

**Examples:**

```
  # Start dashboard with auto-detected sources
  pacto dashboard

  # Start from a specific directory
  pacto dashboard ./services

  # Include OCI repositories
  pacto dashboard oci://ghcr.io/org/order-service oci://ghcr.io/org/payment-service

  # Mix local and OCI sources
  pacto dashboard ./services oci://ghcr.io/org/payment-service

  # Custom port
  pacto dashboard --port 9090

  # Specify Kubernetes namespace (default: all namespaces)
  pacto dashboard --namespace production
```

**Flags:**

```
      --cors-origin string                explicit cross-origin allowed to call the API (default: same-origin only)

It auto-detects sources: pass OCI repositories as arguments, or run it next to the operator (with a kubeconfig) and it discovers OCI repositories from each Pacto resource's `status.contract.resolvedRef`. For a tour of what the dashboard surfaces, see [For platform engineers](platform-engineers.md); to run it as a container, see [Dashboard container](dashboard-docker.md).

## `pacto delivery`

Pacto delivery decides which version each environment (a Stage) runs. Every change is an Operation: plan it to see what the promoter will do and who must agree, propose it, and a person approves only when the contracts say a consumer would break, Pacto cannot see enough or the Stage asks for approval on every promote.

There is no approve tool for agents. `approve` is for people.

```
pacto delivery [flags]
```

**Flags:**

```
      --delivery-namespace string   namespace Pacto delivery runs in, whose published identity policy (agent, break-glass and human groups, team prefix) says who is an agent and who may answer (default "pacto-delivery")
  -h, --help[=true|false]           help for delivery
  -n, --namespace string            namespace of the Stage and its Operations (default "default")
      --trust string                the trust config delivery records are verified with: the recorder's PEM public key, or a YAML file of keys and the streams each may sign (default $PACTO_DELIVERY_TRUST)
```

## `pacto diff`

Compares two contracts (local paths or oci:// references) and produces a classified change set (BREAKING, POTENTIAL_BREAKING, NON_BREAKING).

```
pacto diff <old> <new> [flags]
```

**Examples:**

```
  # Compare a remote contract with a local one
  pacto diff oci://ghcr.io/acme/svc-pacto:1.0.0 my-service

  # Markdown output for CI comments
  pacto diff --output-format markdown oci://ghcr.io/acme/svc-pacto:1.0.0 my-service
```

**Flags:**

```
  -h, --help[=true|false]        help for diff
      --new-set stringArray      set a value on the new contract (e.g. --new-set service.version=2.0.0)
      --new-values stringArray   values file to merge into the new contract (can be repeated)
      --old-set stringArray      set a value on the old contract (e.g. --old-set service.version=1.0.0)
      --old-values stringArray   values file to merge into the old contract (can be repeated)
```

**Exit code:** `1` when the overall classification is `BREAKING`, and also when the diff could not be produced. A non-zero exit alone is therefore no contract verdict. See [Exit codes](#exit-codes) for how to tell the two apart. A `POTENTIAL_BREAKING` result exits `0`, so a CI gate that stops on it must read the classification.

The diff engine performs deep comparison of referenced OpenAPI specs, detecting changes at the path, method, parameter, request body and response level. The optional `docs/` directory is ignored: documentation changes produce no diff entries and leave the compatibility classification unchanged.

When both bundles include an `sbom/` directory with recognized SBOM files (`.spdx.json` or `.cdx.json`), `pacto diff` reports package-level changes: added, removed or modified packages (version and license). SBOM changes are informational and leave the overall classification and exit code unchanged.

When dependencies change between the old and new contracts (version upgrades, additions or removals), a dependency graph diff section is displayed showing the tree of affected nodes.

See [Change Classification](contract-reference/diff.md#change-classification-rules) for the full rules.

## `pacto doc`

Reads a pacto.yaml in the given directory (or oci:// reference) and generates structured Markdown documentation.

```
pacto doc [dir | oci://ref] [flags]
```

**Examples:**

```
  # Print documentation to stdout
  pacto doc my-service

  # Write documentation to a file
  pacto doc my-service -o docs/

  # Serve documentation in the browser
  pacto doc my-service --serve

  # Serve on a custom port
  pacto doc my-service --serve --port 9090

  # Launch an interactive API explorer (Swagger UI)
  pacto doc my-service --ui swagger

  # Select a specific interface
  pacto doc my-service --ui swagger --interface public-api

  # Point try-it-out requests to a running backend
  pacto doc my-service --ui swagger --target http://localhost:3000

  # Per-interface target mapping
  pacto doc my-service --ui swagger --target public-api=http://localhost:3000 --target admin-api=http://localhost:3001
```

**Flags:**

```
  -h, --help[=true|false]    help for doc
      --interface string     interface name to display (used with --ui)
  -o, --output string        output directory for generated Markdown; a NAME.html value writes a static documentation site to a NAME/ directory instead
      --port int             port for the documentation server (used with --serve or --ui) (default 8484)
      --serve[=true|false]   serve the offline dashboard-grade documentation site over a local HTTP server
      --set stringArray      set a contract value (e.g. --set service.version=2.0.0)
      --target stringArray   target server URL for try-it-out requests; supports interface=url mapping (used with --ui)
      --ui string            UI type for the interactive API explorer (one of: swagger)
  -f, --values stringArray   values file to merge into the contract (can be repeated; last wins)
```

The header line reports the contract's own state. `pacto doc` reads a bundle and observes no cluster. A contract that has never been runtime-evaluated therefore reads `status NotEvaluated`, and one that declares no workload reads `compliance REFERENCE`. Both are the expected result for a freshly scaffolded contract. See [Compliance states](model.md#compliance-model).

Markdown prints to stdout by default. `-o DIR` writes `DIR/<service>.md`. `-o NAME.html` writes a self-contained static documentation site (a directory) that reuses the dashboard UI offline.

`--serve` serves that static site locally. `--ui swagger` launches an interactive API explorer.

`--serve`, `--ui` and `-o` are mutually exclusive. Use `--interface` to pick one OpenAPI interface with `--ui`. `--target` and `--target iface=url` point try-it-out at a backend.

Sibling dependencies are resolved in parallel. OCI bundles cache under `~/.cache/pacto/oci/`. `--no-cache` bypasses the cache.

## `pacto evidence`

Produce and verify the signed, versioned envelopes that carry a Pacto EvidenceSet from a remote or disconnected environment to a platform that ingests it. Keys are Ed25519; the wire format is defined by pkg/evidenceenvelope.

```
pacto evidence [flags]
```

**Flags:**

```
  -h, --help[=true|false]   help for evidence
```

### `pacto evidence keygen`

Writes the private seed to &lt;keyId&gt;.key (base64, 0600) and the public key into --out. With --producer, the public key is written as &lt;producer&gt;__&lt;keyId&gt;.pub, which binds the key to that producer in the trust store. Hand that file to the platform. Sign with the SAME --producer and --key-id. With no --producer, a bare &lt;keyId&gt;.pub binds the key to a producer named after the key id (the single-producer default).

```
pacto evidence keygen [flags]
```

**Flags:**

```
      --force[=true|false]   overwrite existing key files instead of failing
  -h, --help[=true|false]    help for keygen
      --key-id string        key id (defaults to a fingerprint of the public key)
      --out string           directory to write the keypair into (default ".")
      --producer string      producer id to bind the key to (writes <producer>__<keyId>.pub)
```

### `pacto evidence provisioned`

Writes an EvidenceSet that reports the provisioning state of the resource a consumer's configuration reference or dependency asked for. Sign it with pacto evidence sign and post it with pacto evidence send. Any adapter (a CI job, a controller, a script) can run it; Pacto keeps no provider-specific code. The subject defaults to &lt;repository&gt;/<environment or default>/&lt;kind&gt;/&lt;name&gt;, so each resource keeps its own latest report. Prints the EvidenceSet JSON.

```
pacto evidence provisioned [flags]
```

**Flags:**

```
      --collector string       collector id recorded as provenance (defaults to pacto)
      --configuration string   consumer configuration (with a ref) that asked for the resource
      --contract string        consumer contract revision: oci://<repo>@sha256:<digest>
      --dependency string      consumer dependency that asked for the resource
      --environment string     consumer environment the resource serves
      --external-ref string    opaque handle of the resource at the provider (at most 253 printable bytes)
  -h, --help[=true|false]      help for provisioned
      --observed-at string     observation timestamp (RFC3339; defaults to now)
      --outcome string         collection outcome: Observed, Unsupported, Failed, Stale or Insufficient; anything but Observed carries no phase (default "Observed")
      --phase string           provisioning phase: Requested, Provisioning, Ready, Failed or Deleting
      --provider string        provider slug (lowercase letters, digits and hyphens)
      --subject string         EvidenceSet subject (defaults to <repository>/<environment or default>/<kind>/<name>)
```

### `pacto evidence send`

Reads a signed envelope JSON file and POSTs it to an ingestion host's --url. Prints the host's JSON response and exits non-zero on a non-2xx status.

```
pacto evidence send <envelope.json> [flags]
```

**Flags:**

```
  -h, --help[=true|false]   help for send
      --url string          ingestion host envelope endpoint URL
```

### `pacto evidence serve`

Starts an HTTP host that accepts signed evidence envelopes at POST /api/evidence/v1/envelopes, verifies them against --trust, evaluates the carried evidence against its resolved contract and publishes accepted records to the contract registry as OCI 1.1 referrers of the exact contract revision each report is about. Every --subject is an immutable oci://&lt;repo&gt;@sha256:&lt;digest&gt; reference; the registry is the only durable store, so the host keeps no local state and survives restarts. GET .../health is an always-200 liveness probe; .../ready reports 503 while a subject cannot be resolved or its referrers enumerated; .../producers advertises trusted producer ids; .../targets exposes the latest accepted targets. Registry credentials come from the same sources as `pacto pull`. Exactly one server may write to a subject set. Serves until interrupted.

```
pacto evidence serve [flags]
```

**Flags:**

```
  -h, --help[=true|false]       help for serve
      --listen-address string   host:port to listen on (supersedes --port)
      --port int                port to listen on (127.0.0.1); superseded by --listen-address (default 8686)
      --producer stringArray    advertised trusted producer id (repeatable)
      --subject stringArray     exact contract revision evidence is stored on: oci://<repo>@sha256:<digest> (repeatable, required)
      --trust string            trust store: a public-key file or a directory of <keyId>.pub files
```

### `pacto evidence sign`

Reads an EvidenceSet JSON file (- reads stdin), wraps it in an Ed25519-signed envelope and prints the envelope JSON. Only --issued-at is non-deterministic (it defaults to now), so pinning it is enough to make re-signing the same evidence produce a byte-identical envelope.

```
pacto evidence sign <evidence.json> [flags]
```

**Flags:**

```
  -h, --help[=true|false]         help for sign
      --id string                 envelope id (defaults to a hash over the API version, producer id, sequence and evidence, so two producers reporting identical evidence never collide)
      --issued-at string          issued-at timestamp (RFC3339; defaults to now)
      --key string                path to the private key file
      --key-id string             producer key id (must match the trust-store entry)
      --producer string           producer id
      --producer-version string   producer version (optional)
      --sequence uint             producer-scoped monotonic sequence; each report must be strictly greater than the producer's last
      --ttl duration              validity window; 0 disables expiry (default 24h0m0s)
```

### `pacto evidence verify`

Decodes an envelope and verifies its signature, freshness and trust against a --trust public-key file or directory of &lt;keyId&gt;.pub files. Exits non-zero when verification fails.

```
pacto evidence verify <envelope.json> [flags]
```

**Flags:**

```
  -h, --help[=true|false]   help for verify
      --trust string        trust store: a public-key file or a directory of <keyId>.pub files
```

## `pacto explain`

Parses a pacto.yaml in the given directory (or oci:// reference) and produces a human-readable summary of the service contract. Each configuration lists its effective values per environment: its inline values with that environment's file merged on top. With two or more environments it also lists the values they disagree on, for every environment or the ones --environments names.

```
pacto explain [dir | oci://ref] [flags]
```

**Examples:**

```
  pacto explain my-service
  pacto explain oci://ghcr.io/acme/orders@sha256:<digest> --output-format json
  pacto explain my-service --environments test,production
```

**Flags:**

```
      --environments strings   compare the effective configuration values of these environments, such as test,production
  -h, --help[=true|false]      help for explain
      --set stringArray        set a contract value (e.g. --set service.version=2.0.0)
  -f, --values stringArray     values file to merge into the contract (can be repeated; last wins)
```

**What it covers.** The text output summarises identity, workload, state, capabilities, interfaces, dependencies and readiness. To read `configurations` and `policies`, use `pacto doc` or open `pacto.yaml`. `metadata` is carried by `--output-format json` only; the text output omits it.

**Readiness output.** When the contract declares a `readiness` section (a `pactoVersion: "2.0"` feature), `explain` adds a Readiness block: the derived **Score**, the **Gate** result (`PASS`/`FAIL` with `score / minScore`), **Earned** and **Total Weight**, the partial credit multiplier, the assessment `expires` date with countdown (or an Expired state) and a per-check table showing each check's declared `status` (`done`/`partial`/`not-done`/`deferred`), `category`, weight, earned weight and `evidence`. The Readiness block also includes a revision-history table when `history[]` is present. `--output-format json` includes the same data plus `doneCount`, `partialCount`, `notDoneCount`, `deferredCount` and `expired` (boolean). Readiness status is time-dependent: the score is 0 when the current date is past the assessment-level `expires`.

## `pacto impact`

Composes a semantic contract diff (old→new) with the operational graph to answer which consumers a change really affects, how strong the evidence is and whether their declared compatibility still holds.

When no fleet source holds the changed service, the new revision is added to the snapshot so the services that depend on it are found.

With --unavailable, --removed or --regressed, impact answers what happens if that service becomes unavailable, is removed or a revision of it regressed. Consumers are graded breaks (every edge on their path is required), may degrade (an optional edge) or unknown. The gate is unverified (exit 2) when anything depends on the service and clear (exit 0) only when the complete snapshot shows nothing does. --regressed with an artifact digest reads delivery's recorded failures with your own cluster credentials when a cluster is reachable.

The answer ends in a release gate, and the exit status follows it:
  0  clear: the change is not BREAKING and every service that references its policy passes the new policy, or the snapshot is complete and no service depends on the changed one.
  1  blocked: a consumer that runs on a known target does not accept the new version of a BREAKING change, or its contract fails the changed service's new policy, whatever the classification.
  2  unverified: nothing is shown to block the change, but the answer cannot clear it: a BREAKING change whose answer is partial or whose consumers none is shown to be safe, or a service that references the changed policy and fails it running nowhere known, could not be checked or could not be resolved. A run over --local bundles alone knows no targets, so a BREAKING change with consumers exits 2.
A command that could not run also exits 1, with nothing on stdout. Add --target-state (or a live source) so the gate can tell deployed impact apart.

Pacto finds consumers only in the sources you pass, such as --local, --root, --oci, --cache, --k8s, --evidence-url and --traces. With --local alone Pacto sees only the contracts in those folders, so "No affected consumers" is not evidence of safety.

```
pacto impact <old> <new> | --unavailable <service> | --removed <service> | --regressed <service>@<revision> [flags]
```

**Examples:**

```
  # Impact of upgrading a local service against the local fleet
  pacto impact ./svc-v1 ./svc-v2 --local .

  # Include observed (runtime) evidence and emit JSON
  pacto impact oci://ghcr.io/acme/svc:1.0.0 ./svc --include-observed --output-format json

  # What breaks if redis becomes unavailable, or postgresql is removed
  pacto impact --unavailable redis --local .
  pacto impact --removed postgresql --local . --target-state targets.yaml

## `pacto init`

Writes the contract for the service in dir (default: the current folder).

An empty or new folder gets a blank contract with the bundle structure
(interfaces/, configuration/) and the owner and domain you pass; with no
--owner the owner is a commented placeholder that Unknown names. A folder that
already holds a service gets a contract read from its Dockerfile and
Kubernetes manifests, and a list of what Pacto found and what it could not
tell (Unknown). The workload's environment, including the ConfigMaps it reads,
becomes a configuration schema with each value as its default. A URL in it
that names another service in the cluster becomes a dependency: with that
service's contract in --fleet, its bundle and a range from its version;
without it, a placeholder range that the comment above it and Unknown name. A
readiness, liveness or startup probe becomes a health check.

Either contract also gets a publish section, for pacto publish, with its
bundle under --registry (default: the workload's image registry, else the
registry.example placeholder). To describe the service and leave delivery out,
pass --describe-only: the contract then has no publish section and needs no
signing key. --delivery also writes the cluster pieces: the Pacto resource
that checks the running service, and per environment a Stage with the Flux
OCIRepository and Kustomization it applies through. Each Stage starts at
observe: it plans every new version and moves nothing, and the OCIRepository
stays pinned to the tag you deploy, so GitOps keeps applying what it did. The
last environment's Stage also asks a person to approve every promote.

--owner is the team's bare name, such as billing: usually the team label on
the workload. --domain is the business domain, such as payments. An AI agent
is a service too: its tools are an mcp interface, the model it calls is a
dependency and its eval suite is a checks entry; see
https://pacto.run/latest/contract-reference/checks/#an-agent-is-a-service.

Several folders are each pactified, with a summary at the end. --cluster
drafts a contract for every workload in the namespaces that no Pacto
describes yet, in &lt;out&gt;/&lt;namespace&gt;/&lt;name&gt;: its manifests are read from the
cluster, and the services its pods were seen calling become dependencies
pinned to the version seen running, for you to widen. Drafts are only
written, never published, and a draft that is not valid fails the command.

With --from the service is created from a golden path: an oci:// reference or
a directory whose contract declares service.template. The path's contract is
copied with its identity reset: the name, version 0.1.0, --owner (required)
and --domain, with --values and --set applied over any field and
service.origin recording the path it came from. A path read from a registry
is pulled by digest; when the trust config (--trust, else
$PACTO_DELIVERY_TRUST) names a template key, the path must be signed by one
or nothing is created, and otherwise the signature is reported Unknown. The
created contract is validated with its references resolved before anything is
written, and the Status block says what was checked and what Pacto cannot
tell yet. Each plugin the path names is listed with the binary it resolves
to; only the ones you name with --run-plugins run, never with --plan, and
the files they return are added like the path's own. --delivery plans the
cluster pieces from the created contract when the path publishes manifests
under publish.deploy; otherwise the delivery step says why none were planned.

It only adds files and missing .pactoignore lines; any other file already
there is yours and is left as it is, so running it twice is safe. --plan shows exactly what would be added and
changes nothing.

```
pacto init [dir...] [flags]
```

**Examples:**

```
  pacto init my-service
  pacto init my-service --owner billing --domain payments --registry ghcr.io/acme
  pacto init --plan
  pacto init --describe-only --owner billing
  pacto init --delivery --owner payments --fleet ../contracts
  pacto init --delivery --no-transparency-log --insecure-registry
  pacto init --delivery --registry-secret registry-creds
  pacto init services/checkout services/payments --plan
  pacto init --cluster --namespace shop --out drafts
  pacto init gift-cards --from oci://ghcr.io/acme/paths/http-service:1.0.0 --owner checkout --domain commerce
```

**Flags:**

```
      --cluster[=true|false]               draft a contract for every workload in the cluster that no Pacto describes, reading the current kubeconfig context
      --delivery[=true|false]              also declares each --env in pacto.yaml with an empty values file, and writes the cluster pieces: the Pacto resource, a Stage per environment and its Flux OCIRepository and Kustomization
      --describe-only[=true|false]         write a contract that only describes the service: no publish section, so no signing key
      --domain string                      business domain, such as payments
      --env strings                        environments for --delivery: declared in the contract and given a Stage each, in promotion order (default [test,prod])
      --fleet strings                      folders of other services' contracts to find the services that use this one
      --from string                        a golden path to create the service from: an oci:// reference or a directory
  -h, --help[=true|false]                  help for init
      --insecure-registry[=true|false]     with --delivery: the Flux OCIRepositories read the registry over plain HTTP (a local registry only)
      --name string                        service name (default: the workload's name, then the folder's)
      --namespace strings                  with --cluster: a namespace to read; repeat it for more (default: every namespace)
      --no-transparency-log[=true|false]   write transparencyLog: false under publish.sign, so signatures stay out of the public transparency log (offline signing, a throwaway key)
      --out string                         with --cluster: the folder the drafts go in, one <namespace>/<name> folder each
      --owner string                       the team that owns the service, as a bare name such as billing (default: the workload's team label)
      --plan[=true|false]                  show what would be added and change nothing
      --registry string                    where to publish, as host/path (default: read from the workload's image)
      --registry-secret string             with --delivery: the docker-registry Secret, in each environment's namespace, that Flux and the Pacto resource log in to a private registry with
      --run-plugins strings                run these plugins the golden path names, by name (see the plan's plugin steps); each step prints the binary it runs
      --set stringArray                    set a contract value (e.g. --set service.version=2.0.0)
      --trust string                       the trust config the golden path's signature is verified with: a PEM public key or a trust config file (default $PACTO_DELIVERY_TRUST)
  -f, --values stringArray                 values file to merge into the contract (can be repeated; last wins)
```

In an empty folder it scaffolds three files: a valid `pacto.yaml`, a placeholder OpenAPI spec at `interfaces/openapi.yaml` and a configuration JSON Schema at `configuration/schema.json`. It also plans a `.pactoignore` that keeps the signing key out of the bundle.

The folder's last part becomes `service.name`, which must match `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$`, so `pacto init fleet/checkout-web` writes a contract for `checkout-web` in `fleet/checkout-web`. Pass `--name` to choose another name.

`--owner` becomes `service.owner.team`; without it the owner is a commented placeholder and Unknown names it. `--domain` becomes `service.domain` and raises `pactoVersion` to `2.4`. The contract gets a publish section with `bundle: oci://<registry>/<name>` and `sign.key: cosign.key`: the registry is `--registry`, else the `registry.example` placeholder that Unknown names. `--describe-only` leaves the publish section out.

All three files are required **by the scaffolded contract**, because its `interfaces:` and `configurations:` sections point at the other two files. If you delete a directory, also delete the section that references it, or validation fails with `FILE_NOT_FOUND`. A contract that declares neither section needs only `pacto.yaml`, so drop the section and the directory together.

`--from` creates one service from a [golden path](golden-paths.md), in a folder that holds no `pacto.yaml` yet, so it refuses `--cluster` and several folders. `--values`, `--set`, `--trust` and `--run-plugins` go with `--from`. `--values` files apply first, then `--set`; a `null` removes a field. `--trust` takes a trust config file or a bare PEM public key, which then verifies golden paths in every repository; a bare key in `$PACTO_DELIVERY_TRUST` verifies records only. Only `role: template` keys verify a golden path; see [Trust](golden-paths.md#trust). The path's `pacto.lock` is not copied: run `pacto lock` in the new folder to pin its references. `--delivery`, with `--env`, `--registry-secret` and `--insecure-registry`, plans the cluster pieces from the new contract when the path publishes manifests under `publish.deploy`; otherwise the delivery step says why none were planned.

```bash
gh auth refresh --scopes write:packages

After this, `pacto push oci://ghcr.io/...` will work without any additional login step.

If `gh` is missing or unauthenticated, pacto moves on to the next credential source in the chain.

## `pacto mcp`

Starts a Model Context Protocol (MCP) server exposing Pacto tools for AI agents. Supports stdio (default) and HTTP transports.

When a bundle reference (local directory or oci:// ref) is given, the server also exposes one executable tool per OpenAPI operation in the bundle's openapi interfaces, plus a pacto_skill tool for any skills/*.md domain knowledge. Read-only (GET/HEAD) operations are exposed by default; pass --allow-writes to expose mutating operations.

With --root, the server exposes a read-only contract catalog: the given roots plus their dependency closure, resolved once at startup and then frozen, so the session keeps its startup view even when a registry tag moves. Roots that fail to resolve stay visible as partial knowledge. The catalog grants no authorization and executes nothing.

With --fleet, the server exposes the read-only operational-graph query tools over a fleet snapshot, rebuilt when a call arrives 30 seconds or more after the last rebuild attempt. With --dashboard-url their answers link each entity to its page on that dashboard. The shared fleet source flags (--local, --target-state, --evidence-url, --traces, --mira-source, --oci, --cache, --k8s, --namespace and --freshness) compose that snapshot and are read in --fleet mode only.

With --delivery, the server exposes the Pacto delivery tools (pacto_delivery_*) over the ambient cluster: operation types, plan, get, explain, history, blame, undo plans and record checks, plus propose and cancel only when the apiserver says the caller is an agent (a service account, or an agent by the identity policy Pacto delivery publishes). It has no approve tool.

Over HTTP, --auth-issuer and --resource make every request carry a bearer token the server verifies (issuer, audience, expiry) and publish protected-resource metadata (RFC 9728); a bind beyond loopback needs them and refuses --auth and --allow-writes, which would lend this process's service credential to every caller. With --delivery the server then exchanges each caller's token for one the apiserver accepts (RFC 8693, --exchange-client-id) and builds the tools for that caller on every request, so an agent proposes as itself and a person gets the read-only tools. With --fleet the server names each caller with the claim mapping (--oidc-username-claim, --oidc-username-prefix, --oidc-groups-claim and --oidc-groups-prefix) and asks Kubernetes RBAC about that user; the API server does not confirm it, so the mapping must match its claimMappings.

With --publish, the authoring server also exposes pacto_publish_plan and pacto_publish, which publish a contract's version exactly as `pacto publish` does, with this process's registry credentials.

A bundle reference, --root, --fleet, --delivery and --publish select different servers and cannot be combined.

```
pacto mcp [bundle-ref] [flags]
```

**Examples:**

```
  # Start MCP server over stdio (default)
  pacto mcp

  # Start MCP server over HTTP
  pacto mcp -t http

  # Expose a bundle's OpenAPI operations as agent tools
  pacto mcp ./my-service --base-url https://api.example.com

  # Include mutating operations and an auth credential
  pacto mcp oci://ghcr.io/acme/svc:1.0.0 --base-url https://api.example.com \
    --auth bearerAuth=$TOKEN --allow-writes

  # Expose a contract catalog discovered from explicit roots
  pacto mcp --root oci://ghcr.io/acme/platform:1.4.0 --root ./experimental-platform
```

**Flags:**

```
      --allow-writes[=true|false]     expose mutating operations (POST/PUT/PATCH/DELETE) as tools
      --audience string               with --auth-issuer: the audience incoming tokens must carry (default --resource)
      --auth stringArray              credential for a security scheme as name=value (repeatable)
      --auth-issuer string            OpenID issuer whose bearer tokens every HTTP request must carry
      --base-url string               base URL for live invocation (overrides the OpenAPI servers[] URL)
      --cache[=true|false]            include every bundle in the local OCI cache as an offline baseline revision
      --dashboard-url string          with --fleet: base URL of a Pacto dashboard; fleet answers then carry an href to each entity's page there
      --delivery[=true|false]         expose the Pacto delivery tools over the ambient cluster
      --delivery-namespace string     in --delivery mode: namespace Pacto delivery runs in, whose published identity policy (agent, break-glass and human groups, team prefix) says who is an agent and who may answer (default "pacto-delivery")
      --delivery-trust string         the trust config delivery records (in --delivery mode) and the golden paths pacto_create creates from are verified with (the recorder's PEM public key or a YAML trust config; default $PACTO_DELIVERY_TRUST)
      --evidence-url stringArray      base URL of an Evidence Server to consume its read-only operational-graph contribution over HTTP (repeatable)
      --exchange-audience string      with --delivery over HTTP: the audience to exchange for, one the apiserver accepts (default "pacto-cli")
      --exchange-client-id string     with --delivery over HTTP: the server's own OAuth client, which exchanges each caller's token for the cluster (RFC 8693); its secret comes from PACTO_MCP_EXCHANGE_CLIENT_SECRET
      --fleet[=true|false]            expose read-only operational-graph (fleet) query tools
      --freshness duration            mark target evidence older than this as stale (0 disables)
  -h, --help[=true|false]             help for mcp
      --host string                   bind address for HTTP transport; beyond loopback it needs --auth-issuer (default "127.0.0.1")
      --k8s[=true|false]              include live Pacto CRs from the current Kubernetes cluster as targets
      --local stringArray             local bundle root(s) to scan (repeatable) (default [.])
      --mira-source stringArray       base URL of a Mira node whose service map supplies observed calls between services (repeatable)
      --namespace string              namespace to read Pacto CRs from with --k8s (empty = all namespaces)
      --oci stringArray               registry reference to include as a published-baseline revision (repeatable)
      --oidc-groups-claim string      ID token claim the API server takes the groups from; must match its claim mapping (default groups)

      --oidc-username-claim string    ID token claim the API server takes the username from; must match its claim mapping (default sub)
      --oidc-username-prefix string   prefix the API server puts before the username; must match its claim mapping (default the issuer URL and #, none for the email claim; - for none)
      --port int                      port for HTTP transport (default 8585)
      --publish[=true|false]          expose pacto_publish_plan and pacto_publish beside the authoring tools
      --resource string               with --auth-issuer: this endpoint's URL as clients reach it, served as protected-resource metadata (RFC 9728)
      --root stringArray              contract root to discover a read-only catalog from: a local bundle path or an oci:// reference (repeatable)
      --target-state stringArray      offline target-state fixture file(s) supplying targets, for demos and tests; production targets arrive as signed EvidenceSets (repeatable)

The **default** server exposes the four authoring tools below. A bundle reference and four flags select a different server, each with its own tools. See [Server modes](#server-modes) after this table:

| Tool | Description |
|------|-------------|
| `pacto_create` | Create a new contract from intent-level inputs (name, description, interfaces, runtime semantics), or with `from` from a golden path (stdio only). Supports dry run. |
| `pacto_edit` | Edit an existing contract: add or remove interfaces, dependencies and configuration references, add environments and set their values, set the service lifecycle or the golden path template, change runtime, update metadata. Checks values against a referenced contract's schema before writing. Supports dry run. |
| `pacto_check` | Validate a contract and return errors, warnings and actionable improvement suggestions. |
| `pacto_schema` | Return the Pacto format explanation and full JSON Schema reference. |

These four authoring tools operate on local contract directories (they read and write `pacto.yaml` on disk) and accept no `oci://` refs.

### Server modes

The default server exposes the authoring tools above. A bundle reference, `--root`, `--fleet`, `--publish` and `--delivery` each select a different server. Passing more than one is an error:

| Invocation | Server |
|------------|--------|
| `pacto mcp` | Authoring tools. |
| `pacto mcp <bundle-ref>` | Authoring tools plus the bundle's OpenAPI operations as executable agent tools, alongside a `pacto_skill` tool for any bundled skills. |
| `pacto mcp --fleet` | Authoring tools plus read-only [operational-graph](operational-graph.md) query tools. |
| `pacto mcp --publish` | Authoring tools plus `pacto_publish_plan` and `pacto_publish`, which publish a version to your registry. Stdio only. |
| `pacto mcp --delivery` | Authoring tools plus the delivery tools over the cluster your kubeconfig points at: read delivery state and, for an agent, ask for or cancel a change. There is no approve tool. |
| `pacto mcp --root <ref> [--root <ref>]` | A read-only contract catalog discovered from the named roots. Catalog mode registers only catalog tools, and none of them writes to disk. |

`--root` is repeatable and takes a local bundle directory or an `oci://` reference. The roots and their dependency closure are resolved once, at startup, through the same reference parsing, credentials and cache the rest of the CLI uses; after that the session is frozen, so every answer reflects startup state even if a registry tag moves. A root that fails to resolve stays visible with a classified reason, and the catalog reports itself as partial. The catalog reads only the named roots and their closure, never refreshes and persists nothing.

### Fleet tool arguments

The arguments each fleet query tool takes. Arguments are optional unless marked:

| Tool | Arguments |
|------|-----------|
| `pacto_fleet_search` | `text`, `owner`, `business_domain`, `offering`, `status`, `compliance`, `workload`, `scope`, `source`, `ready`, `not_ready`, `has_capability`, `has_dependency`, `template` (`only` keeps golden paths, `exclude` leaves them out), `limit`, `offset` |
| `pacto_fleet_get` | `service` (a logical service) **or** `target` (an operational target by key or name) |
| `pacto_fleet_graph` | `service`, `revision` or `target` to root the traversal, then `direction`, `transitive` and `max_depth` (`0` = unlimited) |
| `pacto_fleet_status` | `needs_attention` for every category, or any of `invalid`, `non_compliant`, `unknown`, `stale`, `unresolved_deps`, `unsatisfied_ranges`, `missing_readiness`, `unowned`, `undeclared`, `golden_path_deployed`; plus `limit`. No category, including empty input, reports every category |
| `pacto_fleet_explain` | `subject` (**required**): a service name or a target key or name |
| `pacto_fleet_entities` | `text`, `kind` (`service`, `owner`, `domain` or `offering`; empty lists all four), `owner`, `owner_key`, `business_domain`, `offering`, `consumes` (services that depend on or reference a provider of this offering), `template` (`only` lists golden paths, `exclude` leaves them out), `created_from` (the services created from this golden path, by service key), `ownership`, `status`, `sort`, `limit`, `offset` |
| `pacto_fleet_entity` | `kind` and `key` (**both required**): a service, revision, target, owner, source, business domain or offering |
| `pacto_fleet_attention` | `category`, `severity`, `owner`, `owner_key`, `business_domain`, `service`, `limit`, `offset` |
| `pacto_fleet_neighborhood` | `service` (**required**): a service name or key, then `direction` (`dependencies`, `dependents` or `both`, the default), `depth`, `views` (comma-separated `expected`, `observed` and `differences`; empty means `expected,observed`) and `max_nodes` |
| `pacto_fleet_versions` | `offering` (**required**), then `provider` (a key, or a name only one domain uses) and `range` (a semver range; each version then carries `rangeStatus` and each provider its `latestCompatible` version) |
| `pacto_impact` | `old_ref` and `new_ref` (**both required**), plus `include_observed` and `traces` |

With `--fleet`, the server rebuilds its snapshot when a call arrives 30 seconds or more after the last rebuild attempt, and `pacto_impact` analyses over the same snapshot as the other tools. Add `--dashboard-url <url>` to make search, graph, status, entities, entity, attention, neighborhood and versions answers carry an `href` to each entity's page on that Pacto dashboard, and each contracted consumer in a `pacto_impact` answer an `href` to its service page.

## `pacto publish`

Publishes every artifact the contract's publish section declares (pactoVersion 2.1), the contract bundle and the deploy artifact Flux applies, all tagged with service.version. Docker or the declared command builds. Pacto pushes each artifact to a new tag, signs every digest with Sigstore (built in) and attaches the SBOM files the build wrote. A breaking change since the last published version is refused below a major bump (a minor before 1.0).

--plan shows what is missing and changes nothing. Running publish again from the same commit finishes what is missing and changes nothing else. --propose hands the deploy artifact to Pacto delivery as a promote on a Stage, once the Stage records it as published, meaning Flux polled the candidate OCIRepository and verified the signature. It waits up to --propose-timeout for that.

```
pacto publish [dir] [flags]
```

**Examples:**

```
  # What would be published, and what refuses it
  pacto publish --plan

  # The same, for the contract in ./payments
  pacto publish --plan ./payments

  # Publish, then propose the version on the test Stage
  pacto publish --propose test/payments
```

**Flags:**

```
  -h, --help[=true|false]          help for publish
  -p, --path string                path to contract directory, the same as [dir] (default: current directory)
      --plan[=true|false]          show what is missing and what refuses it; change nothing
      --propose string             after publishing, propose the deploy artifact on <namespace>/<stage> (needs delivery.enabled on the pacto-operator chart)
      --propose-timeout duration   how long --propose waits for the Stage to record the version as published (default 10m0s)
      --revision string            source revision stamped on every artifact (default: the git commit of the contract directory, which must have no uncommitted changes)
      --set stringArray            set a contract value (e.g. --set service.version=2.0.0)
      --values stringArray         values file to merge into the contract (can be repeated; last wins)
```

## `pacto push`

Validates the contract (including remote policy and config refs), builds an OCI artifact and pushes it to the specified registry reference. Pushing the same content again succeeds without writing anything; different content under an existing reference is refused unless --force.

```
pacto push <ref> [flags]
```

**Examples:**

```
  # Push with auto-tag (uses contract version)
  pacto push oci://ghcr.io/acme/my-service-pacto -p my-service

  # Push with explicit tag
  pacto push oci://ghcr.io/acme/my-service-pacto:latest -p my-service

  # Force overwrite an existing artifact
  pacto push oci://ghcr.io/acme/my-service-pacto -p my-service --force
```

**Flags:**

```
  -f, --force[=true|false]   overwrite existing artifact in registry
  -h, --help[=true|false]    help for push
  -p, --path string          path to contract directory (default: current directory)
      --set stringArray      set a contract value (e.g. --set service.version=2.0.0)
      --values stringArray   values file to merge into the contract (can be repeated; last wins)
```

If the tag already holds the same content, `pacto push` succeeds and writes nothing. If it holds different content, `pacto push` refuses with a non-zero exit and writes nothing. Use `--force` to overwrite.

!!! note "`--values` has no `-f` shorthand on push"
    On every other override-taking command `-f` is the shorthand for `--values`. On `pacto push`, `-f` is `--force`, so `--values` must be spelled out in full here.

## `pacto run`

Starts the command and watches the TCP sockets of its whole process tree: the interfaces bound with --bind must be listened on, the dependencies bound with --dep reached. Every --interval it prints the contract's compliance and findings in --output-format; once the command exits it prints a final round from the last view taken while the command ran, and exits with the command's exit code. With --fail-on it exits 1 instead of 0 when the final verdict is that bad or worse.

The command runs in a process group of its own, so a Ctrl-C reaches it once. When pacto run owns the terminal, the command's group takes it over: it reads the terminal and gets Ctrl-C and Ctrl-Z straight from it, and pacto run takes the terminal back once it exits. Otherwise SIGINT and SIGTERM sent to pacto run are passed on to the command's whole group.

Pacto leaves the command's stdin, stdout and stderr untouched. Rounds go to stderr, each in a single write, or with --report to a file: the file is truncated when the run starts and every round is appended to it in a single write, so a reader following it sees whole rounds (with json, one object per line).

With root (or BPF, PERFMON, SYS_PTRACE and write access to its own cgroup) on Linux 5.11 or later with BTF and cgroup v2 (or 5.8 or later with BTF and root or CAP_SYS_RESOURCE), the command starts inside a new cgroup pacto-run-&lt;pid&gt; and an eBPF program sees every listener and every connection outcome of the tree, failures included (collector pacto-run+ebpf). Otherwise it falls back to polling /proc every second and says so (collector pacto-run): listeners are seen in full, so a missing one is still confirmed, but a connection is seen only while it is open at a poll and a failed connection never, so a dependency is reported reachable or unknown, never unreachable. If the program attached but the command cannot start inside the new cgroup, the run falls back to polling too and says so. Elsewhere than Linux the command runs unobserved and every runtime assertion is unsupported.

A negative is reported once it persists for --stabilization-window. Health and metrics capabilities are probed on --host at their bound interface's port. With --evidence-url every round is also signed and sent to an Evidence Server, which needs the contract pinned as oci://...@sha256:&lt;digest&gt;.

```
pacto run --contract <dir|oci ref> [flags] -- command [args...]
```

**Examples:**

```
  pacto run --contract ./payments --bind api=8080 --dep postgres=127.0.0.1:5432 -- ./payments-server
  pacto run --contract oci://ghcr.io/acme/payments:1.4.0 --bind api=8080 --fail-on noncompliant \
    --stabilization-window 30s --output-format json --report rounds.jsonl -- java -jar payments.jar
```

**Flags:**

```
      --bind stringArray                interface=port the command serves the interface on (repeatable)
      --cgroup-root string              cgroup v2 directory the session cgroup is created in (default: the caller's own cgroup under /sys/fs/cgroup)
      --contract string                 contract bundle directory or oci:// reference (required)
      --dep stringArray                 dependency=host:port the command reaches the dependency at (repeatable)
      --enable-probing[=true|false]     also probe the wire protocol of every interface found listening
      --evidence-key string             private key file envelopes are signed with
      --evidence-key-id string          key id (must match the server's trust entry)
      --evidence-producer string        producer id
      --evidence-url string             Evidence Server base URL
      --fail-on string                  exit 1 when the command exits 0 but the final verdict is this bad or worse: one of [none noncompliant unknown] (default "none")
  -h, --help[=true|false]               help for run
      --host string                     address capability and protocol probes dial (default "127.0.0.1")
      --interval duration               how often a round is evaluated and printed (whole seconds) (default 10s)
      --proc-root string                where /proc is mounted (default "/proc")
      --report string                   file every round is appended to instead of stderr (truncated when the run starts)
      --ringbuf-size uint32             kernel ring buffer size in bytes; a power of two and a multiple of the page size (default 262144)
      --stabilization-window duration   how long a negative must persist before it is reported (default 2m0s)
```

## `pacto tui`

Opens a full-screen terminal UI over the same fleet snapshot `pacto fleet` queries. Navigate services, revisions, targets, owners and sources, then run pacto's verbs against the selection, which becomes the command's argument.

Read verbs run in-process against the loaded snapshot. Write verbs shell out to this same binary so they own the terminal, and every one of them asks for confirmation first. Pass --read-only to hide the write verbs entirely.

Requires an interactive terminal. In a pipeline or CI, use the plain commands.

```
pacto tui [flags]
```

**Examples:**

```
  # Browse the local fleet
  pacto tui --local .

  # Browse a live cluster plus the local bundles, without write verbs
  pacto tui --local . --k8s --read-only
```

**Flags:**

```
      --cache[=true|false]         include every bundle in the local OCI cache as an offline baseline revision
      --evidence-url stringArray   base URL of an Evidence Server to consume its read-only operational-graph contribution over HTTP (repeatable)
      --freshness duration         mark target evidence older than this as stale (0 disables)
  -h, --help[=true|false]          help for tui
      --k8s[=true|false]           include live Pacto CRs from the current Kubernetes cluster as targets
      --local stringArray          local bundle root(s) to scan (repeatable) (default [.])
      --mira-source stringArray    base URL of a Mira node whose service map supplies observed calls between services (repeatable)
      --namespace string           namespace to read Pacto CRs from with --k8s (empty = all namespaces)
      --oci stringArray            registry reference to include as a published-baseline revision (repeatable)
      --read-only[=true|false]     hide every write verb
      --root stringArray           contract root whose whole dependency closure joins the snapshot: a local bundle path or an oci:// reference (repeatable)
      --target-state stringArray   offline target-state fixture file(s) supplying targets, for demos and tests; production targets arrive as signed EvidenceSets (repeatable)
      --traces stringArray         OTLP/JSON trace file supplying runtime-observed dependency edges, folded into the snapshot as observed relationships (repeatable)
```

### Update notifications

When a newer version is available, pacto displays a notification after any command:

```
A new version of pacto is available: v1.0.0 -> v1.2.0
Run 'pacto update' to update.
```

The check runs asynchronously and adds no latency. Results are cached for 24 hours in `~/.config/pacto/update-check.json`.

Notifications are suppressed when:

- Running a dev build
- Using `--output-format json` or `--output-format markdown` (the notice shows only for text output)
- The `PACTO_NO_UPDATE_CHECK=1` environment variable is set

## `pacto validate`

Validates a pacto.yaml in the given directory (or oci:// reference) against the specification, running the three validation layers: structural, cross-field and policy.

The output has one PASS, FAIL or SKIP line per stage, in order: load, lock, structural, cross-field, policy, configuration-refs, environments, guarantees, readiness and closure. The configuration-refs stage fetches the contract each configuration ref names and checks the values against its configuration schema; a ref that cannot be fetched fails it when values depend on it. The environments stage checks each environment's file against the schema of every configuration it names. Each error sits under its stage with its file:line:column when Pacto can locate it. A failed load or lock stage skips every stage after it, and a failed structural, cross-field or policy stage skips the stages after it up to environments. A failed configuration-refs stage skips nothing. The guarantees, readiness and closure stages run even when an earlier stage fails. The last line, Next:, names the one command to run now. With --output-format json the same comes as stages and next.

```
pacto validate [dir | oci://ref] [flags]
```

**Examples:**

```
  # Validate a local contract
  pacto validate my-service

  # Validate from current directory
  pacto validate

  # Validate from an OCI registry
  pacto validate oci://ghcr.io/acme/my-service-pacto:1.0.0

  # JSON output
  pacto validate --output-format json my-service

  # Also check the readiness gate (fail if score < minScore)
  pacto validate --readiness my-service

  # Also check every dependency against this contract's policies
  pacto validate --closure my-service
```

**Flags:**

```
      --closure[=true|false]     also check every contract in the dependency closure against the policies this contract resolves. Fails when a dependency cannot be resolved and warns about deprecated interfaces of direct dependencies. Fetches each dependency once
  -h, --help[=true|false]        help for validate
      --readiness[=true|false]   also check the readiness gate: fail if the derived readiness score is below the declared (or default 100) minScore. Opt-in because gate evaluation is time-dependent (check expiry is compared against the run time), which would otherwise make plain validation non-deterministic
      --set stringArray          set a contract value (e.g. --set service.version=2.0.0)
  -f, --values stringArray       values file to merge into the contract (can be repeated; last wins)
```

The `--readiness` gate is **opt-in** because it is time-dependent: it compares the assessment's single `readiness.expires` date against the run time, which would make plain `validate` non-deterministic. Expiry is declared once for the whole assessment. Individual claims carry no `expires` field, and adding one fails to load with `PARSE_ERROR`. Without the flag, validation checks the contract's structure and rules. It still checks the shape of readiness claims and skips the freshness gate. See the [readiness reference](contract-reference/readiness.md#readiness) for the score and gate semantics.

A contract with a mistyped value fails like this:

```
svc is invalid
PASS load
SKIP lock               no pacto.lock
FAIL structural
  svc/pacto.yaml:6:1: ERROR [SCHEMA_VIOLATION] workload: at '/workload': value must be one of 'service', 'job', 'scheduled' (did you mean "service"?)
SKIP cross-field        structural failed
SKIP policy             structural failed
SKIP configuration-refs structural failed
SKIP environments       structural failed
SKIP guarantees         no dependency declares requires
SKIP readiness          not requested (--readiness)
SKIP closure            not requested (--closure)
Next: fix workload at svc/pacto.yaml:6:1 [SCHEMA_VIOLATION], then run pacto validate svc
```

Errors within a stage are listed in file order. An unknown field or an enum value close to a known one carries a `did you mean` hint. A failed `lock` stage names the `pacto lock` command that repairs it. When every stage passes, `Next` is `pacto impact PUBLISHED_REF <dir>`, which shows the services the change breaks; replace `PUBLISHED_REF` with the `oci://` reference of the version you run today. In JSON, `stages` lists each stage with its `status`, `reason` and `errors`, each error carries `line` and `column` when known, `file` is the file they point into, and `next` holds the command. `errors` and `warnings` still list every stage's findings. With `--set` or `-f` an error in `pacto.yaml` carries no `line` or `column`, because those flags validate a merged document whose lines differ from the file. An error in an environment's file keeps them.

**Exit code:** Non-zero if validation fails.

## Environment variables

Boolean variables are parsed the way Go parses a boolean: `1`, `t`, `T`,
`true`, `TRUE` and `True` enable them and `0`, `f`, `F`, `false`, `FALSE` and
`False` disable them. Any other value, including `yes` and `on`,
reads as *off* with no warning. The two opt-outs `PACTO_NO_ANIM` and
`PACTO_NO_UPDATE_CHECK` are the exception: for them any other non-empty value
reads as *on*.

| Variable | Description |
|----------|-------------|
| `PACTO_CACHE_DIR` | Cache directory for the `pacto dashboard` bundle scan. The core CLI cache location is controlled by `XDG_CACHE_HOME` (see below). |
| `PACTO_NO_CACHE` | Boolean. Disable OCI bundle caching (equivalent to `--no-cache`) |
| `PACTO_NO_ANIM` | Boolean. Disables spinners and animations (equivalent to `--no-anim`). |
| `PACTO_NO_UPDATE_CHECK` | Boolean. Disables automatic update checks. |
| `PACTO_REGISTRY_USERNAME` | Registry username for authentication |
| `PACTO_REGISTRY_PASSWORD` | Registry password for authentication |
| `PACTO_REGISTRY_TOKEN` | Registry token for authentication |
| `PACTO_INSECURE_REGISTRIES` | Comma-separated registry **hosts** that Pacto reaches over plain HTTP. It applies to every registry access: `pacto push`, `pacto pull`, dependency and policy resolution and the Evidence Server. Scoped per host, so HTTPS registries are unaffected. Loopback hosts use plain HTTP without being listed. Use it only for a controlled in-cluster registry: it disables transport encryption, so credentials and payloads travel in the clear. |
| `PACTO_EVIDENCE_SOURCE_URL` | Base URL of an Evidence Server whose read-only [operational-graph](operational-graph.md) contribution `pacto dashboard` should consume. The operator sets it when it wires a managed Evidence Server. Unset means *no evidence source configured*, which the dashboard reports separately from an unavailable source. |
| `XDG_CONFIG_HOME` | Override config directory (default: `~/.config`). Affects `pacto login` credentials and update check cache |
| `XDG_CACHE_HOME` | Override cache directory (default: `~/.cache`). Affects OCI bundle cache location |

### Dashboard environment variables

The following variables configure the dashboard when set (see also [Dashboard Container](dashboard-docker.md)). Each mirrors the flag named beside it: an explicitly passed flag wins, and otherwise the variable overrides that flag's default.

| Variable | Flag | Description |
|----------|------|-------------|
| `PACTO_DASHBOARD_REPO` | *(positional args)* | **Comma**-separated OCI repositories, used only when no positional `oci://` argument is given |
| `PACTO_DASHBOARD_HOST` | `--host` | Bind address (default: `127.0.0.1`) |
| `PACTO_DASHBOARD_PORT` | `--port` | HTTP port (default: `3000`) |
| `PACTO_DASHBOARD_NAMESPACE` | `--namespace` | Kubernetes namespace filter (empty = all) |
| `PACTO_DASHBOARD_CORS_ORIGIN` | `--cors-origin` | One explicit origin allowed to call the API. Unset means same-origin only. |
| `PACTO_DASHBOARD_TRACES` | `--traces` | OTLP/JSON trace files to fold observed dependencies from |
| `PACTO_DASHBOARD_MIRA_SOURCES` | `--mira-source` | Space-separated Mira base URLs whose service map supplies observed calls |
| `PACTO_DASHBOARD_TRACE_SOURCES` | `--trace-source` | Named offline trace sources as `NAME=PATH`, where `NAME` is the source's identity (what the fleet, the API and the dashboard's Data Source list call it) and `PATH` is the trace file location. Identity and location are separate, so reordering the configuration or moving the file keeps the source's name. Two sources whose files share a basename stay two sources. A name must be unique across every Data Source the dashboard assembles. |

!!! warning "The three list variables split on **whitespace**"
    `PACTO_DASHBOARD_TRACES`, `PACTO_DASHBOARD_TRACE_SOURCES` and
    `PACTO_DASHBOARD_MIRA_SOURCES` go through the
    same generic flag binding as every other dashboard variable, which splits a
    multi-valued string on spaces. `PACTO_DASHBOARD_TRACES="a.json b.json"` supplies
    two files; `PACTO_DASHBOARD_TRACES=a.json,b.json` supplies **one**, named
    `a.json,b.json`. `PACTO_DASHBOARD_REPO` is read directly and splits on
    commas.

    The dashboard starts either way: it skips a trace file it cannot read, so the
    symptom is missing observed dependencies with no error. Check the snapshot's reported limitations if the operational
    graph looks emptier than you expect.

## Authentication

Pacto follows this credential resolution chain:

1. Environment variables (`PACTO_REGISTRY_TOKEN`, or `PACTO_REGISTRY_USERNAME` + `PACTO_REGISTRY_PASSWORD`)
2. Pacto config (`~/.config/pacto/config.json`, written by `pacto login`, which persists `--username` and `--password`)
3. GitHub CLI (`gh auth token`, for `ghcr.io` and `docker.pkg.github.com` only)
4. Docker config (`~/.docker/config.json`) and credential helpers (including cloud-registry helpers for ECR, GCR and ACR)
5. Anonymous fallback

For GitHub registries, step 3 means you can skip `pacto login` entirely if you have `gh` authenticated with the `write:packages` scope (see [`pacto login`](#pacto-login) above).

Pacto stores no credentials in contract files.
