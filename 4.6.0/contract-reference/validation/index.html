    Validation layers¶

    pacto validate tells you whether a contract is well-formed before anyone relies on it. Run it in the bundle directory:

    pacto validate .

    It runs three checks in order and then the configuration-refs stage and the environments stage, and so does anything else that has to trust a contract. pack, push and publish refuse before they write or transmit a byte, and the operator revalidates every bundle it loads. Each layer short-circuits: if it fails, the layers after it are skipped, so one broken field can hide the rest. A failed configuration-refs stage skips nothing.

    Layer 1: Structural (JSON Schema)¶

    Validates against the embedded schema of the contract's version, pacto-v2.0.schema.json, pacto-v2.1.schema.json, pacto-v2.2.schema.json, pacto-v2.3.schema.json, pacto-v2.4.schema.json or pacto-v2.5.schema.json:

    • Field types match
    • Required fields are present (including the mandatory required on configurations[] and dependencies[])
    • Enum values are valid (for example interface type is openapi/asyncapi/grpc/mcp, capabilities[].type is health/metrics/extension, policies[].target is contract)
    • Fields that must carry a value are non-empty (for example interfaces[].ref and checks[].file)
    • Discriminated shapes hold: a configurations[] entry has exactly one of schema or ref, a capabilities[] extension requires a namespaced ref and health or metrics sets no ref
    • State invariants hold (stateless requires ephemeral durability)
    • A pacto.inferred.yaml in the bundle parses, and every file it cites is in the bundle with the digest it records, and a surface section names the identity service.external names (INFERRED_RECORD_INVALID)
    • A declaration in that record agrees with pacto.yaml: each range it accepts or requests is the declared compatibility (DECLARATION_ACCEPTED_MISMATCH), and each other proposed range stays unknown (DECLARATION_RANGE_NOT_ACCEPTED)

    Structural failures report SCHEMA_VIOLATION. A field a later version adds, in an older contract, reports that version's code for each use instead: set pactoVersion to that version, which keeps every older field.

    Field Version Code
    publish, checks, an external dependency, an mcp interface "2.1" NEEDS_PACTO_2_1
    An interface lifecycle, compatibilityEpoch or guarantees, a dependency requires "2.2" NEEDS_PACTO_2_2
    environments "2.3" NEEDS_PACTO_2_3
    service.domain, service.offering, service.summary, service.lifecycle, service.template, service.origin, values or a configuration selector beside a configuration ref "2.4" NEEDS_PACTO_2_4
    service.external, a dependency compatibility: unknown or identity, an interface port, breaks, a pacto.inferred.yaml in the bundle "2.5" NEEDS_PACTO_2_5
    No field: the contract declares a pactoVersion older than the CLI's newest any older 2.x CONTRACT_BEHIND (info, never fails pacto validate)
    • pacto validate and pacto_check report CONTRACT_BEHIND on the structural stage, in warnings, with valid and the exit code unchanged.
    • Its message says what raising pactoVersion does. Validation checks the pacto.yaml you wrote, without -f or --set values, again at the newest version. The message says the raise keeps what the contract means, or names the finding it would add (usually ENVIRONMENT_VALUES_MISSING, because from "2.4" a required configuration taken by ref has its defaults checked) or says to fix the errors the run reports before Pacto can tell.
    • When raising a contract older than "2.4" that takes a configuration by ref adds no finding, the message says the operator then also accepts ContractOverrides values for those configurations.
    • The fleet revision detail (pacto fleet entity, pacto_fleet_entity, the TUI and the dashboard revision page) shows the declared pactoVersion as 2.3 (behind 2.5). In JSON, pactoVersionCurrent is the newest version the Pacto that answered knows, and pactoVersionUnknown marks a version it does not know. A revision pacto ci raised in memory reads 2.5 (migrated from 2.4, inferred), or 2.5 (behind <newer>; migrated from 2.4, inferred) for a newer Pacto. In JSON, migratedFrom holds the version the authored pacto.yaml declared. It is inferred, read only from a verified pacto.inferred.yaml.
    • When the message says the raise keeps what the contract means, it ends with "run pacto migrate to rewrite the file". pacto migrate rewrites every behind pacto.yaml in a repository, and only in that case.
    • A 1.x contract follows MIGRATION.md and is never raised automatically.

    A contract that fails to load, because of malformed YAML, an unknown field or a pactoVersion other than "2.0", "2.1", "2.2", "2.3", "2.4" or "2.5", fails before any layer runs and reports PARSE_ERROR. Loading is the parse step that turns pacto.yaml into a contract. Validation starts once it succeeds.

    An absent pactoVersion reads as the newest version the CLI supports. In a "2.5" contract service, service.name and service.version may be absent too, so an empty pacto.yaml is valid. pack, push and publish write the version into the bundled pacto.yaml and refuse a contract that does not declare service.version (PUBLISH_NEEDS_SERVICE_VERSION) or service.name (PUBLISH_NEEDS_SERVICE_NAME). A bundle read from a registry, and an inline contract in a Pacto resource, must declare all three.

    The operational graph drops an inferred name another service also claims (SERVICE_NAME_COLLISION). pacto impact keeps a breaking change to a contract with an inferred name unverified (SERVICE_NAME_INFERRED).

    Layer 2: Cross-field¶

    Validates semantic references and consistency:

    Rule Code
    service.version parses as semver, leniently: 1, 0.1 and v0.1 all pass INVALID_SEMVER
    Interface names are unique DUPLICATE_INTERFACE_NAME
    interfaces[].lifecycle dates are strict YYYY-MM-DD and sunset is not before deprecated INVALID_INTERFACE_LIFECYCLE
    interfaces[].lifecycle.successor names another interface or is an absolute URL INTERFACE_SUCCESSOR_UNKNOWN
    service.lifecycle dates are strict YYYY-MM-DD and sunset is not before deprecated INVALID_SERVICE_LIFECYCLE
    service.lifecycle.successor is an absolute URL SERVICE_SUCCESSOR_INVALID
    service.template.plugins[].name values are unique DUPLICATE_TEMPLATE_PLUGIN
    service.origin.ref is a valid oci:// reference or a directory path INVALID_ORIGIN_REF
    Configuration names are unique DUPLICATE_CONFIGURATION_NAME
    Policy names are unique DUPLICATE_POLICY_NAME
    Dependency names are unique DUPLICATE_DEPENDENCY_NAME
    Interface spec file exists in the bundle FILE_NOT_FOUND
    Interface spec file parses, if the ref ends .json, .yaml or .yml (for any other extension, only existence is checked) INVALID_INTERFACE_SPEC
    An mcp interface file lists tools, each with a name used once INVALID_MCP_TOOLS
    Check names are unique DUPLICATE_CHECK_NAME
    checks[].file exists in the bundle FILE_NOT_FOUND
    extension capability ref is well-formed CAPABILITY_REF_INVALID
    Each standard capability type is declared once DUPLICATE_CAPABILITY
    capabilities[].binding.interface matches a declared interface CAPABILITY_INTERFACE_UNKNOWN
    capabilities[].binding.path is a safe application path CAPABILITY_PATH_INVALID
    OCI dependency refs (oci://) are valid OCI references INVALID_OCI_REF
    A dependency has a name, or a ref its name is derived from DEPENDENCY_NAME_REQUIRED
    A dependency without ref is external, or from 2.5 a dependency by name DEPENDENCY_REF_REQUIRED, NEEDS_PACTO_2_5
    A dependency by name gives no version VERSION_WITHOUT_REF
    An external dependency without ref has a version EXTERNAL_VERSION_REQUIRED
    compatibility appears only with ref, and version only without it COMPATIBILITY_WITHOUT_REF, VERSION_WITH_REF
    identity appears only on an external dependency without ref IDENTITY_WITHOUT_EXTERNAL
    identity and service.external are canonical external identities, other than other-egress INVALID_EXTERNAL_IDENTITY
    A dependency with ref has a compatibility range EMPTY_COMPATIBILITY
    Compatibility ranges are valid semver constraints INVALID_COMPATIBILITY
    OCI dependency pins a digest TAG_NOT_DIGEST (warning)
    configurations[].ref is a valid OCI reference INVALID_CONFIG_REF
    configurations[].schema file exists in the bundle FILE_NOT_FOUND
    configurations[].schema file is valid JSON INVALID_CONFIG_JSON
    configurations[].schema file is valid JSON Schema INVALID_CONFIG_SCHEMA
    configurations[].values match the local schema (values beside a ref are checked by the configuration-refs stage) CONFIG_VALUES_VALIDATION_FAILED
    policies[].schema file exists in the bundle FILE_NOT_FOUND
    policies[].schema file is valid JSON INVALID_POLICY_JSON
    policies[].schema file is valid JSON Schema INVALID_POLICY_SCHEMA
    policies[].ref is a valid OCI reference INVALID_POLICY_REF
    Environment names are unique DUPLICATE_ENVIRONMENT_NAME
    environments[].file is a path in the bundle and the file exists FILE_NOT_FOUND
    environments[].expires appears only with lifetime: temporary ENVIRONMENT_EXPIRES_NOT_TEMPORARY
    environments[].expires is an RFC 3339 time such as 2026-11-20T00:00:00Z INVALID_ENVIRONMENT_EXPIRES
    readiness.claims[].id are unique within the contract DUPLICATE_READINESS_ID
    readiness.claims[].evidence has non-whitespace content EMPTY_READINESS_EVIDENCE
    readiness.claims[].description (when present) has non-whitespace content EMPTY_READINESS_DESCRIPTION
    readiness.expires is a strict YYYY-MM-DD date INVALID_READINESS_EXPIRES
    readiness.history[].{date,version,author,description} are valid/non-blank INVALID_READINESS_REVISION
    A consumer appears in one breaks[] entry at most DUPLICATE_BREAK_CONSUMER
    breaks[].consumers never names the service itself BREAK_NAMES_SELF
    breaks[].expires is a strict YYYY-MM-DD date INVALID_BREAK_EXPIRES

    This table lists the codes you can see. Layer 1 rejects the contract first and reports SCHEMA_VIOLATION wherever the JSON Schema already constrains a field. That covers the interface and capability type enums, a non-empty interfaces[].ref or dependencies[].compatibility, the configurations[] schema/ref choice, policies[].target and the stateless/ephemeral invariant. Layer 2 has its own check for each of those, but a contract that breaks them never gets past Layer 1. Build CI rules only on codes in this table.

    Layer 3: Policy checks¶

    Resolves every declared policy and checks the contract against it. Policies apply with strict AND semantics: the contract must satisfy all of them. Policies have no precedence or override logic, so contradictory policies fail.

    Condition Code
    policies[].ref cannot be resolved (resolver unavailable, network error, bundle not found) POLICY_REF_UNRESOLVED
    Cycle detected in recursive policy resolution chain POLICY_REF_CYCLE
    Contract violates a policy constraint POLICY_VIOLATION
    policies[].ref was skipped because no resolver was configured POLICY_REF_NOT_ENFORCED (warning)

    POLICY_REF_UNRESOLVED is a hard error. Validation fails closed when a referenced policy cannot be resolved.

    When ref-based policies are resolved. Recursive resolution of policies[].ref happens only when a resolver is configured. pacto validate and pacto push both supply one, since they can reach OCI/file refs. A ref policy that cannot be fetched then fails closed with POLICY_REF_UNRESOLVED, which is how pacto push checks remote policies before publishing. pacto pack and the operator pass no resolver. They check only the locally compiled schema-based policies and skip ref policies, so they never report the unresolved error. Cycle detection is per chain: a ref is a cycle only when it reappears in its own resolution chain (A → B → A); two sibling policies pointing at the same ref resolve independently.

    Dependency closure¶

    By default Layer 3 checks the root contract only. pacto validate --closure also checks every contract in the dependency closure against the policies the root resolves. Each dependency's own policies[] is left to its owner's validation. The closure resolves the same way pacto graph does, with one fetch per dependency. External dependencies carry no contract and are skipped.

    Condition Code
    A dependency violates a policy the root resolves CLOSURE_POLICY_VIOLATION
    A dependency cannot be resolved, sits in a dependency cycle or has an unreadable contract CLOSURE_DEPENDENCY_UNRESOLVED
    A direct dependency declares a deprecated interface DEPENDENCY_INTERFACE_DEPRECATED (warning)
    That interface has reached its sunset DEPENDENCY_INTERFACE_SUNSET (warning)
    A direct dependency declares a service lifecycle DEPENDENCY_SERVICE_DEPRECATED (warning)
    That service has reached its sunset DEPENDENCY_SERVICE_SUNSET (warning)

    A policy finding names the dependency in its path, for example dependencies[ledger@1.0.0]. A dependency that cannot be resolved is named in the message. When a dependency declared it, the path names that dependency. An unresolvable dependency fails the run, so the check fails closed.

    A deprecated interface is a warning that names the interface, its sunset and its successor, with the path of the dependency that resolved to it, for example dependencies[1]. Both codes stay warnings so the verdict does not change with the date the check runs. To fail a pipeline after the sunset, gate on DEPENDENCY_INTERFACE_SUNSET in --output-format json. When pacto.lock is present, the lock is verified first and a drifted closure fails with the lock error before the closure is checked.

    Configuration-references stage¶

    After the policy layer, the configuration-refs stage resolves each configuration that takes its schema by ref. It fetches the referenced contract, selects one of its configurations and checks the inline values against that configuration's schema. A selected configuration that is itself a ref is followed to the end of the chain. The stage reports SKIP no configuration references for a contract without one.

    Selecting a configuration describes how the stage picks a configuration from the referenced contract.

    Condition Code
    The ref cannot be fetched, read or compiled, or its chain runs past eight refs, and something depends on it (see below) CONFIG_REF_UNRESOLVED
    The ref cannot be resolved and nothing depends on it, or the caller is a gate CONFIG_REF_UNVERIFIED (warning)
    Values for the ref were not checked because the caller has no resolver CONFIG_REF_NOT_ENFORCED (warning)
    The referenced contract declares several configurations and no configuration names one CONFIG_REF_AMBIGUOUS
    configuration names no configuration of the referenced contract, or it declares none CONFIG_REF_UNKNOWN_CONFIGURATION
    The chain of refs comes back to a ref it already followed CONFIG_REF_CYCLE
    A dependency on the same repository has a compatibility the resolved version is outside of CONFIG_REF_VERSION_OUTSIDE_RANGE
    The inline values fail the selected schema CONFIG_VALUES_VALIDATION_FAILED
    The referenced contract declares a service lifecycle DEPENDENCY_SERVICE_DEPRECATED (warning)
    That service has reached its sunset DEPENDENCY_SERVICE_SUNSET (warning)

    In a "2.0" to "2.3" contract, CONFIG_REF_AMBIGUOUS and CONFIG_REF_UNKNOWN_CONFIGURATION are warnings, because an older contract can carry no selector, and values for that configuration stay unchecked.

    Who resolves refs. pacto validate, pacto push, pacto publish and pacto_check fail closed: a ref reports CONFIG_REF_UNRESOLVED when its resolution protects a check. That is the case when the contract is 2.4, when an environment gives values for the configuration or when the contract also declares a ranged dependency on the same repository. A "2.0" to "2.3" ref with nothing to check reports CONFIG_REF_UNVERIFIED and the stage reports SKIP could not verify:. The fleet, the delivery gate and pacto doc report every unresolved ref as CONFIG_REF_UNVERIFIED and skip the stage, so a missing provider never makes a contract invalid there and never passes its values. pacto pack resolves nothing and warns CONFIG_REF_NOT_ENFORCED for each ref with values to check. The operator pulls referenced contracts itself.

    Values the resolved schema rejects and selection errors in a 2.4 contract are errors for every caller: two declarations contradict each other.

    Environments stage¶

    After the policy layer, the environments stage checks each environment's file against the schema of every configuration it names. It runs when the structural, cross-field and policy layers passed, whatever the configuration-refs stage reported, and reports SKIP no environments declared for a contract without environments. Environments lists the rules and the codes it reports: ENVIRONMENT_UNKNOWN_CONFIGURATION, ENVIRONMENT_VALUES_INVALID, ENVIRONMENT_VALUES_MISSING and the ENVIRONMENT_VALUES_UNVERIFIED warning.

    An error in an environment's file carries that file in file, with line and column pointing into it, also when --set or -f is given. The stage passes only when Pacto checked every value set and found no error. A configuration whose schema is behind a ref is checked against the schema the configuration-refs stage resolved. A ref that stage could not resolve leaves its values unchecked, and so does a run with no bundle files to read, such as the operator loading an inline contract. A stage with no error and an unchecked value set reports SKIP could not verify: and names each environment and configuration.

    pacto validate and pacto_check also add an ENVIRONMENT_EXPIRED warning to this stage for each temporary environment whose expires is at or before the clock of the run. The stage keeps its status, and the verdict does not change with the date. Pacto deletes nothing for an expired environment: remove it with pacto_edit remove_environments or move expires. The fleet, the delivery gate and pacto doc never report this warning.
