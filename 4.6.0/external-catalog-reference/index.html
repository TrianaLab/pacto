    External catalog reference¶

    This page describes how the operational graph names the systems outside your Pacto system that contracts depend on: vendor APIs, managed cloud services and legacy hosts. Each one is a single graph node of kind external, so "who depends on Stripe?" has an answer without anyone writing a contract for Stripe. The operational graph reference covers how queries return them.

    An external system never clears a gate. Pacto delivers none, never checks a version range against one and reports its status as Unknown.

    Identities¶

    An identity is a path of lower-case segments. The same string is the graph key and the CLI and MCP subject external:<identity>.

    Form Example Used for
    <vendor> stripe A vendor API, one global segment
    <provider>/<service>/<account-or-project>/<region>/<id> aws/rds/123456789012/eu-west-1/orders-db A managed cloud resource
    host/<registrable-domain> host/corp-legacy.example A host no catalog entry classifies

    Rules:

    • at most five segments and 253 bytes;
    • each segment is 1 to 63 lower-case letters, digits, ., _ or -, starts and ends with a letter or digit and never contains ..;
    • a host identity has exactly two segments;
    • other-egress is reserved for the cap node.

    An identity carries no cluster: a vendor is the same system whichever cluster calls it. The operator reports a host that an ExternalName Service, a selectorless Service or a ServiceEntry names, and no catalog entry classifies, as legacy.

    How a declared external joins¶

    A dependency with external: true and no ref joins the first identity that applies, in this order:

    Order Match Rule
    1 identity The dependency's identity field (pactoVersion: "2.5")
    2 catalog-alias A catalog alias equal to the dependency name, or to its normalized form (Stripe API is stripe-api), ignoring case; organization entries first
    3 host The registrable domain of a name that is a hostname with a public suffix: api.corp-legacy.example joins host/corp-legacy.example
    4 normalized-name The name lower-cased, a numeric :port dropped, with spaces, _ and / turned into - and other characters dropped: Legacy MQ and legacy-mq join legacy-mq

    A dependency with a ref resolves through its provider contract and never joins. A name that normalizes to nothing, or to other-egress, stays an unresolved external dependency. Consumers write nothing new: two contracts that declare Stripe and stripe-api join one stripe node through the default catalog. Two unrelated systems that share a generic name, such as model, also join by name; set identity or add an organization alias to tell them apart. A managed resource such as aws/rds/123456789012/eu-west-1/orders-db takes the class of its provider and service entry (aws/rds) and keeps its own name. The external page says how its consumers join it: by a declared identity, by a registrable domain or by name only.

    Catalog format¶

    A catalog is one YAML file. Pacto decodes it strictly and rejects unknown keys.

    apiVersion: catalog.pacto.trianalab.io/v1
entries:
  - identity: stripe
    class: vendor-api
    label: Stripe
    aliases: [stripe, stripe-api]
    hosts: [api.stripe.com, "*.stripe.com"]
    sdkModules: [github.com/stripe/stripe-go, npm:stripe, pypi:stripe, "maven:com.stripe:stripe-java"]
    keyPatterns: ["STRIPE_*"]
  - identity: aws/rds
    class: managed-cloud
    hosts: ["*.rds.amazonaws.com"]
    terraform: ["aws_db_instance:identifier"]
    crossplane: [rds.aws.upbound.io/Instance]
    Field Required Rule
    apiVersion Yes Exactly catalog.pacto.trianalab.io/v1
    entries[].identity Yes A valid identity, unique in the file; a managed-cloud entry names exactly <provider>/<service>
    entries[].class Yes vendor-api, managed-cloud, legacy or unclassified
    entries[].label No The name the dashboard shows
    entries[].aliases No Dependency names that join this entry; non-empty
    entries[].hosts No Lower-case DNS names with an optional leading *.
    entries[].sdkModules No Client libraries: a bare Go module path without its /vN suffix, npm:<package>, pypi:<normalized name> (lower case, runs of -, _ and . as one -) or maven:<groupId>:<artifactId>
    entries[].terraform No managed-cloud only. A lower-case resource type, optionally with the attribute that holds the resource id: aws_sqs_queue or aws_db_instance:identifier. An id attribute named like a password, secret, token, key, credential, private key or DSN is refused
    entries[].crossplane No managed-cloud only. <api group>/<Kind> of a managed resource, or of a claim or composite resource of your own XRD
    entries[].keyPatterns No Environment and secret key names: A-Z, 0-9 and _, with at most one trailing *
    entries[].otel No dbSystem, messagingSystem and rpcSystem lists of OpenTelemetry system values

    An alias, host, key pattern, SDK module, Terraform resource type or Crossplane kind claimed by two entries of one file is an error, and the error names the entry. A file holds at most 2000 entries and 1 MiB. Pacto joins declared dependencies by aliases. hosts, keyPatterns, sdkModules, terraform, crossplane and otel classify what pacto init, the operator and trace sources recognize, as Matching describes.

    Matching¶

    pacto init, the operator and the fleet all classify through the same matcher.

    Input Rule Confidence
    A host The longest catalog host rule wins, an exact host over a *. wildcard of the same length. An exact rule matches only that name, and *.example.com matches its subdomains and never example.com itself likely
    A host no rule names Three or more labels and a public registrable domain give host/<registrable-domain>. A two-label name matches only a catalog rule, because a namespace short form such as orders.shop reads like a vendor's domain likely
    A configuration key name Compared without case against the entries' key patterns, with - and . read as _, so the Secret name stripe-credentials reads like STRIPE_CREDENTIALS possible
    An SDK a folder's manifest or lockfile lists The package name in its ecosystem. A Go module matches with its /vN suffix dropped, and so does any package under a listed module possible
    A Terraform resource or a Crossplane object in the folder Its resource type, or its <group>/<Kind>, equals an entry's row possible; likely for a Crossplane object whose connection Secret the workload reads
    An OpenTelemetry db.system, messaging.system or rpc.system value Compared exactly, without case, against the entries' values. A protocol no entry claims, such as grpc, gives no match. The default catalog claims only values that name one managed service, such as aws_sqs or dynamodb, so a generic postgresql or kafka callee stays unresolved likely

    A configuration value is a host candidate only when it has a scheme (https://), a port or a key named like a host: one that contains url, uri, host, endpoint, addr, address, server or broker. A value that names no host can still match by its key name. likely means a host or a system value matched. possible means only a key name did, and nothing else confirms it.

    Redaction¶

    The matcher reads a host and a port and nothing else:

    • A URL keeps only its host and port. The user name, password, path, query and fragment are never read, so postgres://user:pass@db.xyz.rds.amazonaws.com:5432/app?password=x shows as db.xyz.rds.amazonaws.com:5432.
    • A value under a key that names a password, secret, token, key, credential, private key or DSN is never parsed. Only its key name is matched. The rule reads parts of a name, so a DATABASE_DSN or KEYCLOAK_URL value gives no host either.
    • A Secret contributes its name and key names, never a value.
    • A comma-separated seed list, such as Kafka brokers, gives one host per entry, and a jdbc: prefix is dropped.

    Names that never match¶

    An IP address, a single label, localhost, a name with a svc label (such as orders.shop.svc.corp.local), a *.cluster.local name and a name with a label outside RFC 1123 give no match. In-cluster names stay dependencies on services. A value that does not parse gives no match, never part of the string.

    Managed resource identities¶

    • A Terraform resource or Crossplane object gets the identity <provider>/<service>/<account>/<region>/<id> only when the provider, account, region and id are all literals in the folder.
    • The id is the entry's id attribute (Terraform) or the crossplane.io/external-name annotation, else the object's metadata.name (Crossplane). A Terraform resource whose id attribute is not a literal is named by its label, and the id is listed as missing.
    • When a part is missing, Pacto never invents it: the dependency keeps the entry's identity and the inferred record names the resource and the parts it misses, as below.
    • A five-segment identity takes the class, label and aliases of its <provider>/<service> entry.
    external:
  identity: aws/sqs
  resource: {type: aws_sqs_queue, name: newsletter-signups, missing: [account, region]}

    The default catalog¶

    Every Pacto binary embeds a default catalog of well-known vendors (Stripe, Twilio, SendGrid, Anthropic, OpenAI, GitHub, Slack, PagerDuty, Datadog, Auth0, Algolia and Mailgun) and the AWS, Google Cloud and Azure managed services. Each host, SDK module, Terraform resource type and Crossplane kind cites the vendor documentation it comes from.

    Each core release publishes the same bytes as an OCI artifact at ghcr.io/trianalab/pacto/external-catalog:<core version> and signs it with Cosign keyless signing, as Installation lists. The digest is the sha256 of a manifest that depends only on the catalog bytes, so the embedded copy and the published artifact have one digest. Every answer records that digest in externalCatalogs, whichever copy was used.

    Pacto checks the default catalog's signature only when a configured source already reads ghcr.io, so a private-registry or air-gapped installation never calls it. The check runs in the background and never delays a build: the first answer reports signature: unknown with a reason saying the check is running, and a later refresh reports the result. A one-shot command such as pacto fleet never starts the check; the dashboard, pacto mcp and the TUI report the result. When the signature verifies, copy reads registry: the embedded copy matches the signed artifact. Otherwise copy reads embedded: Pacto classifies with the copy compiled into the binary and reason says why the signature was not checked. A release run from a branch other than main signs with another identity, so that version's default catalog reads unverified and the embedded copy still classifies.

    Organization catalogs¶

    An organization catalog adds entries and overrides default ones. An entry with the identity of a default entry replaces it, and an alias, host, key pattern, SDK module, Terraform resource type or Crossplane kind the organization claims is taken from any default entry that also claims it.

    Give it by digest:

    Surface Setting
    pacto fleet, pacto impact, pacto mcp, pacto stats, pacto tui --external-catalog oci://REPOSITORY@sha256:DIGEST
    pacto init --external-catalog or PACTO_EXTERNAL_CATALOG, which pacto pack, pacto push and pacto explain also read
    pacto dashboard --external-catalog or PACTO_DASHBOARD_EXTERNAL_CATALOG
    The operator-managed dashboard Chart value dashboard.externalCatalog

    A tag is refused, because a tag can move. The digest pin is what Pacto trusts the catalog by: its signature is reported as unknown with the reason and never decides whether it loads. A catalog Pacto cannot pull or parse is skipped, the default catalog alone classifies and the answer is partial with EXTERNAL_CATALOG_UNAVAILABLE.

    Publish one with ORAS and pin the digest it prints:

    oras push registry.example.com/platform/external-catalog:2026-11 \
  --artifact-type application/vnd.pacto.external-catalog.v1 \
  catalog.yaml:application/vnd.pacto.external-catalog.v1+yaml

    Pacto reads any manifest with that artifactType, the OCI empty config descriptor (ORAS writes it when no --config is given) and one layer of the media type application/vnd.pacto.external-catalog.v1+yaml. From a Pacto checkout, go run ./cmd/genexternalcatalog check -f catalog.yaml validates the file merged over the default and prints the entry count. The digest it prints belongs to Pacto's own minimal manifest; ORAS adds annotations, so pin the digest the registry returns.

    The cap¶

    One answer names at most 200 external systems. Beyond that, the least-consumed fold into one other-egress node of class other-egress, whose folded counts them; a relationship to a folded system keeps its real toExternal and gains foldedInto: other-egress. The answer is partial with EXTERNAL_CAP. The snapshot itself keeps every identity. A list answer shows at most 50 consumers of one external system, with consumersTotal and sourcesTotal counting them all.

    Restricted views¶

    A caller who cannot see a consumer never learns its name. An external system lists only visible consumers and counts the rest in hiddenConsumers, and its totals count visible data only. An external system that only hidden services declare, call or use is left out and counted in the Overview's hiddenExternals. An observed or inferred edge follows its caller, and evidence read on a hidden target is dropped even when its service stays visible. The cap ranks on visible consumers, so two callers with the same view get the same answer.

    Limitations¶

    Limitation Raised when
    EXTERNAL_CATALOG_UNAVAILABLE The organization catalog could not be pulled or is not a valid catalog
    EXTERNAL_CAP An answer folds external systems into other-egress
    EXTERNAL_USE_UNATTRIBUTED A source reported external uses of a service the snapshot does not hold, or with an invalid identity; they are dropped
    EXTERNAL_CATALOG_MISMATCH A source classified external uses with a catalog other than the one the snapshot classifies with
    EXTERNALS_UNREPORTED A target's source cannot say which external systems it uses (an older operator, partial coverage or a stale status)
