    Measure what Pacto does¶

    Pacto can record what it catches as unsigned statistics in a registry you name; pacto stats and the dashboard Metrics page total them, and nothing leaves your registry. This guide shows how to turn recording on, read the totals and keep the records small. The run record reference lists every field a record holds.

    What is recorded¶

    A run record is a small JSON document. Pacto writes one for each pacto diff, pacto impact and pacto publish run in CI that reaches a result, one for each delivery operation the promoter concludes and, when you ask pacto fleet status for it, one coverage snapshot of the fleet. pacto impact event answers, pacto publish --plan and MCP calls record nothing. Recording is opt-in and best effort: a problem with recording prints one warning line, and the command's exit code and output stay the same.

    A record holds no person's name, email address or token. The CI context fields (repository, ciRunUrl and environment) appear only when you list them in --stats-context, and an operation record holds the class of its actor, never a name.

    Where records go¶

    Records go to the repository you name with --stats-registry or PACTO_STATS_REGISTRY, for example ghcr.io/acme/pacto-stats. Pacto never picks one for you. Each service has one anchor in that repository, tagged pacto-stats-<sha256 of the service name>, and each record is an OCI referrer of that anchor, next to your bundles and never inside them. Every record stays in the registry you name. Pacto sends nothing to TrianaLab or any other party.

    A coverage snapshot is the exception: pacto fleet status writes one only with --stats-registry or --stats-file on its own command line and ignores both environment variables on purpose, so a job that sets PACTO_STATS_REGISTRY for its other steps records no coverage by accident:

    pacto fleet status --stats-registry ghcr.io/acme/pacto-stats

    Coverage records has the details.

    Anyone with pull access to the repository can list every recorded service name with plain oras discover, so give it pull access that matches who may see the whole fleet.

    Turn it on in CI¶

    Set the repository on a job that can push to it:

    - run: pacto diff oci://ghcr.io/acme/payments:1.2.0 . --stats-context repository
  env:
    PACTO_STATS_REGISTRY: ghcr.io/acme/pacto-stats

    A job without write access writes the record to a file with --stats-file run-record.json and uploads it as an artifact. A later job of the same trusted repository publishes it:

    pacto stats publish --registry ghcr.io/acme/pacto-stats run-record.json

    The reference has the complete two-job workflow. Never publish files written by untrusted (fork) jobs.

    Turn it on in delivery¶

    The promoter records every operation it concludes when the chart names a repository:

    helm upgrade pacto-operator oci://ghcr.io/trianalab/pacto/charts/pacto-operator \
  --namespace pacto-operator-system --reset-then-reuse-values \
  --set delivery.stats.repository=ghcr.io/acme/pacto-stats

    Delivery run records covers the push credentials and why the repository must be private.

    Read the totals¶

    pacto stats totals the records of a window. With --by owner it infers each service's owner from the fleet snapshot the fleet source flags build:

    pacto stats --registry ghcr.io/acme/pacto-stats --since 30d --by owner

    asOf 2026-11-15T18:44:53Z  window 2026-10-16T18:44:53Z to 2026-11-15T18:44:53Z  records 112 read, 0 skipped (complete)  unsigned statistics; owner inferred as of 2026-11-15T19:44:53+01:00
OWNER     BREAKING CAUGHT  CONSUMERS PROTECTED  CLEAR  BLOCKED  UNVERIFIED
checkout  0 (0 runs)       0 (0 unknown)        4      0        0
orders    0 (0 runs)       0 (0 unknown)        0      0        0
payments  1 (2 runs)       1 (0 unknown)        3      1        0

Environments (alphabetical)
ENVIRONMENT  OPERATIONS  HELD        FAILED     ROLLED BACK  VERIFICATION FAILED  LEAD TIME p50  p90
prod         13          2/13 (15%)  0/13 (0%)  0/13 (0%)    0/13 (0%)            21h0m0s        22h0m0s
test         9           0/9 (0%)    0/9 (0%)   0/9 (0%)     0/9 (0%)             2h0m0s         2h0m0s

    The read-only MCP tool pacto_stats gives the same answer to an agent. An MCP server reads the repository named with --stats-read-registry; over stdio, PACTO_STATS_REGISTRY and the tool's registry argument also work, and over HTTP only the flag turns pacto_stats on (MCP integration). Every answer carries its asOf, its completeness and how many records it read and skipped.

    Read the Metrics page¶

    pacto dashboard --stats-registry draws the same answer on the Metrics page, plus promotion depth and lead time pooled over the environments that end a promotion chain. Only the dashboard computes these: pacto stats and pacto_stats give lead time per environment. Three headline tiles show breaking changes caught with the consumers they protected, release gates by their newest verdict (clear, blocked or unverified) and lead time to production at p50 with its p90. Five charts follow: what Pacto stopped, gate outcomes over time, delivery health by environment, lead time by environment and coverage over time. Each chart has a Show as table view, hovering or focusing a mark shows its exact numbers and every count links to its records.

    An unknown, such as a rate with nothing to take it over, is hatched and never drawn as 0, and unverified gates are dotted. Up to eight environments get one small panel each; more turn delivery health into a heatmap you can filter and group by promotion depth, owner or domain, with owner and domain inferred from the fleet snapshot. A partial snapshot marks the whole answer partial, as pacto stats --by owner does.

    Run records are unsigned statistics¶

    Run records are unsigned statistics. Anyone with push access to the repository can add or change them, so nothing in Pacto that decides reads them: validation, diff, impact, publish and delivery gates work the same with recording on or off. Read the numbers as a trend of what Pacto caught, and use signed delivery records and evidence for anything you have to prove.

    Who sees which records¶

    The CLI and a stdio MCP server act as you and see every record. A signed-in dashboard and an HTTP MCP server started with --auth-issuer show the records of services the viewer may list Pactos for, and operation records only in namespaces where the viewer may list Operations. Records outside the view are left out of every number and never named: the answer says some records are outside your view and is marked partial. A dashboard shared without sign-in (--allow-anonymous) counts only the services of its fleet and no operation record. These restricted readers see no coverage history, only the current value computed from their view. Dashboard access has the details.

    Registries without native Referrers¶

    GHCR and released versions of the CNCF distribution registry have no native Referrers API. On those, run records fall back to the OCI referrers tag, an index of the anchor's records. The fallback has two caveats: two records of one service published at the same moment can drop one of them, and the index grows with every record, so prune it.

    Prune records¶

    Pacto never deletes records. List a service's records with oras, pick the old ones by their dev.pacto.recorded-at annotation and delete them. ORAS 1.2 lists them under manifests and ORAS 1.3 under referrers, so the filter reads both:

    set -o pipefail
repo=registry.example.com/acme/pacto-stats
anchor=pacto-stats-$(printf payments | shasum -a 256 | cut -d' ' -f1)
oras discover --format json "$repo:$anchor" |
  jq -r '((.manifests // []) + (.referrers // []))[] | select(.annotations["dev.pacto.recorded-at"] < "2026-01-01") | .digest' |
  while read -r digest; do oras manifest delete --force "$repo@$digest"; done

    GHCR refuses a manifest delete through the registry API; delete a record there as a package version.
